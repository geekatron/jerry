## 1. What It Specifies (all parts)

ISO/IEC/IEEE 29119 is a joint-logo series under ISO/IEC JTC 1/SC 7/WG 26 (Software Testing Working Group) that standardizes vocabulary, processes, documentation templates, test design techniques, and tooling expectations across the entire software testing lifecycle, applicable to any development methodology. The full series as maintained by WG 26 comprises eight published deliverables:

| Part | Title | Edition in force | Deliverable type | Primary content |
|------|-------|------------------|------------------|-----------------|
| **29119-1** | Software testing -- General concepts | **2022** | International Standard | Vocabulary, taxonomy of test concepts, context for applying the rest of the series. Freely available from ISO (per softwaretestingstandard.org). |
| **29119-2** | Software testing -- Test processes | **2021** | International Standard | Generic test process model with three layers: Organizational Test Process; Test Management (project/phase/type) processes; Dynamic Test processes (plan-design-implement-execute-report). Explicitly *excludes* static testing. |
| **29119-3** | Software testing -- Test documentation | **2021** | International Standard | Documentation templates aligned 1-to-1 with Part 2 processes. Covers Organizational Test Policy, Organizational Test Strategy, Project Test Plan, Test Design Spec, Test Case Spec, Test Procedure Spec, Test Data Requirements, Test Environment Requirements, Test Status Report, Test Completion Report, Test Incident Report. Annex T maps these to pre-existing IEEE 829 artifact names. |
| **29119-4** | Software testing -- Test techniques | **2021** | International Standard | Standard definitions of test design techniques and coverage measures, grouped into: (a) **specification-based** (black-box: equivalence partitioning, boundary value, decision table, state transition, scenario, random, syntax testing, etc.); (b) **structure-based** (white-box: statement, branch, decision, MC/DC, data flow); (c) **experience-based** (error guessing, exploratory, checklist). |
| **29119-5** | Software testing -- Keyword-driven testing | **2024** | International Standard | Requirements for keyword-driven testing frameworks and tools; hierarchical keyword levels (low-level/generic technical keywords like `inputData`, `checkValue`, navigation keywords, vs. higher-level business keywords); common data-exchange format for cross-vendor keyword portability. Supersedes 2016 edition. |
| **29119-6** | Guidelines for the use of ISO/IEC/IEEE 29119 in agile projects | **2021** | Technical Report (TR) | Tailoring guidance for applying 29119 in Scrum / XP / Kanban contexts -- e.g., lightweight versions of Part 3 templates, continuous risk assessment, iteration-level test planning. |
| **29119-11** | Guidelines on the testing of AI-based systems | **2020** | Technical Report (TR) | Risk-based guidance for testing AI/ML systems (non-determinism, oracle problem, data quality, adversarial inputs, bias, explainability). Freely available from ISO (per softwaretestingstandard.org). Under systematic review (deadline reported 2025-10-15, single-source -- flagged). |
| **29119-13** | Using the 29119 series in the testing of biometric systems | **2022** | Technical Report (TR) | Mapping between biometric-specific standards and the 29119 series; risk-based test approach covering reliability, availability, security, usability, human factors, privacy-regulation compliance for biometric systems. |

**Adjacent standards explicitly complementing the series** (per softwaretestingstandard.org):
- **ISO/IEC 20246:2017** -- Work Product Reviews (covers *static* testing, which 29119-2 deliberately excludes).
- **ISO/IEC 33063:2015** -- Process Assessment Model for Software Testing (maturity-style assessment against the 29119-2 process model).
- **ISO/IEC TS 42119-2:2025** -- Overview of testing AI systems, produced by SC 42 (AI), cross-referencing the 29119 series. (Emerging 2025 development.)

## 2. Scope and Boundary

### In scope

- **Dynamic testing** (test execution against a running system): functional and non-functional, manual and automated, scripted and unscripted. Explicitly stated in 29119-3's scope clause per en-standard.eu.
- **Any lifecycle model:** waterfall, iterative, agile -- the process model is intended to be "lifecycle-neutral." Part 6 TR provides agile-specific tailoring guidance.
- **All test levels:** unit, integration, system, acceptance.
- **Both functional and non-functional characteristics** (performance, security, usability, etc., referenced through ISO/IEC 25010 product-quality characteristics).
- **Documentation-driven traceability:** every process step in Part 2 has a corresponding template in Part 3, producing a fully auditable trail.
- **Risk-based testing:** Part 2 mandates a risk-based approach for test strategy, test design prioritization, and completion-criteria selection (per Reqtest / researchgate test-planning diagrams / stureid.info white paper).

### Out of scope / explicit exclusions

- **Static testing** (reviews, inspections, walkthroughs, static analysis): explicitly deferred to **ISO/IEC 20246** per both the committee.iso.org page and Wikipedia. Reason given in Wikipedia: "lack of consensus" at the time Part 2 was drafted.
- **Test tool APIs and technology-specific protocols:** 29119 does not specify wire protocols, language bindings, or tool APIs (WebDriver, HTTP, gRPC, etc.). It sits one level above these.
- **Language-specific or vendor-specific test frameworks:** 29119-5 is framework-agnostic for keyword-driven testing and does not endorse any specific tool.
- **Process maturity scoring:** deferred to ISO/IEC 33063.
- **Specific domain quality characteristics beyond general software:** domain extensions (AI systems, biometrics) are provided as TRs, not as part of the core standard.

## 3. Applicability to a Jerry E2E Skill

For an E2E testing skill targeting web services (UI + API), the 29119 parts matter in the following order of relevance.

### High relevance

**29119-1 (Concepts and definitions)** -- *Foundational.* Provides the canonical vocabulary (test basis, test item, test condition, test coverage item, test case, test procedure, test suite, test level, test type, entry/exit criteria) that a Jerry E2E skill must use to be legible to enterprise QA organizations. Since Part 1 is freely available from ISO, a Jerry E2E skill can cite the exact definitions without paywall friction.

**29119-2 (Test processes)** -- *Process backbone.* The three-layer model (Organizational / Test Management / Dynamic) maps directly onto how Jerry projects are structured:
- *Organizational Test Policy / Strategy* -> Jerry-level defaults for all projects.
- *Project Test Plan* -> per-project E2E test plan produced by the skill.
- *Dynamic Test processes (plan -> design -> implement -> execute -> report)* -> the runtime iteration the skill executes for each E2E scenario.

The dynamic-test workflow (Test Planning -> Test Design & Implementation -> Test Environment Set-Up & Maintenance -> Test Execution -> Test Incident Reporting) is the single most useful concrete artifact for structuring a Jerry E2E workflow.

**29119-3 (Test documentation)** -- *Artifact catalog.* Gives a Jerry E2E skill a drop-in list of documents to generate: Test Plan, Test Design Specification, Test Case Specification, Test Procedure Specification, Test Data Requirements, Test Environment Requirements, Test Status Report, Test Completion Report, Test Incident Report. Annex T's mapping back to IEEE 829 artifact names lets a skill satisfy legacy-documentation stakeholders without extra effort.

### Medium relevance

**29119-4 (Test techniques)** -- *Design-technique catalog.* For E2E specifically, the most relevant techniques are **scenario testing, use-case testing, state-transition testing, and decision-table testing** from the specification-based family, plus **exploratory testing** from the experience-based family. Structure-based techniques (statement, branch, MC/DC) are less relevant at E2E level since E2E tests black-box the system from the outside.

**29119-5 (Keyword-driven testing)** -- *Automation architecture pattern.* If the Jerry E2E skill generates automation with a keyword-driven layer (e.g., high-level business keywords composed of low-level technical keywords like `navigate`, `input`, `checkValue`, `invokeApi`), Part 5 gives a standards-compliant way to structure that keyword hierarchy and a vendor-neutral data-exchange format so keyword libraries can be portable.

**29119-6 (Agile TR)** -- *Tailoring guidance.* Relevant if the Jerry E2E skill is to be used within agile teams; offers lightweight template variants.

### Low relevance for web-services E2E (but noted)

**29119-11 (AI-based systems TR)** -- Relevant only if the web service under test contains AI/ML components (e.g., an LLM-backed endpoint). Addresses oracle problem, non-determinism, test-data quality. Freely available from ISO.

**29119-13 (Biometric systems TR)** -- Specialized; not generally applicable unless the web service performs biometric authentication.

## 4. Strengths and Unique Contributions

1. **Only joint ISO/IEC/IEEE international standard series for software testing.** No other standard series carries this combined authority; joint publication means legal recognition in procurement, regulatory, and contractual contexts in most ISO-member jurisdictions and simultaneously in the IEEE portfolio. (Source: committee.iso.org; softwaretestingstandard.org.)
2. **Explicit replacement for IEEE 829, IEEE 1008, and BS 7925-1/-2.** Organizations with legacy documentation obligations can transition to 29119 with Annex T mappings in Part 3; 29119 is the successor-of-record. (Source: softwaretestingstandard.org.)
3. **Lifecycle-neutral process model.** The three-layer Part 2 model works for waterfall, agile, DevOps, CI/CD -- the only testing-process standard with this breadth. (Source: en.wikipedia.org; arc42.org quality model.)
4. **Integrated artifact set.** Parts 2 and 3 are designed together so every process step has a documented output; this is uniquely strong in the testing-standard space. (Source: en-standard.eu Part 3 scope; Annex T.)
5. **Test-design technique catalog with coverage measures (Part 4).** Gives normative definitions for ~20 techniques and their associated coverage metrics -- widely cited in ISTQB syllabus mappings and academic literature. (Sources: cdn.standards.iteh.ai FDIS draft sample; rcolomo.com mapping paper.)
6. **Risk-based testing is built in, not bolted on.** The Part 2 Design-Test-Strategy activity mandates explicit risk-based prioritization as a first-class input to test-level and technique selection. (Sources: stureid.info white paper; researchgate test-planning figure.)
7. **Free availability of the two most strategically important parts.** ISO publishes Part 1 (concepts/vocabulary) and Part 11 (AI testing) as freely available, lowering adoption friction for the terminology foundation and the highest-growth domain extension. (Source: softwaretestingstandard.org.)
8. **Active evolution.** Part 5:2024 (December 2024) is a recent major revision, showing the series is actively maintained rather than frozen. (Source: standards.ieee.org/ieee/29119-5/11042/.)
9. **Growing AI-testing coverage via 29119-11 + TS 42119-2.** SC 7 and SC 42 are coordinating on AI-system testing, with 29119-11 as the software-testing-side anchor. (Sources: softwaretestingstandard.org; search hits for iso.org/standard/84127.)

## 5. Weaknesses, Gaps, and Criticisms

### The Stop 29119 controversy (2014--present)

Beginning in **summer 2014**, shortly after Parts 1-3 were first published (2013), a coordinated protest emerged from the context-driven and skilled-testing communities:

- **Organizations:** the **Association for Software Testing (AST)** and the **International Society for Software Testing (ISST)** -- the latter formed explicitly in response to 29119's publication (Source: search snippet of sdtimes.com "software testing schism"; en.wikipedia.org).
- **Lead critics** (by name): **James Bach, Cem Kaner, Iain McCowatt** (Wikipedia), **Michael Bolton, James Christie, Keith Klain** (search snippets of developsense.com, clarotesting.wordpress.com, qualityremarks.com).
- **Petition:** hosted at ipetitions.com/petition/stop29119; secondary sources (qxf2.com, clarotesting.wordpress.com 2018 retrospective) reported the signature count reached **"over 3,000"** at peak (single-source / secondary, flagged per P-022 -- the petition page itself was not successfully fetched this session).
- **WG 26 response:** Dr. Stuart Reid (WG 26 convenor) published a rebuttal in September 2014 arguing that the standard "does not restrict testers in how they perform testing" and that risk-based testing is mandated but left methodologically open (Source: search snippet quoting Reid).

### Substantive criticisms (unchanged, still relevant in 2026)

1. **Lack of "true consensus"** -- critics argue ISO/IEC governance rules require consensus of affected professionals, which the drafting process did not achieve within the global testing community. (Source: Wikipedia controversy section.)
2. **Heavyweight documentation burden** -- the standard is accused of privileging paper trails over tester judgment. "Overstructured process model, focused on relentless, ponderous, wasteful bureaucracy and paperwork, with negligible content on actual testing." (Source: search snippet from critic commentary.)
3. **Conflict with the Agile Manifesto** -- critics argue 29119's documentation emphasis conflicts with "working software over comprehensive documentation." Part 6 TR (agile guidance) is viewed by critics as insufficient retrofitting. (Source: search snippets.)
4. **Exclusion of context-driven testing** -- "the standard effectively excludes context-driven testing" as a legitimate approach, pushing a single prescriptive model. (Source: en.wikipedia.org.)
5. **"Implies a single correct way to test"** -- prescriptiveness charge; no such thing as a universal test method. (Source: search snippets of critical commentary.)
6. **Cost-of-access** -- core Parts 2, 3, 4, 5, 6, 13 are paywalled (per-part pricing via ISO/IEEE/national-body resellers, typically CHF/USD low-hundreds per part; exact current pricing not verified this session since ISO.org was blocked -- flagged). Critics argue this conflicts with the goal of community-wide adoption. Only Parts 1 and 11 are free. (Source: softwaretestingstandard.org free-availability note.)
7. **Commercial interest conflicts** -- several critics (Satisfice blog) argue that consulting-firm members of the working groups stand to gain from selling conformance services, a governance concern. (Source: search snippet of satisfice.com "How Not to Standardize Testing".)
8. **Procurement/legal enforcement risk** -- early critics warned the standard could be cited in contracts or litigation as a "professional standard of care" such that non-compliance becomes negligence, imposing it by procurement pressure even on organizations that never chose it. (Source: developsense.com FAQ and context-driven-testing.com -- triangulated via search snippets since direct fetch was blocked.)

### Content gaps (E2E-specific)

- **No explicit guidance for microservices, event-driven, or distributed E2E testing.** The standard predates the dominance of cloud-native architectures and treats the system-under-test as a monolithic unit in most examples.
- **No web-specific guidance.** There is no HTTP/REST/WebSocket/browser-specific content; the skill must bridge from 29119 abstractions to concrete web protocols itself (this is where W3C WebDriver / OpenAPI / OWASP WSTG complement 29119).
- **Static testing excluded** -- requires ISO/IEC 20246 to complete the picture.
- **Test data management** is addressed only as a documentation output (Test Data Requirements); there is no depth on data-generation strategies, synthetic data, or data masking.
- **CI/CD integration** is left as implementation detail; the agile TR (Part 6) is the closest but is still at process-description level.

### Ongoing opposition

Retrospective assessments (James Christie's 2018 blog "Has opposition to ISO 29119 really died down?") suggest the active protest has cooled but opposition has not been retracted; critics continue to advise against mandatory adoption. The philosophical split between context-driven and standards-driven testing factions remains unresolved as of 2026.

## 7. Key Implementation Patterns and Testable Principles

A Jerry E2E skill can encode the following as concrete, testable assertions that make outputs conformant to or informed by 29119. Each principle includes a source anchor.

### Process-level principles (from 29119-2)

| # | Principle | Testable assertion | Source |
|---|-----------|-------------------|--------|
| P1 | Three-layer test process | Every E2E workflow emission has a clear *Organizational* input (policy/strategy defaults), a *Test Management* layer (project test plan), and a *Dynamic Test* layer (execute/report loop) | en.wikipedia.org; arc42.org; slideshare 29119 test management |
| P2 | Test planning is the first step | The skill MUST produce a Test Plan artifact before any test execution activity | Wikipedia; stureid.info |
