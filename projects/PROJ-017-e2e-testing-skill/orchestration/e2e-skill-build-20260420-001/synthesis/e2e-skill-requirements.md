## Synthesis Method

All three input files — lane-standards.md, lane-innovators.md, and eng-team-testing-baseline.md — were read in their entirety before any section of this document was written. A principle is included only where evidence from two or more sources converges, except for principles that address eng-team gaps exclusively (which are sourced from the baseline alone, with the single-source nature made explicit). Tension resolutions are stated with explicit trade-off analysis and a named justification; no tension is resolved by omission or by presenting only one side.

## 1. Executive Summary

### L0: For Stakeholders

The `/e2e-testing` skill gives the Jerry framework the ability to automatically write, run, and verify end-to-end tests for web applications — the kind of tests that click through a real browser the way a user would. Jerry's engineering skill already handles security and code-quality testing at the unit and API level; it has zero coverage of anything that requires a browser. This skill fills that gap. It operates in two modes: generating permanent test scripts for known-critical flows, and using an intelligent in-loop agent for exploratory or self-healing flows where the application keeps changing. Every test it generates traces back to a requirement, a risk, or a security concern so we always know why a test exists. The skill ships with a published quality bar so its own output can be scored objectively.

### L1: For Engineers

The `/e2e-testing` skill provides an LLM-orchestrated E2E testing capability with a three-agent core: `e2e-author` (plans and generates test scenarios), `e2e-executor` (drives the browser via Playwright MCP, emitting either committed Playwright code or live in-loop actions), and `e2e-verifier` (assesses correctness, escalates failures to the author rather than retrying blindly). Two optional agents — `e2e-analyst` (diff-scoped test-suite analysis and coverage gap identification) and `e2e-reporter` (structured multi-level reporting) — extend the core for larger workflows.

The skill's explicit non-goals are: unit testing, API contract testing, static analysis, SAST/DAST, fuzzing, and load/performance testing — all of which remain in `/eng-team`. Security scenarios generated by the skill are WSTG-tagged and complement, but do not replace, eng-qa's threat-driven methodology. The primary invocation mode accepts a `git diff` and scopes tests to changed flows; full-suite generation is opt-in. Playwright MCP is the default browser substrate (a11y-tree-first, token-efficient); Browser-Use is the escape hatch for exploratory/healing flows. Skyvern's AGPL-3.0 code is excluded; its architectural patterns are adopted. The quality gate for generated artifacts uses GenIA-E2ETest metric formulas: execution_recall >= 0.80, element_precision >= 0.70, manual_modification_rate <= 0.15 at initial release.

### L2: For Architects

Key design decisions encoded in this specification:

1. **Dual-mode execution** (P-E2E-05): codegen mode produces committed Playwright artifacts that run in CI without LLM in the loop; explorer mode keeps the LLM in the loop for adaptive/self-healing runs. The two modes are not interchangeable and are not conflated.

2. **Three-role agent triad** (P-E2E-04): the Skyvern-derived Planner→Actor→Validator pattern with Validator-escalates-to-Planner (not Executor-retries) is the core architectural decision. The WebVoyager causal evidence (45%→85.85% accuracy) justifies this as HARD.

3. **Diff-scoped entry** (P-E2E-03): the skill defaults to testing flows adjacent to changed code, preventing the "giant flaky suite nobody trusts" failure mode (Skyvern /qa pattern). Full-suite runs require explicit opt-in.

4. **Standards composure** (Sections 7, 9): WebDriver is a HARD protocol constraint; ISO 29119 artifacts are MEDIUM opt-in; ISTQB gTAA is the architecture reference; WSTG is the security taxonomy; Gherkin is the default scenario format. Standards are layered, not monolithically adopted.

5. **Eng-team integration stance** (Section 9): the skill is additive, not competing. Scope boundary is: eng-team owns unit/API-level/fuzz; /e2e-testing owns browser-driven real-user-journey tests. The eng-reviewer double-scoring seam is resolved by having /e2e-testing own its own quality gate internally at **0.94** (matching this workflow's Gate 2 target), feeding eng-reviewer at the engagement level rather than replacing it.

6. **Threshold posture** (Section 9): internal quality threshold is **0.94** — above the root SSOT H-13 (0.92) and below the eng-team-local strictest value (0.95). Rationale: the root SSOT is a floor, not a ceiling. The e2e-testing skill works on user-facing flows where correctness failures are immediately visible to users; 0.94 reflects that elevated risk. The full 0.95 eng-team standard is appropriate for security-specific deliverables that eng-reviewer scores; it is not the right default for an e2e test-generation skill at initial release.

7. **Validation orthogonality** (Section 6.5): the Jerry adversary quality score (S-014) and the functional correctness quality gate (execution_recall, element_precision) measure orthogonal concerns. Conflating them produces false confidence. The skill keeps them separate.

8. **Tension resolution summary**: ISO 29119 documentation weight is resolved by treating its artifact catalog as opt-in; Gherkin BDD conversation-first discipline is the default. Design-time code generation vs runtime in-loop LLM is resolved by making both modes first-class with explicit user-facing mode selection.

## 2. The 10 Distilled Principles

### P-E2E-01: Risk-First Test Ordering

**Statement:** Before any test scenario is authored, the skill MUST classify the scenario's risk (likelihood × impact using HIGH/MEDIUM/LOW) and map it to a Jerry criticality level (C1–C4), using that classification to drive test ordering and CI gate placement.

**Traceability:**
- SP-1 (lane-standards §6): "Design-Test-Strategy activity mandates explicit risk-based prioritisation as a first-class input" — sourced from ISO 29119-2 §3, ISTQB CTFL Ch. 5, and OWASP WSTG §1.
- eng-team baseline §7.4: "coordinate so fuzz/unit scope stays with eng-qa" — implies risk classification drives the routing decision between skills.
- eng-team baseline §4: eng-reviewer /adversary table already uses C1–C4; the e2e-testing skill must speak the same criticality language to feed the reviewer correctly.

**Rationale:** Risk-based prioritisation is the most consistent imperative across all three input sources. The standards lane documents its presence in four of five standards (ISO 29119-2, ISTQB, OWASP WSTG, Gherkin Example Mapping). The eng-team baseline shows the criticality model is already operational in Jerry (C1–C4 in adversary-integration.md). Aligning the e2e skill to this existing model avoids a parallel risk vocabulary.

**Testable assertion:** Every test case artifact generated by the skill MUST include a `risk_level` field (HIGH/MEDIUM/LOW) and a `criticality` field (C1–C4) in its frontmatter or metadata block. The skill MUST refuse to author test steps until both fields are populated.

**Tier:** HARD

### P-E2E-02: Declarative Gherkin Scenarios with Traceable Basis

**Statement:** All user-journey E2E test scenarios MUST be expressed in declarative Gherkin (Feature → Rule → Scenario, Given-When-Then) and MUST include a `@basis:` tag linking the scenario to its test basis (user story ID, WSTG test ID, risk item reference, or requirement ID).

**Traceability:**
- SP-2 (lane-standards §6): "declarative style mandate" (std-5 §7.2); "traceability to test basis" (std-2 §7 P7; std-4 §7.2; std-3 §3.1).
- INN-P-001 (lane-innovators §6): GenIA-E2ETest three-level pipeline produces structured scenario artifacts; the first level (Scenario Modularization) maps directly to Gherkin Feature/Rule decomposition.
- lane-standards §2 Theme 3: traceability is "universally expected across all five standards."

**Rationale:** Declarative style (no UI-verb tokens in `When` steps) prevents selector-coupling rot. The `@basis:` tag is the mechanical enforcement of the traceability requirement that four of five standards independently mandate. Together, these two requirements make test artifacts self-documenting and verifiable against requirements without reading source code.

**Testable assertion:** A linting rule MUST reject any `Scenario` whose `When` steps contain UI-verb tokens ("click", "type", "enter", "navigate to", "fill in", "select") and MUST reject any `Scenario` lacking a `@basis:` tag with a non-empty, parseable reference value.

**Tier:** HARD

### P-E2E-03: Diff-Scoped Entry with Explicit Opt-In for Full Coverage

**Statement:** The skill's default invocation MUST accept a `git diff` as its primary input and confine test generation to flows adjacent to changed code; comprehensive test-suite generation MUST require explicit user confirmation before proceeding.

**Traceability:**
- INN-P-005 (lane-innovators §6): Skyvern `/qa` and `/smoke-test` skills read git diff and test adjacent flows explicitly to prevent "the typical fate of end-to-end tests, which slowly turn into a giant flaky suite nobody trusts." [SKYVERN SELF-REPORTED metrics on 50% QA-loop reduction and 2.3x PR-success lift.]
- lane-innovators T-002: the design-time vs runtime tension is partially resolved when the entry point is scoped to the change surface rather than the entire application.
- eng-team baseline §6: zero synthetic or smoke-test coverage in eng-team; the diff-scoped model is the pattern most compatible with the existing CI/CD gate structure (eng-devsecops owns the gate; e2e-testing feeds it).

**Rationale:** Diff-scoped testing inverts the traditional failure mode (run everything → accumulate flakiness → suite loses credibility). It also minimises LLM inference cost by generating only tests motivated by actual code changes. Comprehensive generation is not prohibited — it is simply opt-in, preserving the user's ability to trigger full runs at release milestones.

**Testable assertion:** When invoked without explicit `--full-suite` flag, the skill MUST emit a test plan scoped only to flows reachable from the changed code identified in the provided diff. Running the skill with no diff input MUST prompt for one before proceeding, not silently default to full-suite.

**Tier:** HARD

### P-E2E-04: Planner–Executor–Verifier Triad with Supervisor-Loop Escalation

**Statement:** The skill MUST decompose into three distinct agent roles — `e2e-author` (Planner), `e2e-executor` (Actor), `e2e-verifier` (Validator) — where the Verifier escalates failures to the Author for replanning and MUST NOT delegate retry decisions to the Executor.

**Traceability:**
- INN-P-001 (lane-innovators §6): Skyvern 2.0 demonstrated 45%→68.7%→85.85% WebVoyager accuracy by adding distinct Planner then Validator roles (inn-4 §P-SKY-1/P-SKY-2). QA Wolf Verifier+Automation Agent (inn-1 §3.1) [VENDOR BLOG]. Playwright MCP Planner/Generator/Healer (inn-2 §7.4).
- CP-003 (lane-innovators §2): Validator-as-separate-role is the most consequential single design decision in the innovator set — the distinction between "embedded retry" (anti-pattern) and "supervisor-loop escalation" (pattern).
- eng-team baseline §4: eng-reviewer's escalation protocol (1st failure → revise + resubmit; 2nd → eng-lead; 3rd → eng-architect) is the same supervisor-loop pattern at a different abstraction level. The parallel is intentional.

**Rationale:** Causal evidence from Skyvern (the 40-percentage-point accuracy lift attributed specifically to adding a separate Validator) is the strongest empirical evidence in any input source for any single design decision. Matching Jerry's existing H-14 creator-critic-revision pattern also reduces framework cognitive overhead. The Executor-retries anti-pattern produces cascading failures; the Validator-escalates-to-Planner pattern produces structured replanning with diagnostic context.

**Testable assertion:** An A/B test of an Executor-only pipeline vs the full Planner–Executor–Verifier triad on a fixed 20-scenario suite MUST produce a meaningfully higher first-pass success rate for the triad. No Executor agent definition file may contain verification logic or retry-loop code; the `e2e-verifier` agent definition MUST document its escalation path to `e2e-author` explicitly.

**Tier:** HARD

### P-E2E-05: Dual Execution Mode — Codegen for Regression, Explorer for Healing

**Statement:** The skill MUST support two named execution modes: **codegen mode** (agent produces a committed Playwright `.spec.ts` file; CI runs it without LLM in the loop) and **explorer mode** (LLM stays in the loop during execution with assertion tools as first-class actions). The skill MUST declare the mode to the user and MUST NOT default to explorer mode for regression-critical flows.

**Traceability:**
- INN-P-003 (lane-innovators §6): CP-004 identifies design-time code generation vs runtime in-loop LLM as "the deepest architectural fault line in this lane." QA Wolf and GenIA-E2ETest produce durable artifacts (inn-1 §3.5 [VENDOR BLOG]; inn-5 §2.3). Browser-Use argues for in-loop (inn-3 §7.8). Playwright MCP supports both.
- lane-innovators T-002: the tension is acknowledged as unresolvable by a single choice; the resolution is to make both modes first-class and name them explicitly.
- eng-team baseline §7.2 (AD-010 three-level degradation): eng-team already provides a precedent for explicit mode-declaration: Level 0 runs live, Level 2 emits templates only. The dual-mode pattern is consistent with this philosophy.

**Rationale:** Forcing one model for all contexts degrades performance: codegen is brittle to UI drift; in-loop LLM is expensive for stable regression suites. The dual-mode design preserves both. Critically, it prevents silent mode confusion where a user believes they have a deterministic regression script but the CI run actually invokes an LLM at every step.

**Testable assertion:** The skill's invocation interface MUST display the current mode (codegen/explorer) before test execution begins. In codegen mode, the generated `.spec.ts` file MUST run successfully via `npx playwright test` without any LLM calls present in the test code. In explorer mode, the system prompt MUST register assertion tools explicitly before execution.

**Tier:** HARD

### P-E2E-06: Live-DOM-Grounded Locator Generation

**Statement:** Before any LLM step that generates UI selectors, element references, or action targets, the skill MUST take a live DOM or accessibility-tree snapshot and pass it to the LLM. The LLM MUST NOT invent selectors from natural-language prose alone.

**Traceability:**
- INN-P-002 (lane-innovators §6): CP-007 is the highest-confidence pattern in the innovator lane (5/5 sources with different implementations). GenIA-E2ETest Level 2 crawls live HTML specifically to prevent hallucinated selectors (inn-5 §7.3). Playwright MCP element-ref model grounds actions in live `browser_snapshot` output (inn-2 §7.3). Browser-Use `ClickableElementDetector` produces `selector_map` from live DOM (inn-3 §7.1). The WebApp1-TC5 failure (12% element precision) is explicitly attributed to insufficient DOM grounding (inn-5 §7.3).
- SP-5 (lane-standards §6): W3C WebDriver error taxonomy (`stale element reference`) is the standards-side articulation of the same failure mode.
- lane-standards Gap 2: "self-healing selectors" are identified as a gap in the standards lane that the innovator lane must fill. INN-P-002 is that fill.

**Rationale:** Hallucinated selectors are the primary failure mode for LLM-generated E2E tests — confirmed by five independent innovators and a peer-reviewed outlier case. The defense is mechanically simple (take a snapshot before generating) but must be architecturally mandated, not left to prompt discipline.

**Testable assertion:** The e2e-executor agent MUST invoke `browser_snapshot` (or equivalent DOM-traversal tool) before generating any locator. A test of the skill against a page with non-obvious element IDs MUST produce element_precision >= 0.70 on a 10-scenario corpus, consistent with the GenIA-E2ETest baseline [SINGLE-STUDY].

**Tier:** HARD

### P-E2E-07: gTAA-Conformant Layer Architecture

**Statement:** The skill's automation framework MUST map its components to the four gTAA layers (Generation, Definition, Execution, Adaptation), with at minimum Execution and Adaptation layers present. The Adaptation layer MUST be the exclusive integration point with the browser driver; Definition and Generation layers MUST NOT import directly from driver APIs.

**Traceability:**
- SP-3 (lane-standards §6): gTAA four-layer model (std-3 §7.1), W3C WebDriver protocol-layer isolation (std-1 §7 P-WD-1), hexagonal BDD driver-port separation (std-5 §7.4) — three independent standards converge on the same constraint.
- CP-006 (lane-innovators §2): multi-level prompting with structured JSON intermediates — where each agent sub-step consumes a structured input and emits a structured output — is the innovator-side expression of the same layering principle (4/5 sources).
- eng-team baseline §7.1 (agent skeleton): the eng-team's What-You-Do / What-You-Do-NOT-Do boundary assertion pattern is an agent-level expression of layer separation. The same discipline applies to framework layers.

**Rationale:** Separation of specification, execution, and driver interface is an independently derived consensus across both the standards lane (4/5 standards) and the innovator lane (4/5 innovators). The import-graph constraint (analogous to Jerry's H-07/H-08 architecture rules) is the testable enforcement mechanism.

**Testable assertion:** The skill's framework template generates separate source directories for each gTAA layer. An import graph check (linting or AST analysis) MUST flag any import from a browser-driver API (Playwright, WebDriver, CDP) in any file outside the Adaptation layer directory. All intermediate artifacts between agents MUST be persisted to disk (JSON or Markdown), not passed only as in-memory objects, per P-002 compliance and replay support.

**Tier:** HARD (promoted from SP-3's MEDIUM treatment because gTAA layer isolation is architecturally non-negotiable for this skill: the import-graph constraint is the testable enforcement mechanism that prevents selector-coupling rot from propagating across layers, analogous to Jerry's own H-07/H-08 architecture rules; an override requires a documented alternative that achieves equivalent separation and is subject to C3 auto-escalation per AE-003)

### P-E2E-08: Security Scenario Coverage via WSTG Taxonomy

**Statement:** For any web-service E2E test suite, the skill MUST generate or recommend at minimum one security scenario tagged with each of the WSTG v4.2 categories ATHN, ATHZ, SESS, INPV, BUSL, and APIT, using version-pinned identifiers (`@wstg:WSTG-v42-<CAT>-<NN>`) as the canonical tag in scenario files and test reports.

**Traceability:**
- SP-4 (lane-standards §6): std-4 §1 (12-category taxonomy), std-4 §3 (BUSL as highest-applicability category for agentic execution), std-4 §7.1 (version-pinned ID format).
- lane-innovators §4a Gap 5: "all five innovators are functionally oriented; security-testing remains out of scope for the innovators lane." The absence is uniform and explicit. SP-4 is therefore the sole authoritative source for security scenario generation — this is an eng-team-gap-exclusive principle drawing on the standards lane.
- eng-team baseline §6 Gap 1: "overlap risk: e2e-testing that performs security-relevant flows could duplicate eng-qa's threat-driven test derivation." The WSTG-tagging scheme resolves this by making security scope explicit and attributable, enabling eng-qa to see which security concerns are covered at the E2E layer.

**Rationale:** Without an explicit security coverage mandate, E2E test suites default to happy-path functional flows and leave the entire security surface to eng-qa's lower-level tests. WSTG-tagged scenarios operate at the user-journey layer (e.g., "As an authenticated user, I CANNOT access another user's data by manipulating the URL") — scenarios eng-qa's unit-level fuzz tests cannot express. The BUSL category is uniquely suited to agentic execution and must be first-tier.

**Testable assertion:** The skill's completeness check MUST verify the generated test suite contains at least one `@wstg:WSTG-v42-<CAT>-<NN>` tag for each of the six mandatory categories. A CI gate MUST report per-category WSTG coverage as a distinct metric column in the test summary.

**Tier:** HARD

### P-E2E-09: Published Quality Gate with Exact Metric Formulas

**Statement:** The skill MUST ship with a documented quality gate for generated test artifacts using the GenIA-E2ETest metric framework: execution_recall >= 0.80, element_precision >= 0.70, manual_modification_rate <= 0.15 at initial release. The metric formulas (C/G, C/E, CS/GS, CS/ES) MUST be documented in the skill's SSOT. All quality claims MUST cite the evaluation corpus they are computed against.

**Traceability:**
- INN-P-004 (lane-innovators §6): GenIA-E2ETest §7.1 provides exact formulas; inn-4 §P-SKY-4 "any claimed quality metric must be accompanied by a publishable per-task trace"; inn-1 §P5 [VENDOR CLAIM] "coverage claim MUST cite methodology and corpus."
- lane-standards Gap 3: "ISO 29119-4 defines coverage measures for human-authored tests; there is no equivalent for generated tests." The standards lane identifies this as a gap that the innovator lane (GenIA-E2ETest) fills.
- eng-team baseline §4: eng-reviewer uses S-014 six-dimension rubric; the GenIA-E2ETest metrics are a functional-correctness gate that is orthogonal to S-014 — they coexist, not compete. (See Section 6.5.)

**Rationale:** Without a published quality gate with exact formulas, any quality claim about generated test artifacts is unauditable. GenIA-E2ETest is the only peer-reviewed source with exact metric formulas and a reproducible experimental protocol [SINGLE-STUDY — LIMITED STATISTICAL POWER on n=12]. The stated thresholds (0.80/0.70/0.15) are first-release conservative targets; they are explicitly intended to be tightened as Jerry's own eval corpus matures beyond the single-study baseline.

**Testable assertion:** At skill release, execution_recall, element_precision, and manual_modification_rate MUST be computed against a named eval corpus of >= 20 test scenarios (chosen to exceed GenIA-E2ETest's n=12). The three values MUST be persisted as a WORKTRACKER artifact and updated with each skill version bump. A skill release MUST be blocked if any metric falls below the stated threshold on the named corpus.

**Tier:** HARD

### P-E2E-10: Explicit Autonomy-Tier Declaration

**Statement:** Every test run initiated by the skill MUST declare its autonomy tier — AUTONOMOUS (agent acts without human review of individual steps), SUPERVISED (human reviews each generated test before execution), or MANAGED-EQUIVALENT (human engineers backstop AI failures post-run) — and the skill MUST NOT promise outcomes associated with a higher autonomy tier than declared.

**Traceability:**
- lane-innovators T-001 and inn-1 §P8 [VENDOR BLOG]: QA Wolf's reliability advantage derives from human engineers backstopping AI failures — the managed-service model. An open-source skill that implicitly promises QA Wolf-level outcomes without this backstop violates P-022 (no deception about capabilities).
- lane-innovators §5 (QA Wolf posture): "Jerry must explicitly declare its autonomy tier... The skill cannot implicitly promise QA Wolf-level outcomes without QA Wolf-level human supervision."
- eng-team baseline §4: eng-reviewer's escalation protocol (user notification per P-020 on persistent failure) is the existing safety valve for autonomous agent failures. The autonomy-tier declaration gives the user the information needed to calibrate their reliance on that safety valve.

**Rationale:** This principle is a P-022 (no deception) enforcement mechanism specific to the e2e-testing context. Test quality claims that do not disclose the autonomy tier under which they were produced are implicitly deceptive about the level of human oversight involved. A skill that can be invoked at AUTONOMOUS tier must be honest that its quality gate is its only backstop. This is a first-class skill invariant, not a UI footnote.

**Testable assertion:** The skill's L0 output for every test run MUST include an `autonomy_tier: AUTONOMOUS | SUPERVISED | MANAGED-EQUIVALENT` field and a one-sentence description of what that tier means for this run. If the skill cannot determine autonomy tier from context, it MUST ask before proceeding.

**Tier:** HARD

## 3. Resolved Tensions

### RT-001: ISO 29119 Documentation Weight vs BDD Conversation-First Philosophy

**Contributing sources:** lane-standards §3 Tension 1 (ISO 29119 Part 3 eight-document set vs Gherkin/BDD "conversations first" philosophy; Stop 29119 community critique); lane-standards §3 Tension 5 (ISO 29119 institutional authority vs community rejection).

**Tradeoff space:**
- Adopting ISO 29119 fully: gains regulatory/procurement legibility in enterprise contexts; loses practitioner credibility in context-driven teams; adds significant documentation overhead per test run.
- Adopting BDD/Gherkin exclusively: gains practitioner credibility, speed, and alignment with Jerry's "filesystem as infinite memory" philosophy; loses formal traceability language recognized in regulated procurement.

**Resolution:** The skill's default operation follows Gherkin + risk-based prioritisation (which both camps accept) and generates ISO 29119-compatible artifacts on demand via an explicit `--iso29119` flag or R-011-style config parameter. The Gherkin feature file itself serves as the test case specification in 29119-3 terms (satisfying Part 3 intent without a separate document). ISO 29119-1 vocabulary (test basis, test condition, test coverage item, entry/exit criteria) is used throughout the skill's outputs as a shared language layer. ISO 29119-3's full eight-document set is opt-in for regulated/enterprise contexts only.

**Justification:** The Gherkin-as-test-case-spec equivalence is already established in lane-standards §5 (selective alignment). The dual benefit — BDD-first operationally, ISO-compatible on demand — avoids forcing practitioners to choose. The skill's primary users are engineers who value speed and clarity; regulated procurers are a secondary audience served by the opt-in flag.

---

### RT-002: Design-Time Code Generation vs Runtime In-Loop LLM

**Contributing sources:** lane-innovators §3 T-002 (the "deepest architectural fault line in this lane"); CP-004 (medium agreement — QA Wolf/GenIA-E2ETest for codegen, Browser-Use for in-loop, Playwright MCP for both, Skyvern partial); INN-P-003.

**Tradeoff space:**
- Codegen-only: deterministic, reviewable, versionable, cheap to run in CI; brittle to UI drift; requires re-generation after every significant DOM change.
- In-loop-only: adaptive, self-correcting, handles dynamic SPAs; expensive (LLM inference per CI run at potentially ~20k tokens/min/agent); non-deterministic; harder to debug; raises P-003 recursive-agent concerns at scale.

**Resolution:** Both modes are first-class (P-E2E-05). The mode is selected by the user at invocation time and declared in L0 output. Codegen mode is the default for regression-critical flows (criticality C2+) because the cost and determinism properties make it preferable for reliable CI. Explorer mode is the default for exploratory runs and self-healing contexts where DOM drift has broken codegen artifacts. The Healer sub-pattern (Playwright MCP) is a third hybrid: codegen artifacts are healed by an in-loop LLM agent that patches the artifact, not the production run — this is an implementation detail of codegen mode, not a separate mode.

**Justification:** No single mode is universally superior across all contexts. Forcing one mode trades correctness for simplicity in the wrong direction. The dual-mode design mirrors engineering reality: stable, known-good flows deserve deterministic regression; exploratory and evolving flows need adaptive agents. CDP fast-path optimizations (Signal 4 from lane-innovators §4) make in-loop LLM more tractable in CI than previously assumed, but they do not eliminate the cost differential — they reduce it.

### RT-003: Accessibility-Tree-First vs Vision-LLM-First as Actor Substrate

**Contributing sources:** lane-innovators §3 T-003 (Playwright MCP a11y-tree vs Skyvern vision-LLM); inn-4 §P-SKY-7.

**Tradeoff space:**
- A11y-tree-first (Playwright MCP): 2–5 KB per snapshot vs 500 KB+ for screenshots; 10–100x token reduction; suitable for modern, semantically structured apps; fails on canvas-heavy or accessibility-hostile legacy apps.
- Vision-LLM-first (Skyvern): handles apps with weak a11y trees; incurs 4–5 minute latencies on simple flows; high per-step LLM cost.

**Resolution:** The skill defaults to Playwright MCP (a11y-tree-first) for all standard runs. Vision-LLM-based execution is an explicitly declared fallback mode, triggered by user configuration when the SUT is identified as a11y-hostile. The SUT's accessibility profile is a Phase 3 design-time configuration question (see Section 10, OQ-E2E-004).

**Justification:** Token efficiency and latency favor a11y-tree for the majority of modern web applications. The vision fallback preserves coverage of legacy or canvas-heavy targets without imposing its cost on all runs.

### RT-004: Eng-Team 0.95 Threshold vs Root SSOT 0.92 Threshold

**Contributing sources:** eng-team baseline §4 (eng-reviewer uses 0.95 for C2+); quality-enforcement.md H-13 (0.92 SSOT floor); eng-team baseline §4 (explicit note: "e2e-testing should decide whether to mirror 0.95 or inherit the looser 0.92").

**Tradeoff space:**
- Adopting 0.95: higher bar, consistent with eng-team's security-focused stringency; may be too strict for a test-generation skill where some low-confidence scenarios are expected at initial release.
- Adopting 0.92: consistent with root SSOT; lower bar justified for a new skill still building its eval corpus; risks under-enforcement for user-facing quality.

**Resolution:** The skill adopts **0.94** as its internal quality gate threshold. This value is triangulated from three independent anchors: (1) the Jerry SSOT H-13 floor of 0.92 (the absolute baseline any Jerry skill must meet), (2) the eng-team-local maximum of 0.95 (calibrated for security-specific deliverables where failures have regulated-compliance consequences), and (3) a midpoint of 0.935 rounded up to 0.94 to provide headroom above the SSOT floor while remaining achievable for a general-purpose E2E test-generation skill that is less security-critical than eng-team's core domain. Explicitly: **Gate 2's 0.94 target is a downstream consumer of this triangulation, not its source.** The triangulation was established in this specification first; the workflow's Gate 2 target was then set to match it to avoid a mismatch between the skill's internal bar and the workflow's meta-quality bar. The full 0.95 threshold applies when the skill's output is scored by eng-reviewer as part of a security-scoped engagement — that is eng-reviewer's domain, not e2e-testing's internal gate.

**Justification:** A threshold must be defensible on two grounds: higher than the floor (because the user-facing context warrants it) and lower than the strictest constraint (because an initial-release test-generation skill operating on [SINGLE-STUDY — LIMITED STATISTICAL POWER] baselines is a different risk context than a security-specific eng-reviewer deliverable). 0.94 satisfies both. The 0.94 value is a triangulation, not an independently evidenced empirically optimal threshold; it will be revised as the skill's eval corpus provides a data-driven signal beyond the GenIA-E2ETest single-study baseline.

## 6. Validation Strategy

### 6.1 Definition: "Test Ran" vs "Test Verified Application Correctness"

A test has **run** when it executes to completion without a test-runner error (exit code 0, no uncaught exceptions, no timeout). A test has **verified application correctness** when at least one of its assertions is constructed such that:

1. The assertion would **fail** if the application were in the wrong state (i.e., it is sensitive to the defect it is meant to catch), AND
2. The assertion **targets a semantic application concern** (business rule, security property, user-observable behaviour), not a technical execution artifact (e.g., the assertion is not merely that an HTTP 200 was returned when it should also verify the response body reflects the intended state).

A test that asserts `expect(page.url()).toBe('/dashboard')` after login has run and detected navigation, but has not verified that the correct user's data is displayed on the dashboard. A test that additionally asserts `expect(page.getByText(`Welcome, ${username}`)).toBeVisible()` has moved toward verification. A test that additionally asserts that another user's data is NOT visible has completed the security verification. This three-level escalation (navigation → identity → isolation) is the operational model for "verified" vs "ran."

**The e2e-verifier MUST classify each `Then` assertion as:**
- `VERIFIED` — sensitive to the defect class it targets
- `RAN-ONLY` — present but insensitive (would pass even if the application were in the wrong state for that defect class)
- `ABSENT` — no assertion present for this scenario's stated purpose

A test with any `ABSENT` or majority `RAN-ONLY` assertions MUST be escalated to `e2e-author` for revision before the run is recorded as verified.

---

### 6.2 Coverage Dimensions

| Dimension | Definition | Priority |
|-----------|------------|----------|
| **Happy path** | The expected nominal flow succeeds: user completes the intended action, system returns expected state. | First-tier — all flows must have at least one happy-path scenario. |
| **Failure path** | The application handles expected errors gracefully: invalid input rejected with correct error message, network failure surfaced to user, auth failure redirects correctly. | First-tier — each failure type defined in the test basis must have a scenario. |
| **Boundary** | The application behaves correctly at input limits: empty values, maximum-length strings, negative numbers, special characters, concurrent access patterns. | Second-tier — apply to flows where boundary violations cause security or correctness risk. |
| **Security** | The application enforces its security properties: authenticated user cannot access another user's data, WSTG-tagged scenarios test auth/authz/session/input/logic/API surfaces. | First-tier for any flow involving authentication or sensitive data, per P-E2E-08. |
| **Agentic divergence** | For flows where the SUT is itself an LLM agent: the test asserts over the agent's trajectory, not just its final state — including what tool calls it made, what it declined to do, and whether it respected its own declared constraints. | First-tier for any flow testing an AI-powered feature; the standards lane provides no normative model for this (Gap 1) — this is a Jerry supplement. |

---

### 6.3 Validation Check Mechanism

The `e2e-verifier` agent follows this procedure for each generated test:

**Step 1: Assertion Inventory**
Extract all `Then` assertions from the Gherkin scenario and their corresponding Playwright `expect()` calls from the `.spec.ts` file (codegen mode) or from the execution trace (explorer mode). Map each assertion to its stated verification purpose from the `@basis:` tag and scenario description.

**Step 2: Sensitivity Check**
For each assertion, determine its sensitivity class:
- Does it distinguish between a passing and failing application state for the specific defect it targets?
- Would it pass even if the targeted defect were present in the application?

Decision criteria:
- If the assertion checks only navigation (URL change) without state content verification → `RAN-ONLY`
- If the assertion checks element visibility without checking element content → `RAN-ONLY` for content-dependent concerns, `VERIFIED` for existence concerns
- If the assertion checks both visibility and content/text-match → `VERIFIED`
- If the assertion verifies the ABSENCE of sensitive data (e.g., `expect(page.getByText(otherUserEmail)).not.toBeVisible()`) → `VERIFIED` for isolation concerns
- If no assertion is present for the scenario's stated purpose → `ABSENT`

**Step 3: Coverage Dimension Check**
Verify that the test suite (not just this scenario) covers all five dimensions defined in 6.2 for the feature under test. Flag gaps.

**Step 4: Metric Computation**
Using GenIA-E2ETest formulas [SINGLE-STUDY]:
- `element_precision` = C / G, where C = correctly generated locators accepted without modification, G = total generated locators
- `element_recall` = C / E, where E = expected locators needed for the scenario
- `execution_precision` = CS / GS, where CS = generated steps that ran without error, GS = total generated steps
- `execution_recall` = CS / ES, where ES = expected steps for correct execution

Compute `manual_modification_rate` as the fraction of generated steps requiring human modification before the test passed.

**Step 5: Verdict**
- PASS: execution_recall >= 0.80, element_precision >= 0.70, MMR <= 0.15, no `ABSENT` assertions, fewer than 30% `RAN-ONLY` assertions
- REVISE: any metric between threshold and (threshold - 0.05), or 30–50% `RAN-ONLY` assertions → escalate to `e2e-author` with targeted revision request
- FAIL: any metric below (threshold - 0.05) or >50% `RAN-ONLY` assertions, or any `ABSENT` → escalate to `e2e-author` with full diagnostic

**Example output (FAIL case):**
```json
{
  "verdict": "FAIL",
  "scenario": "User cannot view another user's profile data",
  "assertion_inventory": [
    {"step": "Then I should not see alice@example.com", "class": "VERIFIED"},
    {"step": "Then the page loads successfully", "class": "RAN-ONLY"}
  ],
  "metrics": {
    "element_precision": 0.62,
    "execution_recall": 0.75,
    "MMR": 0.20
  },
  "failure_category": "data — assertions present but element_precision below threshold due to hallucinated email locator",
  "webdriver_error_class": "no such element",
  "escalation_to": "e2e-author",
  "replan_recommendation": "Add live DOM snapshot before email locator generation; add explicit negative assertion on alice's email with data-testid anchor rather than text match."
}
```

### 6.4 Metrics

The following numeric thresholds govern the skill's quality gate for generated test artifacts. All values are derived from GenIA-E2ETest [SINGLE-STUDY — LIMITED STATISTICAL POWER, n=12] and treated as directional reference points until Jerry's own eval corpus (>= 20 scenarios) supersedes them.

| Metric | Initial Release Threshold | Maturity Target | Formula |
|--------|--------------------------|-----------------|---------|
| execution_recall | >= 0.80 | >= 0.85 | CS / ES |
| element_precision | >= 0.70 | >= 0.77 | C / G |
| element_recall | >= 0.70 | >= 0.77 | C / E |
| manual_modification_rate | <= 0.15 | <= 0.10 | MMR fraction |
| WSTG category coverage | 6/6 mandatory | 6/6 + CRYP, CLNT | count of tagged categories |
| Assertion sensitivity | <30% RAN-ONLY | <20% RAN-ONLY | fraction of assertions |

**Calibration note:** The initial thresholds are conservative relative to the GenIA-E2ETest reported values (77% element precision, 85% execution recall) to account for the limited statistical power of the single-study baseline [SINGLE-STUDY]. As Jerry's own eval corpus grows, these thresholds should be tightened on evidence, not convention.

### 6.5 Relationship to Jerry SSOT Quality Gate

The Jerry SSOT quality gate (S-014 six-dimension rubric, threshold 0.94 for this skill) and the functional correctness quality gate (Section 6.4 metrics) measure **orthogonal concerns** and MUST be kept separate.

| Concern | Measured by | Scored against | Owner |
|---------|-------------|----------------|-------|
| **Process quality** — did the skill follow its methodology? Are artifacts complete, consistent, well-traced, actionable? | S-014 LLM-as-Judge (Completeness 0.20, Internal Consistency 0.20, Methodological Rigor 0.20, Evidence Quality 0.15, Actionability 0.15, Traceability 0.10) | 0.94 threshold (this skill's gate) | e2e-verifier (S-014 step); eng-reviewer (engagement-level) |
| **Functional correctness** — do the generated tests actually verify application behaviour? | execution_recall, element_precision, MMR (Section 6.4) | Thresholds in 6.4 | e2e-verifier (validation check mechanism) |

A test suite can score 0.96 on S-014 (well-documented, traceable, methodologically rigorous) and simultaneously score 0.65 execution_recall (the tests rarely pass because the locators are fragile). Conversely, a suite can have 0.95 execution_recall (tests run reliably) but score 0.88 on S-014 (no `@basis:` tags, missing WSTG coverage, poor documentation). Both failures are real and must be reported separately, not averaged together.

The `e2e-verifier` MUST emit both scores as distinct fields in its output. Neither score substitutes for the other in a pass/fail determination.

### Overlap Seams and Routing

**Seam 1: Security Scope (eng-qa ↔ e2e-testing)**
Routing rule: eng-qa owns threat-model-derived unit and API-level security tests (input validation fuzz, property-based invariants, SSDF PW.8). /e2e-testing owns WSTG-tagged user-journey security scenarios (auth-bypass through browser, business-logic abuse at the UI layer, session fixation via browser flow). The `@wstg:` tag on e2e-testing scenarios and the `@owasp-tg:` tag on eng-qa scenarios make the attribution explicit and non-overlapping.

**Seam 2: Quality Scoring (eng-reviewer ↔ e2e-verifier)**
Routing rule: `e2e-verifier` owns the internal functional correctness gate (execution_recall, element_precision, MMR — Section 6.4) and the skill-internal S-014 quality score (threshold 0.94). `eng-reviewer` owns the engagement-level quality gate (threshold 0.95 for security-focused engagements) when /e2e-testing output is reviewed as part of a full eng-team engagement. These are sequential gates, not competing ones: e2e-testing must pass its own gate (0.94) before its artifacts are eligible for eng-reviewer scoring. A deliverable MUST NOT be submitted to eng-reviewer at a score below 0.94.

**Seam 3: CI/CD Wiring (eng-devsecops ↔ e2e-testing)**
Routing rule: /e2e-testing produces WSTG-tagged test artifacts, quality metric reports, and per-category coverage reports. eng-devsecops owns the CI/CD gate configuration that determines whether those artifacts gate a deployment. The two skills do not re-implement each other's gates — they compose. The e2e-testing skill's `e2e-governance-config.md` declares the quality thresholds; eng-devsecops wires those thresholds into the pipeline gate.

### Threshold Choice: 0.94

The /e2e-testing skill's internal quality gate is **0.94**.

**Against root SSOT (0.92):** The SSOT H-13 is a floor, not a ceiling. e2e-testing generates artifacts that are directly executed against production-adjacent environments and whose failures are visible to end users. A floor threshold for a new skill generating user-facing test artifacts is insufficient; 0.94 is the minimum credible elevation.

**Against eng-team-local (0.95):** The 0.95 threshold is calibrated for security-specific deliverables (eng-reviewer scores security engagements). A test-generation skill at initial release, operating with a GenIA-E2ETest baseline that has [SINGLE-STUDY — LIMITED STATISTICAL POWER] statistical backing, should not commit to 0.95 until its eval corpus grows to a size that justifies the claim. 0.95 remains the correct threshold when eng-reviewer scores /e2e-testing artifacts as part of a security-focused engagement — that is eng-reviewer's domain.

**Triangulation disclosure:** The 0.94 value is triangulated between three independent anchors — SSOT floor 0.92, eng-team-local maximum 0.95, and the midpoint 0.935 rounded up to 0.94 — and is not independently evidenced as the empirically optimal threshold for test-generation skill quality. It will be revised as the skill's eval corpus provides a data-driven signal. Gate 2 of this workflow uses 0.94 as its target because it was set to match this specification's triangulated threshold; the gate target is a downstream consumer of this justification, not its source.

### OQ-E2E-001: Agentic-Flow Gherkin Extension Syntax

**Question:** What exact Gherkin extension syntax should Jerry use for scenarios where the actor is an LLM agent? The standards lane provides no normative model (Gap 1). A candidate is `When an agentic actor invoked as [skill-name] processes [input]`, but the syntax for trajectory assertions (`Then the agent SHOULD have called tool X before calling tool Y`) is unresolved.

**Why design-phase:** This requires a concrete syntax decision that will define the format of all agentic-flow test artifacts. It affects the linting rules (P-E2E-02), the `e2e-agentic-flow.md` template, and the `e2e-verifier`'s trajectory-assertion logic. It is a design decision, not a synthesis decision.

**Resolution format expected:** Prose specification of the extension keywords and grammar, with 3–5 worked examples covering the agentic divergence coverage dimension (Section 6.2).
