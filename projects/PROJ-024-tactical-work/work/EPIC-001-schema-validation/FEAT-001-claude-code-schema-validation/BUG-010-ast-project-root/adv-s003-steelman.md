## Steelman Reconstruction

### 1. Deep Understanding — Core Thesis (Step 1)

The most charitable, and most accurate, reading of this change is **not** "loosen a security check because a user asked for convenience." It is: **the original single-root containment model conflated two independent needs — "resolve the right ambient project boundary automatically" and "let the user or an integrating tool declare an exact boundary explicitly" — and the widening splits those into two clean, independently-testable modes.** Everything else in the design (temp/scratchpad roots, the ownership gate, the transparency notes) is a consequence of getting that split right, not an ad hoc pile of exceptions.

### 2. Design Principle: Two Orthogonal Modes (SM-001 — filling an unstated organizing principle)

The codebase implements, but does not explicitly *name*, two containment modes:

| Mode | Trigger | Allowed set | Who decides | Intended consumer |
|------|---------|-------------|-------------|-------------------|
| **Ambient smart-default** | No `--root` supplied | `{project root, tempfile.gettempdir(), /tmp if it exists}` — additive, de-duplicated (`get_containment_roots`, `project_root.py:120-177`) | The tool infers a reasonable boundary from `CLAUDE_PROJECT_DIR`/cwd plus known OS scratch locations | Interactive/agent use (a human or an LLM agent working inside one project, possibly staging via a scratchpad) |
| **Explicit hermetic override** | `--root <path>` supplied | Exactly `{resolved(--root)}` — exclusive, non-additive (`project_root.py:159-169`) | The invoking user or script decides, in full | Scripted/CI/programmatic use, or any case where ambient inference (env var, cwd) is wrong, absent, or untrustworthy |

This is a defensible two-mode design, not a single fuzzy default trying to do both jobs at once. The exclusivity of `--root` (proven in code: `if explicit_root is not None: return [resolved_root]` — no fallthrough to the project-root/temp defaults) is the load-bearing property: it means declaring `--root` doesn't just *add* a location, it *replaces the entire inference layer* with a single deterministic value. That is exactly the semantic a CI job or a wrapper tool needs: given the same `--root`, the same file, and the same filesystem state, the containment decision is 100% reproducible and independent of ambient environment variables or working directory — a property the pre-widening single-root design also had, but which a naively *additive* `--root` (root ∪ project-root ∪ temp) would have silently broken.

**Evidence:** `_check_path_containment` (`ast_commands.py:290-367`) calls `get_containment_roots(explicit_root)` once and treats the result opaquely as "the allowed set" for that invocation — the read path, the symlink check, and the `ast_modify` write-time TOCTOU recheck (`ast_commands.py:677-682`) all consume the *same* function with the *same* `explicit_root` argument, so the exclusivity guarantee is enforced identically at every containment check site, not just the entry point. eng-lead's plan explicitly called this out as a designed invariant (implementation plan, "Threading required" item 3, and the dedicated regression test `test_ast_modify_when_root_given_and_write_target_outside_root_then_rejected_at_write_time`).

### 3. Evidence for Default-Widening Correctness (SM-002 — strengthening the "why temp roots" claim with the failure mode it prevents)

The steelman's strongest form of "why widen the default set at all" is not "because the owner asked" — the owner's directive is *sufficient* authorization, but the *design justification* is that the pre-widening single-root default produced a **genuine false-negative failure class that BUG-010 itself was filed to eliminate**: a legitimate, Jerry-generated artifact (a Claude Code agent's own scratchpad output) would be silently rejected as "escaping the repository root," even though the file was produced *by the same session's own agent workflow* moments earlier. Without the temp/scratchpad roots, fixing BUG-010's headline bug (wrong root anchor) would have solved the "plugin install dir vs. user project dir" problem while leaving an adjacent, equally real false-negative untouched: "project dir vs. this session's own scratchpad dir." Both are the *same class of bug* — the containment boundary not matching the actual, legitimate operating envelope of the tool — and the widening closes both with the same mechanism (`get_containment_roots`), rather than requiring two separate fixes at two separate times.

**Evidence for the platform-specific necessity of registering *two* temp roots, not one:** the design doesn't merely add "a temp directory" — it adds `tempfile.gettempdir()` **and** `/tmp` (existence-gated) because, on macOS, these are genuinely different filesystem trees (`$TMPDIR` under `/var/folders/...` vs. Claude Code's scratchpad under `/tmp/claude-*`, canonically `/private/tmp/...`). A single-temp-root design would have "fixed" the false negative on Linux (where they usually coincide) while leaving it silently broken on macOS — the exact platform Jerry is developed and used on per this repository's own environment metadata. Registering both, rather than hard-coding a Claude-Code-specific path string, is the more general and more defensible fix: it works for *any* tool that stages files via the stdlib's own `tempfile` module or writes directly to `/tmp`, not only Claude Code's specific scratchpad convention.

### 4. The Standalone Pip Package Future — Reconstructed Forward-Compatibility Case (SM-003 — filling the requested lens explicitly; the source artifacts do not state this rationale directly, so this section is an inference from the code's actual shape, labeled as such per academic honesty)

None of the four touched files, the BUG-010 entity, the eng-lead plan, or the red-vuln findings state "this design is chosen because Jerry may ship as a standalone pip package" as an explicit rationale. That is a genuine gap in the stated argument (see SM-004 below). However, the strongest version of the case *can* be constructed directly from the code's actual properties, and it holds up:

1. **`get_project_root()` has no Claude-Code-specific hard dependency.** Its resolution order — `CLAUDE_PROJECT_DIR` env var, else `Path.cwd()` (`project_root.py:46-60`) — degrades gracefully to "the directory you ran the command from" the instant the env var is absent, which is precisely the correct, unsurprising default for *any* standalone CLI tool invoked from a shell, not a Claude-Code-plugin-specific behavior with no fallback. A `pip install jerry-cli && cd my-project && jerry ast validate PLAN.md` invocation, with zero Claude Code involvement, resolves correctly today, with no code change, because `CLAUDE_PROJECT_DIR` is simply unset and the cwd fallback fires — the same code path that fixes the plugin-deployment bug is already the correct standalone-package behavior.
2. **The temp/scratchpad roots are OS-generic, not Claude-Code-branded.** There is no hard-coded `/tmp/claude-*` string anywhere in `project_root.py` — the constants are `tempfile.gettempdir()` (stdlib, platform-correct on Windows/macOS/Linux by construction) and a bare `/tmp` existence check. This means the same widened-defaults logic transparently serves *any* future caller that stages files via the OS temp directory before or after invoking `jerry ast` — a CI runner, a pre-commit hook, a doc-generation pipeline, or a completely different agent framework — not only Claude Code's specific convention. Solving the concrete Claude Code scratchpad problem produced a more general, reusable mechanism rather than a narrowly special-cased one.
3. **`--root` is exactly the escape hatch a standalone package needs where ambient inference cannot be trusted.** A pip-installed CLI invoked by an unrelated wrapper script, from an unpredictable cwd, with no `CLAUDE_PROJECT_DIR` set (because there is no Claude Code session at all), has no ambient signal to infer a project boundary from beyond cwd — which may be wrong (e.g., invoked from a build tool's own working directory, not the target repository). `--root` gives an integrator a way to be fully explicit and bypass cwd/env-var ambiguity entirely. Without it, the standalone-package scenario would degrade to "hope cwd is right, with no way to override" — exactly the class of problem BUG-010 itself was filed against (a wrong, un-overridable root assumption). The design closes the *general* version of the bug it was filed to fix, not only the specific plugin-vs-project instance of it.
4. **`get_containment_roots(explicit_root: str | None = None) -> list[Path]` is a small, pure, directly-callable function with no argparse or Claude-Code-specific coupling.** It is independently testable and independently callable from any future consumer — a library API surface, an MCP server tool, or a subprocess wrapper — without modification. This is the right interface shape for logic that a future non-CLI integration will need to reuse, and it was arrived at as a byproduct of solving today's bug, not as premature architecture.
5. **eng-lead's own L2 Strategic Implications section (independently, in the plan artifact) recommends this exact pattern — "default set + exclusive override + testability seams" — become "the house pattern" for future Jerry CLI surfaces touching the filesystem outside the project tree**, naming `jerry agents build` output paths and transcript ingestion as anticipated future consumers. This is direct evidence the design was consciously built as reusable infrastructure, which directly supports (though does not, on its own, prove) robustness under a broader standalone-package deployment model.

**Best Case Scenario (Step 4):** This design is strongest under the following conditions, which should be stated explicitly rather than assumed: (a) `CLAUDE_PROJECT_DIR` continues to be the *only* Claude-Code-specific coupling point, and no other code path acquires an implicit Claude-Code assumption as the tool evolves; (b) the OS temp directory is not, in practice, treated by operators as a place any other principal can write attacker-controlled content the tool would then trust — the H-01 ownership gate is precisely what makes this assumption safe rather than merely convenient; (c) future non-Claude-Code integrators either supply `--root` explicitly or accept cwd-based inference as adequate for their use case. **Confidence in the reconstructed standalone-package case: MODERATE-HIGH.** The code-shape evidence (points 1–4 above) is strong and directly verifiable; the claim is weakened only by the fact that no artifact in scope states it as an intentional design goal — it is a favorable emergent property, not a documented target. This distinction should be made explicit rather than implied (SM-004).

### 5. Preemptively Addressing the Obvious Objection (Step 3.3 — address likely counterarguments)

The most obvious objection a critique strategy will raise is: *"Widening the default containment set to include world-writable OS temp directories inherently weakens a security boundary — how is this not a regression?"* The strongest rebuttal, grounded in the actual shipped code rather than intention alone:

- The M-08 (path escape) and M-10 (symlink escape) invariants are **generalized, not removed** — both checks changed from `is_relative_to(single_root)` to `any(is_relative_to(r) for r in allowed_roots)` (`ast_commands.py:334, 350-353`) — the *predicate* (must be inside a known-good root) is unchanged; only the *cardinality* of "known-good" grew, and grew for a stated, verifiable reason (SM-002/SM-003), not arbitrarily.
- The team did not merely assert this was safe — they **red-teamed their own widening** (RED-BUG010) and found exactly the class of gap a reviewer would predict (H-01: no ownership check on the newly-admitted shared-writable roots) — and then **closed it in the shipped code**, scoped with surgical precision to *only* the temp-default-match case (`_is_temp_default_root_match`, `ast_commands.py:181-209`), never touching the project-root or explicit-`--root` paths. This is the textbook-correct scope for the fix: it closes the one place where the *tool*, not the *user*, made an implicit trust decision, while leaving both explicitly-user-chosen locations (project root, `--root`) exactly as permissive as the owner directed.
- The H-02/H-08 remediation (`_is_broad_containment_root`, `project_root.py:63-117`) replaced a brittle exact-match check with a portable `PurePath.relative_to()` ancestor-of-home predicate — this is evidence the team responds to red-team findings with *generalizing* fixes rather than narrow patches, which is the stronger engineering signal for a design intended to be a reusable "house pattern" (SM-003, point 5).
- Every one of the pre-existing invariants this design must not break was independently verified, not assumed: TOCTOU recheck reuses the identical `root` value at write time as at read time (`ast_commands.py:679-682`, dedicated regression test); `mkstemp`+`os.replace` atomic-write staging is completely untouched by the widening; the 1 MB size cap (M-05) is untouched; the A-07 path-traversal regression suite was re-run unmodified and passes.

### 6. What This Reconstruction Does NOT Claim (Step 2 — substantive weaknesses, explicitly left for critique strategies, not addressed here)

Per S-003 methodology, presentation and structural gaps are strengthened above; substantive questions are surfaced, not resolved, so subsequent strategies can attack them fairly:

- Whether `os.geteuid()`-based ownership scoping is *sufficient* on shared hosts with more exotic privilege models (setuid, containers sharing a UID namespace, etc.) is a substantive security question, not addressed by this steelman — legitimate target for S-001 Red Team / S-012 FMEA.
- Whether the cwd-fallback in `get_project_root()` is the *right* default for the standalone-package future, versus requiring an explicit `--root` in the absence of `CLAUDE_PROJECT_DIR`, is a genuine design trade-off this steelman surfaces but does not resolve — legitimate target for S-002 Devil's Advocate / S-004 Pre-Mortem.
- The R-3/R-4 open decisions (broad-`--root` warn vs. reject; temp-match transparency note vs. silence) were owner-recommended, not owner-mandated, per the eng-lead plan's own framing ("OPEN — requires owner/user confirmation") — whether the shipped stderr-warning behavior is the right final answer, versus a harder guardrail, is appropriately left open for challenge.

## Genuine Strengths the Tournament Should Preserve

These are properties of the *actual shipped code* (verified by direct read, not inferred from the plan) that subsequent challenge strategies should recognize as strengths rather than attack as if they were gaps:

1. **The M-08/M-10 predicate is generalized, not weakened** — `any(is_relative_to(r) for r in allowed_roots)` is the same security check extended over a principled, evidenced root set, not a loosened check.
2. **The H-01 ownership gate is scoped with surgical precision** — `_is_temp_default_root_match` ensures the new `st_uid`/`geteuid()` check applies *only* to implicit (tool-inferred) temp-root admissions, never to the project root or an explicit `--root`, preserving both the zero-friction common case and the owner's explicit user-discretion directive simultaneously.
3. **TOCTOU discipline is provably unbroken across the widening** — the write-time recheck in `ast_modify` consumes the identical `root` parameter as the read-time check, with a dedicated regression test proving no read/write disagreement is possible within one invocation.
4. **The `--root` exclusivity (not additive union) is the correct primitive** for reproducible, hermetic scripted/CI use, and is exactly the mechanism a future standalone-package or non-Claude-Code integration will need.
5. **The team red-teamed its own widening voluntarily** and closed both findings with generalizing, portable fixes (`PurePath.relative_to()` ancestor-of-home) rather than narrow platform-specific patches — this is the pattern to hold subsequent scope-widening changes to, referenced explicitly by eng-lead's own plan as a candidate "house pattern."
6. **Test-suite integrity was actively defended, not assumed** — the team identified and fixed a genuine blind spot (pytest `tmp_path` living inside the system tempdir, which would have silently flipped two security-regression tests into false passes) and manually verified the fix was load-bearing (remove-seam-confirm-red, restore-seam-confirm-green) rather than cosmetic.
7. **Deployment-model severity was stated honestly, not minimized** — the red-vuln assessment explicitly rates H-01 differently for single-user-laptop vs. shared/CI-host deployment rather than picking the more favorable rating and hiding the other, and fixed the issue regardless of which model currently dominates.
