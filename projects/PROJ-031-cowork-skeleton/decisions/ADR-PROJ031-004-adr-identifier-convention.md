## L0: Executive Summary

Jerry has never had a written rule for naming Architecture Decision Records (ADRs), and the result is a zoo of incompatible ID styles — some keyed on the birth project (`ADR-PROJ031-001`), some on the subject (`ADR-agent-design-001`), some bare and colliding (`ADR-001` reused in three unrelated places). This matters because ADRs are the **one** artifact class in Jerry that is *supposed to change scope*: a good decision made inside a project is meant to "graduate" into the framework. Today, graduating an ADR means renaming it, which silently breaks every document that cited the old name. This has already happened — all three framework ADRs (from two framework-mandate projects) were born inside projects and renamed on promotion; the resulting broken citations remain *unrepaired* months later (verified for the PROJ-007 pair — see [References](#references)).

**The decision:** ADR identity encodes the **subject** of the decision (a domain slug like `agent-design` or `plugin-distribution`), not its **origin** project. Origin is preserved, but it lives in the file's frontmatter, not in its name. An ADR keeps the same identity for its whole life; promotion from a project into the framework becomes a plain file move with no rename and no broken citations. The project-scoped style (`ADR-PROJ031-NNN`) survives only as a *permitted, discouraged dialect* for purely local decisions, and the existing project ADRs are grandfathered in place — no mass rename. Because Jerry's HARD-rule budget is full (25/25), this is a MEDIUM-tier convention (RECOMMENDED, override-with-justification), **to be enforced by a deterministic CI lint** (CC-001, iter-3: the lint is *designed, not yet built* — enforcement is advisory until M-6 ships; see the [lint Claim-Status](#enforcement-design-l5-ci-lint)) rather than a hard block.

**Why this answers the user's challenge:** the objection is that Jerry's whole ontology is scope-prefixed (PROJ/EPIC/STORY/DEC), so ADRs "should" be too. But those entities carry (or imply) scope in their identity *precisely because their scope never changes* — and the true differentiator is **mutability, not whether scope literally appears in the ID string**. (`DEC-NNN`, for instance, is written *bare* at Enabler/Story level — `DEC-001-cli-hook.md` — its scope supplied by the parent folder, not the ID; yet its scope is still permanently fixed.) The ADR is the sole entity whose *scope is mutable by design* — the one thing built to migrate — so encoding its current scope into its immutable identifier is a category error. Subject and origin are both immutable; subject is also what readers search by; therefore subject wins the identity, and origin goes to metadata.

**The crux (the user's challenge, verbatim in spirit).** Project-scoping encodes **origin into identity**. Jerry's ontology is scope-prefixed everywhere (PROJ/EPIC/FEAT/STORY entities; `DEC-NNN` parent-scoped — `skills/worktracker/rules/worktracker-directory-structure.md:56-88`), which *favours* origin-encoded schemes (A/C). ## Forces

1. **Distributed, uncoordinated authoring.** Many agents/branches author ADRs in parallel. Any scheme needing a shared counter or central registry is a standing merge-conflict liability (the exact failure that produced the live bare-`ADR-NNN` collisions, and that log4brains publicly abandoned monotonic numbering to escape — `adr-convention-standards-research.md:100`).
2. **Migration is intrinsic to ADRs, unique among Jerry artifacts.** Promotion (project → framework) is not an edge case the ontology anticipated; it is the accrual thesis in action. All 3 framework ADRs got there this way — from 2 correlated framework-mandate projects, not 3 independent trials (DA-004; see [Bimodal Refinement](#which-regime-is-real-the-bimodal-refinement)).
3. **Origin is worth preserving, but it is a *birth fact*, not an identity.** A decision's birth project never changes; its *current* governing scope does. Encoding the mutable thing (scope) into the immutable thing (the ID) is the tension at the heart of the crux.
4. **Discoverability vs provenance.** Readers and future agents query ADRs by *subject* ("the ADR governing plugin distribution"), not by birth project. BUG-006's two *major*-severity findings are discoverability/recognition failures of opaque origin IDs. Provenance still matters — but it can live in frontmatter.
5. **Ontology coherence.** Every other Jerry entity ID is scope-prefixed; a subject-slug ADR is a visible deviation with an onboarding cost. The force pulling toward A/C is real; the question is whether it should govern the one entity the ontology never contemplated migrating.
6. **Governance economy.** MEDIUM tier means the convention cannot compel ("MUST"); it can only recommend and lint. The scheme chosen must degrade gracefully when authors ignore the recommendation.

## Options Considered (A–F)

All six schemes from the trade study are evaluated. Per H-16 (steelman before critique), each option leads with the *strongest* case its blind advocate made before the weaknesses are stated. Scores are the trade study's weighted-sum totals (`orchestration/adr-convention-20260702-001/explore/trade-study.md:217-231`), reproduced for reference; they are *inputs*, not the decision.

### Scheme A — Project-scoped sequence: `ADR-{PROJECT-ID}-NNN-slug`

**Strongest case (steelman, from `advocate-project-scoped.md`).** A is not a new pattern invented for ADRs — it is the *only* pattern Jerry's entity ontology uses, for every entity, everywhere (`worktracker-directory-structure.md:60-90`). It is already the dominant, near-collision-free, converged-upon practice (11 project-scoped ADRs, zero *project-ID* collisions), and the collision record directly indicts the alternatives: bare unscoped numbering has collided three times; scope-prefixing is strongly collision-*resistant* because the *scope portion* of the ID is uniquely allocated at creation. (Steelman honesty, CV-001: "immune by construction" is too strong — the per-scope `NNN` sequence is still uncoordinated, and `ADR-EPIC002-001` did collide within its entity-ID family; see [Context](#context). The correct claim is *resistant*, which is still materially better than bare numbering.) Provenance is maximal (origin is visible at a glance), lint is a trivial local regex, and no new tooling is needed.

**Pros:** Maximal provenance (C3=5); perfect ontology consistency (C5=5); trivial deterministic lint (C8=5); strong collision-*resistance* (C1=4 — resistant, not immune, per CV-001).
**Cons:** Worst-in-class on promotion-stability (C2=2): origin *is* the identity, so promotion forces a rename that breaks citations — the verified live wound. Worst-in-class on discoverability (C4=2): `ADR-PROJ031-001` says nothing about subject (BUG-006 F-001/F-003, both severity 3).
**Fit with constraints:** Satisfies c-006 (lint-able) best; violates the *spirit* of c-005/force-2 by making the migrating artifact's identity the mutable property. Baseline score **3.52 (rank 4)**.

### Scheme B — Domain-slug everywhere: `ADR-{domain-slug}-NNN-slug`, origin in frontmatter

**Strongest case (steelman, from `advocate-domain-slug.md`).** The live repo already converged on B *and paid to get there*: all three framework ADRs were born under A/C identity and force-migrated to domain-slug via a dedicated C4 remediation (BUG-006), touching ~150 references in one commit (`41539073`) and rule files in another (`5ef0b2fa`), both 2026-04-13. **This is a paid promotion tax with a git receipt** — and it is not even fully repaid: stale citations to the extinct `ADR-PROJ007-001/002` IDs still sit in PROJ-007's own `ORCHESTRATION.yaml:228,242`, `WORKTRACKER.md:106-107`, and `EN-001.md:48-49,72-73` as of 2026-07-02. B would have prevented every dollar of that tax: assign the eventual domain identity at birth, and promotion is a `git mv` with zero rename. B also wins discoverability (C4=5), sortability (C6=5), and — decisively — promotion-stability (C2=5). Jerry's thesis says promotion is the point; B is the only scheme that treats it as first-class and free.

**Pros:** Best promotion-stability (C2=5); best discoverability (C4=5) and sortability (C6=5); matches the already-accepted BUG-006 remediation (Alternative 3) and external slug-as-ID norm (log4brains; **JPH — Joel Parker Henderson's `architecture-decision-record` collection, which uses descriptive kebab-case names with no numbering; source-verified `adr-convention-standards-research.md:99,216`**, added to [References](#references) #12 per CC-002 iter-4).
**Cons:** Slug-uniqueness is an *uncentralized* discipline, not a structural guarantee (C1=3) — two authors could independently mint the same slug with no error signal. Diverges from the scope-prefixed ontology (C5=2). Higher one-time migration for the ~15 pre-existing project/entity dialect ADRs (C7=2; filesystem-verified 2026-07-02).
**Fit with constraints:** Its one non-local check (repo-wide slug-uniqueness) is a cheap `sort | uniq -d`, satisfying c-006. Its ontology divergence is exactly the deviation the crux argues is *correct* for the migrating artifact class. Baseline score **3.58 (rank 3)**; **flips to 3.96 (rank 1) under high-promotion weighting**.

### Scheme C — Two-namespace: A in `projects/*/decisions/`, B in `docs/design/` after renumber-on-promotion + tombstone

Its promotion mechanic has no external precedent — it is admitted synthesis (`adr-convention-standards-research.md:113,158`).

### Scheme F — Scope+slug, no number: `ADR-{SCOPE}-{slug}`

**Strongest case (steelman).** If `{SCOPE}` is read as a domain, F shares all of B's recognition/discoverability wins (C4=5, C6=4) while dropping the counter B/D/E fight over — no shared sequence to race on, so collision only on same-scope + same-slug (rare, lint-catchable; C1=4).

**D-1 — Identity encodes subject, not scope.** An ADR's canonical identifier is `ADR-{domain-slug}-NNN`, where `{domain-slug}` names the *subject* of the decision (kebab-case) and `NNN` is a 3-digit, zero-padded, never-reused sequence **within that domain slug**. ## Rationale — Answering the Crux Head-On

**The question the user put to me: is *project* really the right scope key for ADR identity?**

**Answer: No — and for a principled reason that does not depend on how often promotion happens.** An identifier should be **invariant across the artifact's lifecycle**. Jerry's scope-prefixed ontology (PROJ/EPIC/FEAT/STORY/DEC) works *because* those entities have an invariant scope: a STORY is born and dies a story; a `DEC-NNN` is permanently parent-scoped (`EPIC-001--DEC-001`, `worktracker-directory-structure.md:65`). Their scope *is* a permanent property, so encoding it in the ID is correct and free. The ADR is the sole entity whose governing scope is **mutable by design** — it is built to graduate. Encoding a mutable property (current scope) into an immutable string (the identifier) is the actual defect. Of an ADR's properties, two are immutable — its **origin** (birth project) and its **subject** (what it decides) — and one is mutable — its **current scope**. Origin is worth preserving but nobody searches by it; subject is both immutable *and* the axis every reader and agent queries on. Therefore **subject wins the identity, origin goes to frontmatter, and scope — the mutable thing — is expressed by *location*, which is allowed to change.** Project is the wrong scope key because it encodes the one mutable property into the one place that must never change. **Honest bound on "subject is immutable" (DA-008, iter-4, P-022):** this is an assertion about a well-scoped decision, not a proof — hindsight *can* relabel a decision's subject (a decision first framed as "agent-design" might later be seen as really about "routing"). The claim is that subject is **far more stable than scope**: scope changes *by design* on every promotion (a certainty the whole convention is built around), whereas subject-relabeling is a rare, judgment-dependent edge case handled by the same supersession mechanism as any other identity change (DA-006's remediation loop). So the argument does not need subject to be *perfectly* immutable — only *materially more* immutable than scope, which it demonstrably is.

Three independent lines converge on this, and — importantly — **only one of them is promotion-frequency-dependent**, which is what makes the decision robust:

1. **The ontology argument proves less than it appears (promotion-independent).** Yes, every worktracker entity is scope-prefixed — but those entities never migrate. Applying a *never-migrates* naming rule to the *one thing that migrates* is a category error. Consistency with the ontology (force-5) is real, but it should not govern the exception the ontology never contemplated. This holds whether promotion is frequent or rare.

2. **The discoverability failure is promotion-independent and already adjudicated.** BUG-006 — an evaluation the maintainers *accepted and acted upon* — found the origin-encoded scheme fails 4 of 10 Nielsen heuristics, 2 at major severity, purely on recognition/discoverability grounds (`BUG-006-adr-naming-evaluation.md:12-21`). `ADR-PROJ007-002` is opaque *even if it never promotes*. Origin-encoding (A/C) fixes discoverability only for the promoted framework minority; the project-local majority stays opaque forever. Subject-encoding fixes it everywhere. This argument stands even in the low-promotion regime.

3. **Jerry's own thesis picks the regime, and the corpus has already voted (promotion-dependent, but empirically supported).** If "accrues knowledge from projects into the framework" is the product's reason to exist, promotion is the success condition, not an edge case. All framework ADRs arrived by promotion — but stated with DA-004 honesty (iter-3): this is **3 promoted ADRs from 2 correlated framework-mandate projects (PROJ-007 → 2; EPIC-002 → 1), not 3 statistically-independent trials** (the [Bimodal Refinement](#which-regime-is-real-the-bimodal-refinement) makes the correlation explicit). Each incurred an ID change and a citation break — one of which (`ADR-PROJ007-001/002`) is *still* unrepaired in its origin project 2.5 months later (`advocate-domain-slug.md:57-61`). The evidentiary base is thus a small, correlated one (this is exactly why [Confidence](#confidence) is capped at 0.75 and the [adverse-regime test](#the-regime-in-which-this-decision-is-wrong-stated-plainly-p-022) is kept live); the two *promotion-independent* arguments (1 and 2 above) are what make the decision robust despite it. Betting on A/C is still betting against the framework's premise and taxing its success path.

**The honest counter-case (kept alive per H-16 / divergent discipline).** If, in practice, the overwhelming majority of ADRs are project-local forever and only a rare few promote, then Scheme C is the better-*calibrated* choice: it gives origin-in-identity and near-zero migration for the 80–90% that never move, and pays the renumber cost only for the rare graduate. **C is not wrong — it is right under a different, testable belief about promotion frequency.** I reject C anyway, for reasons that survive even the low-promotion regime: (a) C institutionalizes a *demonstrated* failure (the citation break) rather than eliminating it; (b) C's decisive advantage is migration cost (C7=5), a *one-time, self-liquidating* quantity that is methodologically wrong to let govern a permanent, forever-growing convention; and (c) arguments 1 and 2 above do not need promotion to be frequent. The promotion-frequency evidence (argument 3) is the *tie-breaker that makes the win decisive*, not the sole support — which is precisely the robustness the crux demands.

### The zero-governance null alternative (requested benchmark, IN-004)

The invoking task asked that the winner be benchmarked against a **do-nothing / index-and-search** null option: impose *no* ID convention at all and instead rely on a generated index or repo-wide `grep`/semantic search to locate ADRs regardless of how they are named. This is the honest "why have a convention at all?" baseline, and it is stated plainly here even though it loses:

- **What the null gets right.** It has zero adoption cost, zero migration, zero taxonomy-governance burden, and it never breaks on promotion (there is no ID rule to violate). For *discovery* specifically, a good index can partly substitute for a legible identifier — you find the plugin-distribution ADR by searching "plugin distribution," not by reading a filename.
- **Why it still loses to B.** (1) **Citations, not discovery, are the load-bearing failure.** The demonstrated wound (the still-stale `ADR-PROJ007-001/002` and dangling `ADR-CI-001` references) is a *citation-integrity* problem; a search index does nothing for a hyperlink or path that already points at a moved file. B fixes citations at the source (stable identity + `git mv`); search cannot. (2) **The null has no collision story** — it is exactly today's state, which already collided three times on bare `ADR-NNN`. (3) **An index is itself governance** — someone must build, run, and keep it fresh (a server-ish process the constraints reject, c-006), whereas B's *discovery* substrate is the filename grammar itself: a subject-encoded ID is self-describing at zero maintenance cost, so `grep`-by-subject is free and always current. **Honesty qualifier (IN-003, iter-3, P-022):** this "free and always current" property is claimed *only* for the filename-grammar-as-discovery-index — it does **not** extend to B's *taxonomy-coherence* layer (the `docs/design/README.md` domain registry + a human best-effort synonymy review — no automated lint, that check was descoped in the subtraction pass), which the [L2 Architectural Implications](#l2-architectural-implications) correctly names as "the new long-term liability… a soft process that can rot," requiring a named arbiter (M-5b). The two are distinct: the ID *string* is free and self-current; keeping the *slug vocabulary* coherent is the governed, non-free part. The null alternative loses because it has neither — no free discovery substrate AND no collision/coherence story — whereas B has the free discovery substrate and pays a bounded, owned cost only for taxonomy coherence. (4) The null is not even truly "zero" — it externalizes the cost onto every reader, every time, forever, rather than paying it once at authoring. B is therefore, by design, better than the null on citation-integrity and collision-safety while matching it on promotion-stability; the null's only edge (no taxonomy burden) is the single negative consequence B already discloses and mitigates. **Qualifier (IN-002, iter-6, P-022):** this "better than the null" is an *argued design advantage, not yet a demonstrated one* for agent-authored ADRs — its discovery-substrate benefit is only fully realized once the producing agent emits compliant IDs (M-12) and the guidance is auto-loaded (M-2); until then it is a well-reasoned prediction. The benchmark confirms a convention is warranted; it does not favour doing nothing.

## Promotion-Frequency Sensitivity (The Load-Bearing Assumption)

The user mandated an explicit sensitivity analysis of the winner against the promotion-frequency assumption. Here it is, in full, including the regime in which the winner *loses*.

### The tipping point

The trade study's re-weighting is unambiguous (`trade-study.md:246-292`): the single assumption that decides A/C-vs-B is the weight on promotion-stability (C2). At the baseline (C2≈16, "promotion is important but ordinary"), **C wins (3.86 > B 3.58)**. Under a promotion-is-normal weighting (C2≈28, with ontology-consistency and one-time migration correspondingly discounted), **the winner flips to B (3.96 > C 3.70)**. The approximate crossover is **C2 ≳ 22**. **Derivation disclosure (DA-005, P-022):** this "≳ 22" is a **linear interpolation between exactly two bundled reweighting scenarios** — the baseline (C2≈16) and the high-promotion bundle (C2≈28), each of which reweights *three* variables at once (C2 up, ontology-consistency C5 and one-time-migration C7 correspondingly down). It is therefore an *approximate midpoint of a two-point line through multi-variable bundles*, **not an independently-computed single-variable threshold**: the trade study did not sweep C2 alone in isolation while holding all other weights fixed, so "22" carries the precision of an interpolation, not of a derived univariate tipping point. The `≳` (greater-than-approximately) notation is used deliberately for that reason. The qualitative conclusion — that the flip is driven by the promotion-stability weight and lands somewhere in the upper half of the plausible C2 range — is robust; the exact "22" is illustrative. Discoverability pressure alone (sensitivity (b)) does *not* flip it — C survives that — but discoverability + high-promotion together drive B decisively ahead (~4.0 vs ~3.6).

### Which regime is real? The bimodal refinement

The raw promotion rate is a poor statistic, and reading it naively cuts *both* ways. Raw rate ≈ 3-in-18 ≈ 17% (`advocate-domain-slug.md:123`) — "most ADRs do not migrate," which superficially favours C. But the denominator is wrong, because **promotion frequency is bimodal, not uniform** (`advocate-domain-slug.md:125`):

- **Tactical, single-project decisions** promote at ≈ 0%. They are born local and stay local.
- **Framework-mandate decisions** promote at a materially higher rate. Of the two projects whose entire mandate was framework-general governance (PROJ-007 "agent patterns"; EPIC-002 quality/output-path), the flagship *cross-cutting* decisions promoted: **2-for-2 PROJ-007**; **1-of-3 EPIC-002** — `ADR-output-path-resolution-001` promoted to `docs/design/` (verified: `Parent: EPIC-002`), while `ADR-EPIC002-001-strategy-selection` and `ADR-EPIC002-002-enforcement-architecture` stayed local as internal governance (both verified on disk in `PROJ-001-oss-release/decisions/`). That is 3-of-5 for the framework-mandate subset versus ≈ 0% for tactically-scoped work — the gap, not the exact rate, is what makes promotion frequency bimodal.

  > **Count reconciliation (P-022, iter-1, closes SM-004).** The cited advocate source (`advocate-domain-slug.md:125`) reports "1 of EPIC-002's **2** ADRs"; this ADR reports **1-of-3**. The "1-of-3" is the corrected figure: three ADRs were born under EPIC-002 — the promoted `output-path-resolution` one (originally minted as `ADR-EPIC002-001`, renamed on promotion, commit `9b36bda2`/`41539073`) **plus** the two that remain local on disk (`ADR-EPIC002-001-strategy-selection`, `ADR-EPIC002-002-enforcement-architecture`, both filesystem-verified 2026-07-02). The advocate source's "2" omitted `enforcement-architecture`. Using either denominator, the qualitative point (framework-mandate ADRs promote far above the tactical ≈ 0% baseline) is unchanged.

**Circularity disclosure (DA-001, iter-4, P-022 — the classification is retrospective, not predictive).** S-002 correctly challenged that the "framework-mandate vs. tactical" bucket is applied *after the fact* to exactly the two projects whose ADRs are known to have promoted (PROJ-007, EPIC-002), with **no prior, outcome-independent criterion** given for labeling a project "framework-mandate" *before* observing whether its ADRs promote — which risks unfalsifiability, and means the sampling procedure selects on the outcome variable. Worse, **this very ADR is a live disconfirming instance**: it was born in `PROJ-031-cowork-skeleton` (a skeleton/distribution project, *not* pre-labeled "framework-general governance" the way PROJ-007/EPIC-002 explicitly were), yet it is maximally framework-scope and self-promoting. Honest resolution: **the bimodal argument is downgraded here from a *predictive model* to an *illustrative retrospective pattern-match*.** It is *not* load-bearing on its own — it is the tie-breaker (argument 3 of the [Rationale](#rationale--answering-the-crux-head-on)), and the two *promotion-independent* arguments (ontology category-error; discoverability, arguments 1–2) carry the decision even if the bimodal pattern is discounted entirely. An *ex-ante* criterion, if one is wanted, would be: "a project whose PLAN.md charter states a framework-general / cross-project governance mandate at creation" — and PROJ-031 shows even that would misclassify (its charter is distribution, yet it produced a framework ADR), which is precisely why the [Confidence](#confidence) cap (0.70–0.75) and the [adverse-regime test](#the-regime-in-which-this-decision-is-wrong-stated-plainly-p-022) are kept live rather than the bimodal pattern being treated as settled evidence. The `≳ 22` tipping point already carries its own two-point-interpolation disclosure (DA-005, iter-1); the circularity of the *category feeding* that analysis is now disclosed alongside it.

This bimodality is the key that dissolves the false binary. Pure-A/C forces the *tactical majority and the framework-intended minority into the same origin-encoded mould*, paying the promotion tax on the minority. Pure-B-from-birth-for-everything imposes domain-taxonomy governance on the tactical majority that never needs it. **The decision (D-1 through D-3) resolves this by matching identity to intent:** subject-slug is RECOMMENDED for anything with cross-project/framework relevance (the promoting population), and the project-scoped dialect is permitted (SOFT `MAY`) for the purely-tactical population (the non-promoting one).

**The "author knows the intent at birth" premise — reconciled honestly against its own counter-evidence (IN-001 / DA-003, P-022).** An earlier draft asserted "the author *usually knows* the intent at birth." Two independent adversarial strategies caught that this over-claims and contradicts two things this very ADR relies on: (a) the GOV.UK maturity-gradient principle it *approvingly cites* in the [Scheme C steelman](#options-considered-af) — "you typically do not know an ADR is framework-wide the day you write it; you learn it by living with it"; and (b) this ADR's **own authorship** — it is maximally framework-scope yet was filed under the discouraged dialect (`ADR-PROJ031-004`). The claim, as stated, was false. **Corrected position:** authors are *sometimes* confident of intent at birth (the 2-for-2 / 1-of-3 framework-mandate evidence, `advocate-domain-slug.md:133`) and *often uncertain* (GOV.UK). Crucially, **the decision does not depend on authors classifying correctly at birth**, and this is its robustness: because the canonical domain-slug form is *scope-agnostic* — free to keep if the ADR stays local, free to move (`git mv`) if it promotes — **the correct default under uncertainty is the canonical slug, not the dialect.** The dialect (D-3) is reserved for the narrow case of *positive certainty of locality*; uncertainty resolves *toward* B, never toward the rename-prone dialect. To make declared intent explicit rather than implicit, the `scope:` frontmatter field is **mandatory at authoring time** (added to ADR-M-003 in the companion draft): the author records `framework` or `project`, and — per the strengthened D-3 — an ADR that touches `.context/rules/`, agents, routing, or is authored at C3/C4 SHOULD NOT use the dialect regardless of the author's guess. **Residual risk, named and monitored (not waved away):** the Path-2-rename recurrence risk this ADR exists to remove *does* survive as [R-4](#risks) (dialect abuse) — bounded by SHOULD-guidance, the promotion-cost-visibility of the process, and the L-4 lint flagging any dialect ADR that later carries `promoted_to`. This ADR's own dialect filename is the disclosed, deliberate instance of that risk, scheduled for Path-2 self-promotion at M-9 precisely to model — and thereby teach authors to avoid — the discouraged path.

### The regime in which this decision is wrong, stated plainly (P-022)

**If all three of the following hold, C would have been the better choice and this decision is over-engineered:**
1. Forward promotion rate stays near zero *even for framework-mandate projects* (i.e., future PROJ-007/EPIC-002-like efforts stop producing promoted ADRs); AND
2. Domain-slug collisions become frequent and painful in practice; AND
3. The ontology divergence causes measurable onboarding friction.

I judge this conjunction unlikely but *not* impossible (n=3; the framework is young; base rates can regress as project count grows). **This is why the decision is deliberately low-regret rather than maximal:** it does not big-bang (D-4), it keeps the project dialect alive (D-3), and it is MEDIUM-tier and reversible (D-5). Even in the adverse regime, B is never *worse* than C on the promotion-independent axes (arguments 1–2 of the rationale); it only "pays governance for a benefit realized rarely," and that governance is a one-line lint (`sort | uniq -d`). The downside is bounded and cheap; the upside (free promotion, permanent discoverability) compounds with corpus size, which only grows.

### Confidence

**0.75 (moderate-high) — capped at the trade study's declared ceiling (SM-002 correction, P-022).** An earlier draft stated **0.78**, which silently **exceeded the trade study's own explicit, reasoned ceiling**: "I decline to claim >0.75 for a C4 governance flip resting on n=3" (`trade-study.md:341`). Crossing a cited source's stated ceiling without acknowledgement is exactly the kind of quiet inflation P-022 forbids, so the headline is corrected to sit **at** that ceiling, not above it. The reason to sit at 0.75 rather than at the trade study's lower **0.70 single-winner** figure is defensible and disclosed: (a) the decision no longer rests *solely* on the promotion-frequency belief — two of its three supporting arguments ([ontology category-error](#rationale--answering-the-crux-head-on) and [promotion-independent discoverability](#rationale--answering-the-crux-head-on)) hold even in the low-promotion regime — and (b) the graceful posture (permitted dialect, grandfather, MEDIUM-tier, reversible) de-risks the adverse regime. But it is **not raised above 0.75**, in explicit deference to the trade study's ceiling and because the load-bearing empirical unknown — the *forward* promotion rate at n=3 — genuinely remains. Expressed as a range to make the residual uncertainty legible: **0.70–0.75** (0.70 = the trade study's single-winner call; 0.75 = the ceiling, credited for the two promotion-independent arguments and the low-regret posture; never higher, on a C4 governance call resting on n=3).

## L1: Technical Implementation

### ID grammar (canonical and dialect)

```
Canonical (RECOMMENDED, all scopes):   ADR-{domain-slug}-NNN-{title-slug}.md
  domain-slug : ^[a-z][a-z0-9]*(-[a-z0-9]+)*$   (subject; kebab-case; e.g. agent-design, plugin-distribution)
                (SM-101, iter-3; CC-003-iter7 tier-hygiene: this "must" is the grammar/lint mechanism's
                 own match condition, not a HARD author obligation — the FIRST token must begin with a
                 LETTER, not a digit. An all-numeric
                 leading token like `150` is deliberately excluded so that a GH-issue/bare-number ID
                 such as `ADR-150-001` is NOT admitted as a "domain slug" — that would both collide
                 with the L-2 bare-detection `^ADR-\d` and falsify the "matches neither grammar" claim
                 the grandfather allowlist relies on. Subject slugs are words; numeric-leading IDs fall
                 to bare/grandfather handling.)
  NNN         : \d{3}   zero-padded, monotonic WITHIN the domain-slug, never reused
  title-slug  : optional human tail (kebab-case)

Dialect (permitted / SOFT MAY, project-local only): ADR-{PROJECT-ID}-NNN-{title-slug}.md
  PROJECT-ID  : one of a CLOSED entity-prefix set {PROJ|EPIC|FEAT|STORY}\d{3} — legacy/tactical
                (PM-005: this is a fixed enumeration, NOT open-ended "any finer entity ID"; it
                 matches the L-1 dialect sub-pattern ^ADR-(PROJ|EPIC|FEAT|STORY)\d{3}-\d{3} exactly. FEAT
                 is included for parity with the worktracker entity set even though no FEAT-dialect
                 ADR exists on disk today; adding a new prefix requires editing BOTH this grammar
                 AND L-1's dialect sub-pattern, so the two can never silently diverge.)
  NNN         : \d{3}   monotonic within that scope ID

Deprecated (new ADRs):  bare ADR-NNN...  (collision source — Scheme E degenerate)
Frozen (legacy):        docs/adrs/ADR-NNN, docs/archive/.../ADR-0NN  (do NOT extend)
```

**`canonical_id` is an OPTIONAL advisory field (IN-006/FM-007 fix, iter-4, P-022).** Two independent iteration-4 strategies (S-013 IN-006, S-012 FM-007) flagged that this ADR's *own* frontmatter (`:15`) uses `canonical_id: ADR-adr-convention-001` — a field the published schema did not define — so the flagship "worked example of self-compliance" used a mechanism the rules did not offer other authors. Corrected: `canonical_id` is now a documented, optional, null-by-default advisory field in **both** this schema and the companion rule draft's [Frontmatter Schema](../design/adr-standards-rule-draft.md#frontmatter-schema). It has **no lint enforcement** (it is informational, not a relationship link L-7 checks) — any dialect author in this ADR's own "born-under-dialect, destined-for-Path-2" situation may now declare their known canonical destination the same way this ADR does.

The three existing framework ADRs already do this informally via `PS-ID`/`Parent` comments (`docs/design/ADR-agent-design-001.md:3` → `PS-ID: PROJ-007 | ENTRY: e-004`), proving origin survives an identity change in metadata (see the [FM-104 correction](#positive) — "survives" is presence-checked, not accuracy-checked) — the traceability argument for A/C is already satisfied by B without the identifier carrying it.

**Two frontmatter mechanisms coexist — YAML for the lint, blockquote for `jerry ast` (CC-003 reconciliation, iter-3, P-022).** A verified tooling tension must be stated plainly: Jerry's existing `jerry ast frontmatter` command parses **blockquote** frontmatter only ("Extract all **blockquote** frontmatter fields as a JSON object," `skills/ast/SKILL.md:105`, verified 2026-07-02), whereas the ADR frontmatter this convention mandates (`id`, `scope`, `origin_project`, `superseded_by`, …) is written as a **YAML `---` block** and is read by the L-7 relationship lint. These are two different parsers. The reconciliation, chosen deliberately rather than left implicit:

- **The L5 ADR lint parses the YAML `---` block.** YAML parsing is a **new capability the lint must implement — explicitly scoped into M-6** (it is not free; `jerry ast` does not provide it). This is disclosed here so the lint's dependency on YAML parsing is owned, not discovered.
- **`jerry ast frontmatter` (blockquote) is retained for worktracker entities and human-readable ADR headers, not as the ADR lint's parser.** This ADR therefore carries **both**: the YAML `---` block above the H1 (for the lint) *and* its existing blockquote header (for `jerry ast` and human reading). The two are kept in sync by convention; a future consolidation (single source) is possible but out of scope here.
- **Why not switch to blockquote-only (zero new tooling)?** Considered and rejected: the mandated relationship fields (`supersedes: []`, `promoted_to: null`) are list/null-typed and read far more naturally as YAML than as blockquote `> **Key:** value` lines, and the broader Jerry/MADR ecosystem expects YAML ADR frontmatter. The cost of teaching the lint to read YAML (one parser, scoped into M-6) is judged lower than the cost of contorting typed relationship metadata into blockquote form. This is an author judgement, disclosed as such.

**Entity-prefix dialect in a project `decisions/` dir — grandfathered legacy, not a new permitted row (002-001 / CV-001-iter010).** The two `ADR-EPIC002-001/002` files predate this convention and live in `PROJ-001-oss-release/decisions/` — an `EPIC`-prefix dialect in a *project* `decisions/` dir rather than the `work/.../{ENTITY}/` home the Entity-embedded row describes. They are **grandfathered legacy dialect instances on the ratification-time baseline** (per the single authoritative [D-4 exemption rule](#decision)), so L-4 is baseline-exempt on them rather than misfiring. No fresh *permitted* Location Model row is added for this (location, ID-form) pairing: a *new* entity-prefix dialect SHOULD use the `work/.../{ENTITY}/` home or, preferably, a canonical slug from birth. This is disclosed here so the model's coverage of its own corpus is explicit, not implicit.

**Worktracker topology branch (FM-102, iter-3).** Jerry's worktracker SSOT documents **two mutually-exclusive placement topologies** — *project-based* (`projects/{ProjectId}/work/`) and *repository-based* (`{RepositoryRoot}/work/`, the entire repo is the work context) — as a `ONE-OF` choice (`skills/worktracker/rules/worktracker-directory-structure.md:23,36,51-52`, filesystem-verified 2026-07-02). This ADR's own examples all assume the project-based topology, but **downstream plugin adopters (PROJ-031's stated audience) may run the repository-based topology**, in which there is no `projects/PROJ-NNN-*/` prefix. In that topology the canonical ADR home is **`{RepositoryRoot}/decisions/`** and the framework home `docs/design/` is unchanged; the L-4 dialect↔location lint's `projects/PROJ-{NNN}-*/` path assumption is **inapplicable — L-4 has zero operative effect there, not merely degraded (DA-004-iter7)** (a repository-based repo has no such directory, so L-4 is scoped to project-based repos only — see [Enforcement Design](#enforcement-design-l5-ci-lint)). L-1/L-3/L-7 likewise do not reach that topology's `{RepositoryRoot}/decisions/` home (out-of-scan, R-10). The canonical domain-slug form (D-1) is **topology-agnostic** — it works identically under both — which is a further robustness argument for subject-encoding over the project-ID dialect, whose very grammar presumes the project-based tree.

Do **not** introduce `docs/decisions/` (the MADR name the template inherited by accident); the homes above are canonical. Recommended low-effort win: add `docs/design/README.md` as a framework-ADR domain index (BUG-006 F-004, never implemented) and a `docs/adrs/README.md` frozen-legacy banner.

### Testing / verification approach

The convention will be verified by the L5 lint (deterministic; [spec below](#enforcement-design-l5-ci-lint)) **once M-6 ships it — the lint is designed, not yet built, so these checks are advisory today (CC-001, iter-3)** — and by these post-adoption checks: (1) every file in a canonical `decisions/` dir matches the grammar regex; (2) `sort | uniq -d` over extracted canonical **and dialect** IDs is empty (the extraction regex is case-insensitive on the leading token per the iter-6 RT-101 fix, so dialect IDs are included — reconciling this line with the rule draft's L-3 scanned-root scope, `projects/*/decisions/` + `docs/design/`, RT-001-iter7 having replaced an earlier unqualified "Repo-wide"); (3) each `promoted_to`/`superseded_by` target resolves; (4) no *new* bare `ADR-NNN` appears outside frozen dirs.

**Pre-flight collision check (locally runnable, FM-018).** So that collisions are caught *before* commit rather than only post-merge in CI, authors onboarding a new project or minting a new ADR SHOULD run this one-liner (which is also exactly what lint L-3 runs in CI):

```bash
# Lists any {domain-slug}-NNN OR dialect ADR-PROJ{NNN}-NNN identity used by more than one non-frozen ADR.
find projects docs/design -name 'ADR-*.md' \
  \( -path '*/decisions/*' -o -path '*docs/design/ADR-*.md' \) \
  -not -path '*/docs/adrs/*' -not -path '*/docs/archive/*' \
  | sed -E 's#.*/(ADR-.*)\.md#\1#' \
  | grep -E '^ADR-[A-Za-z0-9-]+-[0-9]{3}' \
  | sed -E 's/^(ADR-[A-Za-z0-9-]+-[0-9]{3}).*/\1/' \
  | sort | uniq -d
# Two-clause scan (RT-001-iter9 fix, filesystem-verified 2026-07-06): `*/decisions/*` reaches the 15
# project dialect ADRs; `docs/design/ADR-*.md` reaches the 3 flat canonical framework ADRs (which sit
# directly in docs/design/, NOT under a decisions/ segment) = all 18 reachable. The earlier single
# `-path '*/decisions/*'` returned only 15, silently excluding docs/design/ and contradicting "18 reachable".
# [A-Za-z] (fixed iter-6, RT-101) covers BOTH canonical lowercase slugs AND uppercase-dialect
# prefixes (ADR-EPIC002-001) — the earlier [a-z0-9-] silently dropped every dialect ID.
# Empty output = no collision. Any line printed = a duplicate identity to resolve before commit.
```

## L2: Architectural Implications

- **Promotion becomes a first-class, zero-cost primitive.** By decoupling identity from scope, the framework's central value-delivery mechanism (accrual) stops being a citation-fragile chore and becomes `git mv`. This aligns the ADR lifecycle with Jerry's stated thesis and removes the recurring C4-remediation class of work that BUG-006 represents.
- **Identity stability compounds with corpus size.** The `docs/design/` corpus only grows (nothing is demoted). A convention whose promotion cost is O(1) file-move scales; one whose cost is O(citations) per promotion (A/C) taxes the framework more the more successful it is. This is the systemic reason the one-time migration advantage of C is the wrong axis to optimize.
- **A deliberate, narrow ontology exception is introduced and must be documented as such.** ADRs become the one Jerry entity whose ID encodes subject, not scope — because they are the one entity whose scope is *mutable*. The differentiator is mutability, not literal scope-encoding: `DEC-NNN` already appears bare at Enabler/Story level (`DEC-001-*`, scope supplied by its parent folder), so "every other entity spells scope into its ID" was never strictly true; what *is* true is that every other entity's scope is *fixed*, so its identity can safely omit or embed scope with no migration risk. Left implicit, the ADR exception is an onboarding trap ("why is this one thing different?"). The rule draft (Deliverable 2) makes it an explicit callout: *ADRs encode subject because scope is mutable for them alone.* This is correctly-differentiated design, not inconsistency.
- **Taxonomy governance is the new long-term liability.** B trades the *scope portion's* structural collision-*resistance* (which, per CV-001, was never full freedom — the `NNN` sequence still collided once as `ADR-EPIC002-001`) for a domain-slug taxonomy that must stay coherent (`agent-design` not also `agent-definition`/`agents`). This needs a lightweight index (`docs/design/README.md`) and an arbiter (**TBR-2** — "To Be Resolved" open item 2; the named taxonomy arbiter and its cadence are specified at [M-5b](#migration-plan-from-todays-exact-corpus-state)). This is a *soft* process that can rot; the lint catches collisions but not synonymy. Named here so it is owned, not discovered.
  - **Collision-risk-at-scale estimate (DA-004, explicitly labeled *qualitative order-of-magnitude*, not a measured rate, P-022).** The critic correctly noted that the "compounds/scales with corpus size" claim was asserted without any scale framing, unlike BUG-006's own scale-based severity argument for the scheme it replaces. Honest framing: an *exact* domain-slug collision (`sort | uniq -d` non-empty, caught by L-3) requires two authors to independently choose the *same kebab-case subject slug AND the same `NNN`* — the surface is (# distinct subject taxonomies) × (per-subject sequence depth), which grows only with *thematic* overlap, not raw project count. Going from today's ~18 ADRs to a 50-project / ~150-ADR corpus, the dominant risk is **not** exact collision (L-3 makes it a hard stop) but **synonymy drift** (`agent-design`/`agent-definition`), whose likelihood *does* rise roughly with the number of *independent authors touching the same theme* — plausibly a handful of near-duplicate clusters at 50 projects, not dozens. This is an order-of-magnitude judgement (author inference from the ~18-ADR base rate and the thematic-overlap argument), **not** a quantitatively stress-tested figure; it is offered so the scaling claim is legible and falsifiable rather than hand-waved. It is the reason M-5b (the `docs/design/README.md` synonymy review) is elevated from cosmetic to owned: exact collision is bounded by L-3; synonymy is the risk that actually scales, so it gets an owned human/index check — the automated synonymy lint was descoped in the subtraction pass, so this is a best-effort review, not a CI gate.
- **Future evolution paths remain open.** If promotion later proves rare, the permitted project dialect (D-3) is already the escape hatch — the framework can lean on it without a new ADR. If slug collisions prove painful, the lint can be tightened from warn to fail. If a programmatic ADR index is ever built, subject-encoded IDs are the grep-friendly substrate for it. The decision constrains nothing it does not have to.

## Consequences

### Positive

1. **Promotion is a pure file move** — zero ID-string churn for canonical (domain-slug) ADRs, and therefore zero breakage for the **bare-ID citation majority (grep-measured, DA-001 iter-3: ~72% of ADR citations in `.context/rules/` are bare-ID — 28 of 39; see the [Path 1 caveat](#path-1--canonical-domain-slug-adr-pure-file-move-the-default-zero-churn) for the full ratio)**. (Qualified per that caveat: full-path citations, which a `git mv` does move, are the remaining ~28% — a real, bounded minority, not a single example — a disclosed residual ([R-B, citation staleness](#enforcement-design-l5-ci-lint)) addressed by a manual `grep` sweep, not lint-covered in the 5-rule core.) **Removes the ID-string-churn *cause*** of the demonstrated failure mode (BUG-006's ~150-reference remediation; the still-stale `ADR-PROJ007-001/002` citations, now tasked at M-10) **for that bare-ID majority** — softened from "eliminates" (DA-002-iter7, P-022): the 72%/28% ratio is measured only within `.context/rules/` (scope limitation disclosed at [Path 1](#path-1--canonical-domain-slug-adr-pure-file-move-the-default-zero-churn)), so the full-path/free-text minority is *reduced, not eliminated*, until a real Path-1 promotion measures it repo-wide.
2. **Best-in-class discoverability and sortability** — `grep -r "ADR-agent-" docs/design/` clusters a subject; directory listings sort by domain. Fixes BUG-006 F-001/F-003/F-004 everywhere, not just for the promoted minority.
3. **Provenance preserved by convention (convention-carried, not lint-verified)** — origin lives in frontmatter (`origin_project`/`origin_entity`), satisfying P-004/c-005 without polluting identity. **FM-104 correction (iter-3, P-022):** an earlier draft said "preserved *losslessly*," which over-claims — **no lint in the 5-rule core checks provenance at all** (both the presence and correctness checks were descoped in the subtraction pass), so a copy-pasted or stale `origin_project` value passes undetected. "Lossless" is therefore softened to "preserved by convention": the mechanism carries origin faithfully *when authored correctly*, but nothing guarantees the value is right — the gap is a disclosed limitation mitigated only by authoring discipline, not by a mechanism.
4. **No big-bang migration** — the 3 framework ADRs already comply; the 15 pre-existing project/entity dialect ADRs (16 incl. this ADR) are grandfathered; PROJ-031's set already migrated. Net near-zero forced churn (D-4).
5. **Aligns with the framework's thesis and with external norms** (log4brains slug-as-ID; JPH — Joel Parker Henderson's name-as-ID collection, [References](#references) #12; the accepted BUG-006 Alternative 3).
6. **Graceful under uncertainty** — MEDIUM-tier, reversible, permitted dialect escape hatch; low-regret in either promotion regime.

### Negative (stated honestly, P-022)

1. **Slug-uniqueness is a discipline, not a structural guarantee.** Two authors can independently mint the same domain slug with no error signal until the lint runs. Scope-prefixing (A/C) is *more resistant* to this — the scope portion is uniquely allocated — but **not immune** (CV-001: the `NNN` sequence within a scope family still collided once, `ADR-EPIC002-001`); the difference is one of degree, not of a structural guarantee A/C possesses and B lacks. Mitigated for B by the L5 lint (scanned-root `sort | uniq -d` — `projects/*/decisions/` + `docs/design/`, not repo-wide; out-of-scan classes R-10), but the lint must actually be built and wired into CI before the guarantee is real; until then, enforcement is advisory (see the [lint Claim-Status](#enforcement-design-l5-ci-lint)).
2. **ADRs become the one ontology exception.** New contributors must learn "ADRs encode subject, not scope." A genuine, if small, cognitive cost. Mitigated by an explicit rule-file callout.
3. **Domain-slug taxonomy can sprawl** (`agent-design` vs `agent-definition`). **Precise, RT-009-corrected framing (iter-4, P-022):** the lint's L-3 *hard-blocks* exact-collision duplicate IDs; fuzzy synonymy is **not** lint-checked in the 5-rule core (the synonymy lint was descoped in the subtraction pass), so it rests on a human/index review (M-5b). The accurate statement is: **L-3 hard-blocks exact duplication; synonymy is a human best-effort check (no lint); and neither catches *incorrect reuse of an existing, valid slug* for an unrelated subject** (the distinct DA-004 "slug-squatting" gap, tracked as [R-7](#risks)). Mitigated by a `docs/design/README.md` index + arbiter, which is soft process.
4. **The permitted dialect (D-3) is a hedge that can be abused.** Authors defaulting to `ADR-PROJ*` for decisions that *do* later promote re-create the rename case. Mitigated by SHOULD-guidance to prefer domain slugs and by the promotion process making the rename cost visible.
5. **Two coexisting identity grammars during the grandfather period** raise momentary cognitive load — readers see both `ADR-PROJ010-001` and `ADR-agent-design-001`. Self-liquidating as the corpus grows domain-slug-first.
6. **Slug reuse for an unrelated subject is unenforced (DA-004, iter-4).** Extending an established slug family (`ADR-agent-design-004`) for a subject *unrelated* to prior `agent-design` decisions triggers **no lint** — `NNN` sequencing is exactly what a *legitimate* extension looks like, so a semantically-wrong reuse is indistinguishable at the lint layer from a correct one. This directly threatens the scheme's central discoverability/clustering benefit. Named as unmitigated residual [R-7](#risks); the M-5b arbiter/index review is the only (human, best-effort) backstop.

### Neutral

1. Every ADR already carries a `Created:` date and (for framework ADRs) frontmatter provenance, so the frontmatter additions are incremental, not novel.
2. Location still signals scope (projects/ vs docs/design/) — the ontology's scope-awareness moves from the *identifier* to the *path*, not away entirely.

## Promotion Process (Step-by-Step)

Promotion elevates a project-relevant decision to framework-governing scope. There are **two promotion paths** (below), plus a **Path 0** that graduates an exploratory draft into a canonical home. Grounded in GOV.UK scope-determination + AWS/Nygard immutability + adr-tools link mechanics; the ID-handling specifics are Jerry synthesis (labeled per P-022, `adr-convention-standards-research.md:113,158`).

### Path 0 — Draft → canonical `decisions/` home (graduation, not yet promotion) (FM-005)

An ADR authored in a transient location (`projects/*/orchestration/*/explore/`, or a working `ADR-OSS-NNN`/`adr-*` draft) is **non-canonical** until it lands in a `decisions/` (project) or `docs/design/` (framework) home. To graduate it:

1. **Pick the identity at graduation, not before.** Assign the canonical `ADR-{domain-slug}-NNN` (RECOMMENDED) or, for a purely tactical decision, the `ADR-{PROJECT-ID}-NNN` dialect. This is the moment to choose subject-encoding and avoid a later Path-2 rename.
2. **`git mv`** the draft into `projects/PROJ-NNN-*/decisions/` (or `docs/design/` if already known to be framework-scoped — then Path 0 and Path 1 collapse into a single move).
3. **Add the frontmatter block** (`id`, `scope`, `origin_project`, `created`, …); set `status` appropriately (usually `PROPOSED`).
4. Path 0 has **no tombstone** — a transient draft has no stable prior identity to preserve; it simply acquires its first canonical identity here. (Contrast Path 2, which *replaces* an already-canonical dialect identity and therefore must tombstone.)

### Path 1 — Canonical (domain-slug) ADR: pure file move (the default, zero-churn)

1. **Determine scope.** Promote only when the decision governs the framework broadly (rules/, agents, routing, enforcement, cross-project standards) — GOV.UK "identify the appropriate level."
2. **`git mv`** the file from `projects/PROJ-NNN-*/decisions/ADR-{slug}-NNN-*.md` to `docs/design/ADR-{slug}-NNN-*.md`. **The identifier does not change** — and the human `title-slug` tail SHOULD be **preserved unchanged during the move too (DA-006, iter-3)**, so that any citation written against the *full filename* (not just the bare ID) also survives the promotion; re-slugging the title tail during a promotion is a needless second churn source and is discouraged.
3. **Update frontmatter:** `scope: project` → `scope: framework`. `origin_project`/`origin_entity` are already present and stay.
4. **Bare-ID citations require no re-pointing** — the ID is unchanged, so every citation of the form `ADR-{slug}-NNN` remains valid. This is the core win, and it covers the majority of citations in the corpus. **Caveat, now quantified (P-022; DA-001 iter-3 correction):** a `git mv` *does* change the file's path, so any citation written as a **full relative path** must still be re-pointed. An earlier draft scoped this caveat to "a single external example (`ci.yml`)," which **understated the internal pattern** — the critic (DA-001) correctly flagged that Jerry's own SSOT rule files cite ADRs by full path too (e.g. `.context/rules/mcp-tool-standards.md`, `.context/rules/agent-development-standards.md`, and every References table). **Measured ratio (grep over `.context/rules/`, 2026-07-02):** **28 bare-ID citations vs 11 full-path citations — ≈ 72% bare-ID, ≈ 28% full-path.** Two honest conclusions follow: (a) the finding's implication that full-path is the *dominant* style is **not** borne out — bare-ID dominates roughly 2.5-to-1, so the "majority is bare-ID" claim stands on evidence; but (b) full-path is a **substantial ~28% minority, not a lone `ci.yml` outlier**, so "overwhelming" was an overstatement and the caveat is widened accordingly. Path 1 eliminates *ID-string* churn (the ~72% class, the expensive corpus-wide one) and leaves the ~28% full-path residue as a disclosed residual ([R-B, citation staleness](#enforcement-design-l5-ci-lint)) — a manual `grep` sweep, since free-text/full-path citation scanning is descoped from the 5-rule core. Full-path citations *inside the SSOT rule corpus itself* are retrofit-scoped as [M-11](#migration-plan-from-todays-exact-corpus-state)-adjacent cleanup, not silently edited by this ADR (P-020).

**Scope limitation of the 72%/28% figure (DA-002, iter-4, P-022 — disclosed at the point the figure is cited).** This ratio was measured **only within `.context/rules/`** — a narrow corpus that excludes worktracker entity files (`projects/*/WORKTRACKER.md`), orchestration YAMLs (`projects/*/orchestration/**/*.yaml`), non-markdown config, and the downstream CoWork/plugin distribution audience PROJ-031 exists to serve. The document's own evidence shows full-path citations exist and go stale *outside* that corpus (the dangling `ADR-CI-001` in `.github/workflows/ci.yml:2` was found precisely because it was a full-path citation the `.context/rules/`-scoped measurement would never have counted, see [Context](#context)). **The 72%/28% split therefore cannot be safely generalized repo-wide**; the true full-path share across the whole citation population may be materially higher, which would raise the residual Path-1 churn the manual `grep` sweep must catch (free-text citation scanning is descoped — R-B). **Commitment (paired with M-9 / the first real Path-1 promotion):** (a) extend the citation-ratio measurement beyond `.context/rules/` to at least `WORKTRACKER.md`, orchestration YAMLs, and non-markdown config before M-6 ships, disclosing whatever ratio is found even if it lowers the 72% figure; and (b) instrument the **first genuine Path-1 promotion** (the candidate `ADR-plugin-distribution-001` graduation named in the [Promotion Process](#promotion-process-step-by-step) Claim-Status) as measured evidence — record the actual citation-survival outcome, not just the prediction. Until then, "promotion is free" remains a well-argued *prediction* scoped to a narrow measured corpus, not a repo-wide measurement — an [INHERENT] residual (DA-002/DA-003) that resolves only when a real promotion runs.
5. **(Optional) index:** add a row to `docs/design/README.md`.

**AE-004 scoping of a promotion (FM-103, iter-3; Path-2 clause added FM-003, iter-5, P-022).** A promotion touches a possibly-*baselined* (`ACCEPTED`) ADR, and AE-004 auto-escalates "modifies baselined ADR" to C4 — so the boundary must be stated for **both** paths, not left ambiguous.

- **Path 1 (metadata-only) → C3 floor.** A Path-1 promotion changes only **location** (`git mv`) and the **`scope` field** (`project → framework`); the **decision body is immutable**. A metadata+location transition that does not alter decision content is a *governed lifecycle move* at the **C3** floor — it does **not** trip AE-004's C4, because AE-004 targets changes to a baselined ADR's *decision content*, not its lifecycle metadata.
- **Path 2 (rename + tombstone) → AE-004 auto-C4.** A Path-2 promotion **flips a baselined dialect ADR's `status` to `SUPERSEDED`** and sets `promoted_to` on it — a supersession-class change to a baselined ADR. This **IS subject to AE-004's auto-C4 escalation** (it is the same class of change as any supersession). The companion rule draft states the identical Path-1-C3 / Path-2-C4 split in its [AE-004 scoping](../design/adr-standards-rule-draft.md#promotion-process).
- **Any content change** to a baselined ADR is **not** a promotion at all — it is a supersession (new ADR, per [Amend vs Supersede](#amend-vs-supersede-conventions)), fully subject to AE-004/C4.

This keeps the cheap, frequent operation (metadata-only Path-1 promotion) at C3 while preserving AE-004's teeth for both the thing it guards (content change) and the baselined-status flip a Path-2 promotion performs.

**SSOT-authority disclosure (CC-002-iter7, P-022).** AE-004 as written in `.context/rules/quality-enforcement.md` reads "Modifies baselined ADR → Auto-C4" **unconditionally**. The Path-1 = C3 reading above is **this ADR's own interpretation** — that a metadata-only lifecycle move is not the "modification" AE-004 targets — and is **not yet ratified into the SSOT**. Until a one-line SSOT clarification lands (an [INHERENT] governance action, adjacent to M-4), a strict reading of AE-004 could still class even a Path-1 promotion as C4. Disclosed as this ADR's interpretation pending harmonization, not asserted as settled SSOT.

### Path 2 — Legacy/dialect (`ADR-PROJ*`) ADR: rename + tombstone (the discouraged case)

Used only when a *project-scoped dialect* ADR (D-3) turns out to be framework-worthy. This is the one case with a rename, and its cost is exactly why D-1 recommends domain slugs from birth.

1. **Determine scope** (as above).
2. **Choose a domain slug** and the next `NNN` within it. Author the framework ADR at `docs/design/ADR-{domain-slug}-NNN-*.md`. **Do not mutate the original decision body** (AWS immutability).
3. **Preserve provenance:** new file frontmatter `promoted_from: ADR-PROJ{NNN}-NNN (path)`, plus existing `origin_project`.
4. **Bidirectional back-link (tombstone):** original project ADR → `status: SUPERSEDED` (by promotion) + `promoted_to: ADR-{domain-slug}-NNN`; framework ADR → `promoted_from: ADR-PROJ{NNN}-NNN`. Reuse the template's `Supersedes/Superseded By` fields and the `PROMOTED_FROM/PROMOTED_TO` relationship type.
5. **Re-point citations:** `grep -rl "ADR-PROJ{NNN}-NNN"` deterministically finds every citation site (structured IDs are unique strings); replace with the new domain-slug ID **in live documents only**. **Exclude append-only / historical records (FM-014):** CHANGELOGs, `git` commit messages, release notes, and archived audit logs MUST NOT be rewritten — a reference that was accurate when written is a correct historical record, not a stale citation, and silently editing it falsifies history. The L5 lint's L-7 flags any surviving *structural* relationship reference to a tombstoned ID; free-text/full-path citations are swept manually with `grep` (free-text scanning is descoped from the 5-rule core — R-B), with the same historical-record exclusion.

**Note on why Path 1 dominates:** the empirical failure (BUG-006, the still-stale PROJ-007 citations) is entirely a Path-2 phenomenon. The decision's core contribution is making Path 1 the default so Path 2 is rarely reached.

**Claim-Status: Path 1 is the *designed* default, not yet a *demonstrated* one (DA-003, iter-3, P-022).** Honesty requires stating that **zero Path-1 promotions have actually occurred yet**: every framework ADR to date arrived via a Path-2-style rename (the BUG-006 remediation), and *this very ADR* is itself scheduled for Path 2 (M-9), because it was born under the dialect. So "the default, zero-churn path" describes the **intended** future steady-state, not observed history — the corpus has so far exercised only the discouraged path. Two honest consequences: (a) the "default path" framing is **downgraded to "designed default"** wherever it appears; and (b) the **first genuine Path-1 exercise is a concrete, named future milestone** — the *next* framework-relevant ADR authored *from birth* under a canonical domain slug (a candidate: a future `ADR-plugin-distribution-001` graduating from PROJ-031 into `docs/design/`) will be the first real Path-1 instance and its zero-churn `git mv` should be captured as the confirming evidence. Until that instance exists, Path-1's zero-churn property is a well-argued *prediction*, not a *measurement* — an [INHERENT] residual that resolves only when a future promotion actually runs.

## Amend vs Supersede Conventions

Formalizes the two amendment styles observed ungoverned in the corpus (in-body dated blocks in `ADR-PROJ031-001`; separate amendment files in `docs/adrs/ADR-001-amendment-001`). One style is chosen; the other is deprecated.

| Situation | Mechanism | Identity | Status | Links |
|---|---|---|---|---|
| **Minor clarification / non-reversing update** (decision unchanged) | **In-body dated block** `**AMENDED YYYY-MM-DD:** …` appended to the ADR (the `ADR-PROJ031-001` practice). **Deprecate the separate-amendment-file style.** | Same ID | Stays `ACCEPTED` | `amends`/`amended_by` if cross-ADR |
| **Decision reversal / replacement** | **New superseding ADR** with a new ID; never edit the old decision body (AWS/Nygard immutability). | New ID | Old → `SUPERSEDED`; new → `ACCEPTED` | Old `superseded_by:` ↔ new `supersedes:` |
| **Scope elevation** | **Promotion** (Path 1 or 2 above). | Path 1: unchanged; Path 2: new domain-slug ID | Path 2 old → `SUPERSEDED` (by promotion) | `promoted_from`/`promoted_to` |

Rule of thumb: *amend* preserves the decision and its ID; *supersede* replaces the decision with a new ID; *promote* changes scope (and, for the dialect only, the ID). Numbers are never reused (Nygard; Jerry's tombstone precedent).

**Amendment boundary (FM-010, iter-1; vocabulary aligned to MEDIUM tier per CC-003).** An in-body amendment **SHOULD NOT** change an ADR's `scope`, `origin_project`/`origin_entity`, or canonical location. Those are exactly the properties the [Promotion Process](#promotion-process-step-by-step) governs; mutating them under the guise of a "minor clarification" bypasses the tombstone/back-link machinery and re-creates the citation-break class this ADR exists to prevent. Any change to scope or location **SHOULD** go through Promotion (Path 1 or 2). The strength of the origin-immutability point rests not on tier but on fact: changing `origin_project` is not "overriding a MEDIUM rule with justification," it is **asserting a factual falsehood** — origin is a birth fact, so no justification *can* make it true. Amendments are limited to the decision's *explanatory prose* while the decision, ID, origin, and location stay fixed.

**Honest limit (residual R-C) ([INHERENT] — FM-001 correction, P-022).** An earlier draft claimed "the L-8 citation lint (WARN) surfaces any downstream breakage if the boundary is crossed anyway." **That claim is retracted:** L-8 (descoped from the minimal lint core in any case) detects *stale citations to a moved/renamed ID*, but an **in-place frontmatter mutation of an unmoved file** moves nothing and renames nothing, so no citation goes stale and there is nothing structural for any lint to catch. This boundary therefore rests on SHOULD-NOT guidance and immutability discipline **only** — stated plainly rather than backed by a mechanism that cannot see the violation. **Owner + cadence (FM-009, iter-6):** R-C (and the citation-staleness residual R-B) are reviewed by **governance at each Path-1/Path-2 promotion** — the point at which scope/origin mutation would matter — mirroring M-5b's owner+cadence pattern. The companion rule draft states the same [honest limit](../design/adr-standards-rule-draft.md#supersede-and-amend).

**Supersession-cycle residual (FM-011, iter-6, P-022 — disclosed, not machinery).** No rule in the 5-rule core structurally prevents a supersession cycle (A supersedes B, B supersedes A) or two ADRs both claiming `superseded_by` the same target. The [Status Vocabulary](#status-vocabulary) states the terminal `SUPERSEDED` state does "not transition further," but that rests on SHOULD-NOT discipline, not a lint check — a disclosed residual, not a gap papered over with a cycle-checker. **Concurrent-authorship variant (FM-003-iter8):** the same single-valued `superseded_by` cannot represent *two competing successors authored on separate branches* for one predecessor — a cross-branch concurrent-supersession race that a merge silently resolves last-write-wins, orphaning the other successor. It is the supersession-lifecycle analog of the creation-time race R-6 and is registered as [R-17](#risks); mitigated by PR-review, not lint.

## Status Vocabulary

`PROPOSED | ACCEPTED | REJECTED | DEPRECATED | SUPERSEDED`

| Status | Meaning |
|---|---|
| `PROPOSED` | Under consideration; not in force (default for new ADRs per P-020) |
| `ACCEPTED` | Ratified and in effect |
| `REJECTED` | Considered and declined (added per MADR/AWS; the template lacked it) |
| `DEPRECATED` | No longer applies (e.g., technology sunset) but not replaced by a specific ADR |
| `SUPERSEDED` | Replaced by a specific newer ADR (see `superseded_by`); also the terminal state of a dialect ADR after Path-2 promotion |

The exemplar template currently offers only `PROPOSED | ACCEPTED | DEPRECATED | SUPERSEDED` (`docs/knowledge/exemplars/templates/adr.md:6`); Deliverable 2 specifies adding `REJECTED`.

**Valid status transitions (FM-020).** Statuses are not freely interchangeable; the permitted transitions are:

| From | To | Trigger |
|------|----|---------|
| `PROPOSED` | `ACCEPTED` | Ratified (P-020) |
| `PROPOSED` | `REJECTED` | Considered and declined |
| `ACCEPTED` | `SUPERSEDED` | A specific newer ADR replaces it (`superseded_by` set); also the terminal state of a dialect ADR after Path-2 promotion (`promoted_to` set) |
| `ACCEPTED` | `DEPRECATED` | No longer applies, with no specific replacement |
| `DEPRECATED` | `SUPERSEDED` | A specific replacement is *later* identified for a decision first deprecated without one (see the [forward-link note](#status-vocabulary) below) |
| `REJECTED` | `PROPOSED` | Re-opened for reconsideration (rare; a new consideration cycle) |

**`SUPERSEDED` is the one terminal state** (FM-001-iter7 correction, P-022) — a superseded decision that becomes relevant again is addressed by a *new* ADR, never by reviving the old status (Nygard immutability). `DEPRECATED` is **not** terminal: as the [forward-link note](#status-vocabulary) below spells out, a decision deprecated *without* a specific successor may **later** transition to `SUPERSEDED` if a specific replacement is identified. An earlier draft listed `DEPRECATED` alongside `SUPERSEDED` as "terminal — do not transition further," directly contradicting that handling; the false invariant is deleted here rather than papered over. `PROPOSED`→`DEPRECATED`/`SUPERSEDED` is invalid (an un-ratified decision was never in force to deprecate/supersede).

**On the DEPRECATED/SUPERSEDED forward-link asymmetry (FM-107, iter-3 — rebuttal-with-clarification, P-022).** A reviewer flagged that `DEPRECATED` has no forward-link field (no `deprecated_by`), asymmetric with `SUPERSEDED`'s bidirectional `superseded_by`/`supersedes` (checked by L-7). This asymmetry is **intentional, not a gap**: by the definitions above, `DEPRECATED` means "no longer applies **and is not replaced by a specific ADR**," whereas `SUPERSEDED` means "replaced by a **specific** newer ADR." A DEPRECATED ADR *by definition has no successor to forward-link to* — adding a `deprecated_by` field would contradict the status's own meaning. The correct handling if a DEPRECATED decision *does* later acquire a specific replacement is to use the **SUPERSEDED** relationship (which already carries the bidirectional link and L-7 check), not to bolt a forward-link onto DEPRECATED. So the asymmetry mirrors a real semantic difference (unreplaced vs. specifically-replaced) rather than a missing feature; no `deprecated_by` field is added, and this reasoning is recorded so the asymmetry is understood as deliberate.

**Amendment-block ordering and the combined case (FM-009, FM-011).** When multiple in-body `**AMENDED YYYY-MM-DD:**` blocks accrue, they are appended in **reverse-chronological order (newest first)** under a single `## Amendments` heading, each dated, so the latest clarification is immediately visible. If a single event is *both* a supersession and a promotion (e.g. a dialect ADR is simultaneously replaced and elevated), it is handled as **Path-2 promotion** (which already sets `SUPERSEDED` + `promoted_to`), not as two separate lifecycle events — the promotion tombstone subsumes the supersession, and both `superseded_by` and `promoted_to` point at the same new canonical ID.

## Enforcement Design (L5 CI Lint)

MEDIUM-tier means the lint *reports* and can *fail CI*, but a FAIL is **overridable with a documented justification in the PR** (the standard MEDIUM mechanism, `.context/rules/quality-enforcement.md` Tier Vocabulary) — there is **no waiver ledger, no CODEOWNERS gate, and no "non-bypassable" rule**. **Honesty (PM-002-iter7):** under the current single-`@geekatron`-owner repo that documented justification is *self-approvable* — deleting the waiver ledger removed its structure, not the underlying single-approver condition RT-002/RT-003 named (disclosed as R-12). This is inherent to MEDIUM tier + solo maintenance, disclosed rather than re-gated; the prior disposition table's flat "CLOSED-BY-DELETION" for RT-002/RT-003 is corrected to "closed + residual-disclosed" in the [subtraction-pass notes](../orchestration/adr-convention-20260702-001/subtraction-pass-notes.md). Deterministic, zero-token, no central registry (c-002/c-006), run via `uv run` (H-05) in `.github/workflows/` CI. The authoritative spec is the companion rule draft's [L5 CI Lint Specification](../design/adr-standards-rule-draft.md#l5-ci-lint-specification); this is the ADR-level summary.

> **Claim-Status: the lint is DESIGNED, NOT BUILT (P-022).** As of 2026-07-05, `scripts/lint_adr_convention.py` **does not exist** (Glob-verified). Everything below is an engineered specification. Until the script is implemented, wired into CI, and its grandfather regression test is green (Migration-Plan M-6), **enforcement is advisory-only**: nothing today prevents a non-compliant ADR from merging. The *convention* is nonetheless ratified and in force as MEDIUM-tier guidance — the guidance delivers value with zero tooling; the lint hardens it. This follows the [Claim-Status Convention](ADR-PROJ031-003-credential-protection-supply-chain.md#claim-status-convention-p-022--foundational) precedent (designed-but-unvalidated controls are labeled, never asserted as achieved).

> **Subtraction note (iter-5, P-022).** Iterations 1–4 grew this design from 4 lint rules to 18, plus a waiver ledger, a two-tier ratification gate, and a CODEOWNERS-gated second-reviewer mechanism — and each addition drew new adversarial findings (a false-mitigation L-8 backstop claim, a verified CODEOWNERS gap, a self-waivable control built to prevent unilateral orphaning, and a monolith unbuildable by a solo maintainer). The user-authorized subtraction pass (FEEDBACK-LOG FU.1) **deletes all of that machinery** and keeps a **5-rule fail-closed core**. The enforcement story is now simply *guidance + minimal lint*, and the FAIL override is the standard MEDIUM documented-justification path — no ledger, no second-reviewer gate, nothing self-waivable to exploit.

### Enforcement Scope and Deployment Targets (P0-2 / PM-001)

**The L5 CI lint governs the `geekatron/jerry` SOURCE repository only — by design, not omission.** The sibling Phase-3 skeleton design strips `projects/ tests/ skills/.graveyard .github` (and, as a recommended addition, `docs/`) from every distributed Jerry CoWork/plugin release (`projects/PROJ-031-cowork-skeleton/design/phase3-skeleton-generation-design.md:159,168`; install-validated 2026-07-02). Two consequences follow, and both are stated plainly per P-022:

1. **The CI that runs this lint (`.github/workflows/`) is not present in a plugin install** — `.github` is stripped. A distributed plugin therefore carries *no* copy of the L5 gate.
2. **The `decisions/` corpus the lint validates is also not present** — `projects/` (and recommended `docs/`) are stripped, so a plugin install ships *no* ADR files to lint.

These two facts are **coherent, not contradictory**: ADRs are authored *in the Jerry source repo* (or in an end-user's own downstream project), which is precisely where the CI lives and runs. The plugin skeleton is a *distribution artifact*, not an ADR-authoring surface, so it is correctly outside CI scope.

**Baseline capture procedure — who / where recorded / what changes it (004-002 · 012-005 · 013-002 convergence, iter-010; policy-without-procedure gap closed).** The baseline is not a prose count to be reconstructed from memory when M-6 is eventually built (a real risk given FM-5's "nothing lands" framing). - **Where recorded:** a checked-in data artifact, `scripts/adr-grandfather-baseline-20260705.txt` (one ADR path per line), generated by the two-clause `find` at [L1 Technical Implementation](#l1-technical-implementation); **plus** the ratification commit SHA recorded in this ADR's [Changelog](#changelog). A future M-6 implementer anchors to that pinned artifact/SHA, **not** to a fresh `find` over whatever the working tree contains at build time (which would silently re-anchor to lint-ship-time — the exact amnesty-window defect 012-003 rejected).
- **What changes it:** the file is immutable once captured; a legacy ADR discovered *after* ratification is added to the baseline **only** via a superseding/amending ADR that regenerates the artifact against a newly-pinned commit — never a silent re-scan. Routine future ratifications of *new* ADRs do not touch this baseline: a post-ratification dialect ID passes L-1 on its own merits and a post-ratification bare/numeric-leading ID is correctly held as new.

This makes the anchor **executable, not merely stateable** — data capture + disclosure, no new lint rule (the core stays L-1/L-2/L-3/L-4/L-7).

**Anchoring to ratification, not lint-ship, is deliberate (012-003-iter9, P-022):** because M-6 has no committed ship date (FM-5 rates "nothing lands" the best-evidenced risk) and the dialect stays SOFT-`MAY`-permitted with no expiry, anchoring the baseline to *lint-ship* would sweep every ADR minted in the (possibly long) ratification→lint-ship gap into it *as if pre-existing legacy* — an unbounded, growing post-ratification amnesty window inconsistent with D-4's own "existing/legacy/pre-existing" framing. Fixing the baseline at ratification closes that: a dialect ADR minted after ratification is a *valid dialect* that passes L-1 on its own merits (no grandfather needed), while a bare/numeric-leading ID minted after ratification is correctly held to L-1/L-2 as **new**, not amnestied. A git-modified file that is **already on that baseline** is treated as grandfathered-exempt from L-1/L-2, **not** as a newly-minted ID. This closes the gap the deleted L-12 allowlist previously covered: without it, the numeric-leading legacy `ADR-150-001` (which matches *neither* the canonical nor the dialect grammar) would FAIL L-1 — and risk a false-positive L-2 bare flag — on its very next `git`-modify (a typo fix, or an `AMENDED` block per this ADR's own convention). With the baseline, only files **absent** from it are held to L-1/L-2 as "new," so the "18 files pass L-1" claim is durable across future edits, not merely at the initial dry run. This is a spec-wording clarification of the existing "pre-adoption grandfathered" parenthetical; it adds **no rule** (the core stays L-1/L-2/L-3/L-4/L-7) and no ledger.

**Descoped, honestly (not phased, not committed).** Deliberately out of the minimal core to keep it buildable by a solo maintainer and free of overclaimed coverage: provenance/framework-home WARNs, provenance-correctness checks, **repo-wide free-text citation scanning** (incl. GitHub-Issue citations, full-path citations, non-markdown config), taxonomy-synonymy matching, producer-side drift monitoring, supersession separation-of-duties, repository-topology dialect rejection, and **entity-embedded-ADR scanning** (the `ADR-STORY015-001` out-of-scan case, R-10, iter-6). The citation-scan omission is an **[INHERENT] residual (R-B)** — the core detects only structural frontmatter links (L-7); it does **not** catch stale full-path citations (~28% of `.context/rules/` citations), stale GitHub-Issue references (the FM-006 surface), or an in-place amendment mutation. Path-1's ID-stable move avoids the churn for the bare-ID majority (~72%); a manual `grep`/`gh issue list` sweep (**owner: governance; cadence: at each Path-1/Path-2 promotion**, FM-009 iter-6) is the fallback for the rest. **Scope of "not committed" (DA-005-iter7).** This disclaims *future lint rules* — no descoped check is promised for a later release. It does **not** disclaim the honest *monitoring* commitments (R-6's ≥2-collisions/90-day threshold, R-7 escalation, PM-009's re-examination after 2–3 framework projects): those are a distinct category — named residual-monitoring signals with owners, not lint deliverables — so "no new machinery promised" and "these residuals are watched" are not in tension. None of the above descoped *lint scope* is promised for a later release; if a specific gap causes real pain, a future amendment MAY add a single targeted rule. ## Relationship to Worktracker DEC-NNN (Non-Conflation)

This standard governs **ADRs only**; it does **not** touch the worktracker `DEC-NNN` "Decision File" entity (c-004).

| Property | ADR (this standard) | `DEC-NNN` Decision File |
|---|---|---|
| Purpose | Architecture/design decision record | User↔Claude decision log, co-located with a worktracker parent |
| Identity | Subject (domain-slug), canonical | Parent-scoped composite `{ParentId}--DEC-NNN-slug` at Epic/Feature level (`worktracker-directory-structure.md:65`); **written bare `DEC-NNN-slug` at Enabler/Story level** (`:80,:88` — scope supplied by the parent folder, the very fact the L0/L2 crux-rebuttal leans on). Either way the DEC's scope is permanently fixed. |
| Scope | *Mutable* — can migrate project→framework | *Immutable* — permanently parent-scoped; never migrates |
| Location | `projects/*/decisions/` or `docs/design/` | Typically inside the owning worktracker entity folder (SM-102: not universally — `PROJ-002-roadmap-next/decisions/DEC-001-project-creation.md` shows a DEC file in a project-level `decisions/` dir; the two classes stay separated by the `ADR-` filename prefix the lint keys on, not by a strict per-folder invariant) |

Because a `DEC-NNN` never changes scope, scope-prefixed identity is correct for it (consistent with the whole ontology). Because an ADR does, subject identity is correct for it. **A `DEC-NNN` is not "promoted" into `docs/design/`.** If a worktracker decision rises to architectural significance, a *new* ADR is authored and cross-linked — the `DEC-NNN` is not renamed into an ADR. This keeps the two artifact classes cleanly separated and prevents the standard from leaking into worktracker territory.
