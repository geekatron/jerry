## Summary

The convention's GUIDANCE half (D-1..D-5, ADR-M-001..013) is well-argued, low-regret, and largely closed against prior adversarial rounds. This blind iteration-5 pass targeted the ENFORCEMENT half specifically — "does the L5 lint actually catch it, fail-closed vs advisory, and can promotion/supersession be exploited to orphan or shadow decisions." Eight new attack vectors survive that targeted pass, despite the deliverable's exceptionally thorough self-critique record. **Three are Critical and all three land on the same fault line the deliverable claims to have closed:** (1) the lint's WARN/FAIL split leaves the *exact founding failure mode* (stale cross-corpus citations after promotion) as advisory, not blocking; (2) the two files the entire "audited waiver" narrative depends on are, verified today, absent from `.github/CODEOWNERS` entirely; (3) L-13 — the rule explicitly built to stop "a single self-approved PR flips a trusted ACCEPTED ADR to SUPERSEDED" — is itself a waivable FAIL rule under the disclosed solo-maintainer fallback, and even a compliant second reviewer is never asked to verify that a "superseding" ADR actually addresses the same decision. Recommendation: **REVISE (Tier 2 / enforcement scope only).** Tier 1 (guidance) ratification is not blocked by these findings. Tier 2's own completion gate (G-2, "the L5 lint exists... and its regression test is green") does not currently reference any of RT-001/002/003, so **M-6 as currently scoped could ship "green" while all three Critical gaps remain live** — this is itself the sharpest finding and is called out explicitly in Recommendations.

## Finding Details

### RT-001: L-8 (citation staleness) is WARN, not FAIL — the founding failure mode is not CI-blocking [CRITICAL]

**Attack Vector:** A careless (or hostile) contributor completes a Path-2 promotion or supersession — new file authored, frontmatter set, bidirectional `promoted_to`/`superseded_by` links in place (satisfying **L-7**, FAIL) — but never re-points the wider corpus's prose/path citations to the old ID (skips [Promotion Process](../../decisions/ADR-PROJ031-004-adr-identifier-convention.md#promotion-process-step-by-step) step 5). CI still goes green, because the only check that scans corpus-wide prose/path citations for staleness is **L-8**, and L-8 is explicitly classified **WARN**, not FAIL.
**Category:** Rule Circumvention (compliant in letter — L-7's structural link is satisfied — not in spirit).
**Exploitability:** High — this requires no adversarial cleverness at all, only omission of one optional-feeling step; it is also the exact failure this ADR's own [Context](../../decisions/ADR-PROJ031-004-adr-identifier-convention.md#context) section documents as having *already happened and stayed unrepaired for 2.5 months* (`ADR-PROJ031-004-adr-identifier-convention.md:185` — "stale citations to the extinct `ADR-PROJ007-001/002` IDs still sit in PROJ-007's own `ORCHESTRATION.yaml:228,242`, `WORKTRACKER.md:106-107`, and `EN-001.md:48-49,72-73` as of 2026-07-02").
**Severity:** Critical — the deliverable's entire stated purpose is "promotion becomes a plain file move with no rename and no broken citations" (`ADR-PROJ031-004-adr-identifier-convention.md:73`, L0 Executive Summary). If the one mechanism designed to catch a recurrence of the demonstrated wound is advisory-only, the enforcement design does not actually deliver on the deliverable's central promise; it only prevents the *renamed-ID* half of the wound (via L-7), not the *stale-citation* half, which is the half that is still unrepaired 2.5 months later in the cited evidence.
**Existing Defense:** Partial-to-missing. L-7 (FAIL) catches a broken bidirectional link *between the two ADR files themselves*. L-8 (WARN) is the only check that scans the rest of the repo's prose/paths for stale references, and it is explicitly non-blocking (`ADR-PROJ031-004-adr-identifier-convention.md:696`: "**L-8 Free-text citation scan** | WARN | ..."; identical row in `adr-standards-rule-draft.md:225`).
**Evidence:** `ADR-PROJ031-004-adr-identifier-convention.md:696` (L-8 = WARN), `:695` (L-7 = FAIL, scope limited to the two linked ADR files), `:185` (the still-unrepaired PROJ-007 citations, the demonstrated real-world instance of exactly this failure mode), `:73` (L0 claim "no broken citations"). No line in either deliverable states that L-8's WARN classification means the founding failure mode itself is not CI-blocking — this is a gap the extensive self-critique record does not appear to have surfaced.
**Dimension:** Methodological Rigor (the enforcement design's "fail-closed" framing overstates what actually blocks CI) / Actionability (a contributor has no forcing function to complete citation re-pointing).
**Countermeasure:** Either (a) elevate L-8 to FAIL for the specific sub-case of citations to a file that now carries `status: SUPERSEDED` + `promoted_to`/`superseded_by` (i.e., a *known-tombstoned* ID) — this is a narrower, well-defined FAIL surface than "all stale citations," reducing false-positive risk while closing the exact demonstrated gap; or (b) make completion of citation re-pointing an explicit, checked precondition of the Path-2/supersession PR itself (a review-checklist gate, analogous to the M-9/M-2 atomicity enforcement already specified for the ADR's own self-promotion at `ADR-PROJ031-004-adr-identifier-convention.md:534`).
**Acceptance Criteria:** M-6's regression suite includes a named, individually-asserted fixture (`test_L8_blocks_tombstoned_id_citation` or equivalent) demonstrating that a PR completing a promotion/supersession without re-pointing at least one corpus citation to the now-tombstoned ID **fails CI**, not just warns.

### RT-002: Waiver ledger + grandfather allowlist are absent from `.github/CODEOWNERS` today [CRITICAL]

**Attack Vector:** The entire "audited, non-bypassable-via-unreviewed-comment" override model (`ADR-PROJ031-004-adr-identifier-convention.md:203-211` in the rule draft; `:638-640` in the ADR) rests on a second-reviewer-approval check that is itself gated by `CODEOWNERS`. Verified directly (2026-07-02): `.github/CODEOWNERS` lists exactly four path groups requiring `@geekatron` review — `.github/workflows/`, `.github/dependabot.yml`, `.github/CODEOWNERS`, `.pre-commit-config.yaml`, `.context/rules/`, `docs/governance/` (`.github/CODEOWNERS:8-15`). **`scripts/` is not present in this file at all.** `scripts/adr-lint-waivers.yaml` and `scripts/adr-grandfather-allowlist.txt` — the two files whose "append-only, API-verified-approver" integrity is the entire basis of L-11/L-12 — therefore have **no CODEOWNERS-mandated reviewer today**, meaning (absent some other, undisclosed branch-protection rule) *any* contributor with merge rights, not merely the disclosed "self-approving sole maintainer," could modify them.
**Category:** Boundary Violation — a governance boundary (CODEOWNERS coverage) that the deliverable's own narrative assumes exists but that does not, verified against the live repo.
**Exploitability:** High — no special access or cleverness needed; it is the absence of a control, not the circumvention of one.
**Severity:** Critical — this is *strictly worse* than the disclosed solo-maintainer self-approval gap (PM-102, `ADR-PROJ031-004-adr-identifier-convention.md:674-682`), which at least requires the review to route through the named sole owner. Without a CODEOWNERS entry, the review need not route through anyone in particular. The deliverable's own PM-102 disclosure (point 3, `:682`) names "adding the waiver-ledger path to CODEOWNERS" as an "[INHERENT] staffing/CODEOWNERS change... flagged in Migration-Plan M-6 as a precondition" — but the actual **M-6** migration-plan row (`:531`) does not enumerate this sub-task in its completion criteria ("Implement + wire the L5 CI lint... into CI, with the mandatory 16-file dialect... regression test green plus the L-11/L-12 integrity cases... and the named adversarial fixtures"). There is a live gap between the prose disclosure (which says this is "flagged in M-6") and the M-6 row's actual, checkable gating text (which never mentions CODEOWNERS).
**Existing Defense:** Missing today; disclosed-but-untracked as a gating item for the future.
**Evidence:** `.github/CODEOWNERS:1-16` (full file; no `scripts/` entry); `ADR-PROJ031-004-adr-identifier-convention.md:682` ("adding the waiver-ledger path to CODEOWNERS... flagged in Migration-Plan M-6 as a precondition"); `:531` (the M-6 row itself, no CODEOWNERS sub-task listed).
**Dimension:** Internal Consistency (the "audited" framing is asserted for a mechanism whose access-control precondition is verifiably absent) / Traceability (the PM-102 prose disclosure and the M-6 gating row do not cross-reference each other, so the precondition is easy to lose track of).
**Countermeasure:** Add an explicit M-6 sub-criterion: "`.github/CODEOWNERS` includes `scripts/adr-lint-waivers.yaml` and `scripts/adr-grandfather-allowlist.txt` under the `@geekatron` (or successor governance-owner) pattern, verified present in the same PR that lands the lint script." This converts an easy-to-lose prose cross-reference into a checkable G-2 gate item.
**Acceptance Criteria:** G-2's evidence requirement (green CI run link) is amended to also require a diff showing the CODEOWNERS addition, reviewed in the M-6 PR itself.

### RT-003: L-13 separation-of-duties is itself self-waivable; no semantic correspondence check protects against a compliant-but-inattentive second reviewer [CRITICAL]

**Attack Vector:** L-13 is explicitly designed to close "the orphan/shadow exploit: a single self-approved PR flips a trusted `ACCEPTED` ADR to `SUPERSEDED`" (`ADR-PROJ031-004-adr-identifier-convention.md:702`, Rejects column, verbatim). But L-13 is itself listed as "**FAIL (waivable-in-principle; see tier reconciliation)**" (`:702`), meaning it is subject to the *same* structured-waiver mechanism as every other FAIL rule, including the disclosed `solo_maintainer: true` fallback (`:674-682`). Under the verified single-`@geekatron`-CODEOWNERS reality, the one rule built specifically to prevent "a single [actor]... flips a trusted ACCEPTED ADR" can be defeated by that same single actor waiving their own L-13 finding with a boilerplate ≥40-character justification and the `solo_maintainer` flag. Separately and independent of the solo-maintainer gap: even where a *bona fide* distinct second reviewer approves the supersession (satisfying L-13's separation-of-duties check as written), nothing in L-7 or L-13 verifies that the "superseding" ADR's *decision content* actually corresponds to the ADR it claims to replace — both checks are purely structural (do the IDs resolve? does a distinct identity appear in the approver list? is there a Changelog entry?), never semantic. A reviewer who approves without carefully reading both documents — plausible under normal review fatigue, and not defended against by any part of the spec — would let a decoy or unrelated "superseding" ADR through cleanly.
**Category:** Rule Circumvention (the disclosed self-waiver path) compounded by a Dependency Attack (the un-stated dependency on reviewer diligence for the semantic-correspondence gap).
**Exploitability:** Medium — the solo-maintainer path requires only what any FAIL-rule waiver already requires (already disclosed as a broad gap for L-1..L-14); the semantic-correspondence gap requires either collusion or ordinary reviewer inattention, both plausible.
**Severity:** Critical — this is the deliverable's own named answer to "can this be exploited to orphan/shadow a decision," and under the currently-verified repo state, that answer's central control (separation of duties) collapses to the same self-waivable status as a routine lint nit. The broader "every FAIL rule is self-waivable under solo-maintainer" fact is already disclosed generically (`:638`, IN-005/RT-002); what is not stated anywhere in either deliverable is the specific conclusion that **the one rule purpose-built to prevent unilateral orphaning/shadowing inherits that exact same weakness**, nor is the independent semantic-correspondence gap (which persists even with a compliant second reviewer) disclosed at all.
**Existing Defense:** Partial. Structural link integrity (L-7) and reviewer-identity distinctness (L-13) are real, useful checks; they are just not sufficient on their own for the specific class of attack this ADR names as the thing L-13 exists to stop, given the current repo state.
**Evidence:** `ADR-PROJ031-004-adr-identifier-convention.md:702` (L-13 definition and "Rejects" column naming the orphan/shadow exploit; also marked "FAIL (waivable-in-principle...)"); `:638` (generic self-waivable-under-solo-maintainer disclosure covering "every FAIL-class rule (L-1...L-14)"); `:674-682` (solo-maintainer fallback mechanics); `adr-standards-rule-draft.md:231` (identical L-13 row).
**Dimension:** Methodological Rigor (the control's stated purpose and its actual current-state strength diverge) / Internal Consistency.
**Countermeasure:** (a) Explicitly exclude L-13 from the `solo_maintainer` fallback — i.e., state that a supersession/orphaning event on an `ACCEPTED` ADR **cannot** be waived via the solo-maintainer path even though other FAIL rules can, given the asymmetric blast radius of an incorrect supersession vs. a naming nit; this requires a true second reviewer to exist before any supersession of an `ACCEPTED` ADR can land, which is a stronger and more defensible posture than treating it identically to a slug typo. (b) Add a required, human-completed `content_correspondence_summary` field to the Changelog entry L-13 already mandates, naming specifically what changed and why the new ADR addresses the same decision — this does not make review substance-checking automatic, but it forces an explicit claim that a later audit can falsify.
**Acceptance Criteria:** L-13's spec states an explicit non-waivability carve-out (distinct from L-2/L-3's "waivable-in-principle-but-never-constructable" logic, which is not equivalent here because the harm/reversibility profile differs), and the Changelog-entry requirement is extended with the correspondence-summary field.

### RT-004: No content/subject-level duplicate-decision detection — a shadow ADR via a deliberately dissimilar new slug is invisible to every lint rule [MAJOR]

**Attack Vector:** **L-3** (slug-uniqueness) only catches an *exact* `{slug}-NNN` string collision (`ADR-PROJ031-004-adr-identifier-convention.md:689`). **L-10** (taxonomy synonymy) only fuzzy-matches the *slug string itself* against other slug strings (`:698`) — it never inspects decision *content*. **L-13** (supersession legitimacy) only fires when a PR explicitly sets `status: SUPERSEDED`/`superseded_by`/`promoted_to` on a pre-existing `ACCEPTED` ADR (`:702`). None of these three checks fires if a contributor simply authors a brand-new ADR under a deliberately *dissimilar* domain slug (e.g., `ADR-skill-dispatch-001` shadowing an existing, unrelated-sounding `ADR-agent-routing-003`) that makes a competing or contradictory decision on the same real-world topic, and never links the two via `supersedes`/`superseded_by` at all. This is a distinct gap from the already-disclosed **R-7** risk (`:475`, "slug reuse for an unrelated subject" — extending an *existing* slug family with an unrelated `NNN`); RT-004 is the mirror case — a *brand-new* slug deliberately chosen to *avoid* triggering L-10's fuzzy-match against the topic it actually competes with.
**Category:** Ambiguity Exploitation — nothing in the standard defines an obligation to declare or check "relatedness to existing decisions on the same subject" before authoring a new ADR.
**Exploitability:** Medium — requires the author to deliberately pick a dissimilar slug, but this is a trivial, undetectable-by-tooling action (there is no mechanism that would even flag it for human review, unlike R-7 which at least sits inside an existing, arbiter-reviewed slug family per M-5b, `:530`).
**Severity:** Major — this directly threatens governance integrity (two ACCEPTED decisions can silently contradict each other with no cross-link, no tombstone, and no lint signal) but does not by itself invalidate the naming/promotion mechanics the ADR is chiefly about; hence Major rather than Critical.
**Existing Defense:** Missing. The `docs/design/README.md` domain index + M-5b arbiter (`:530`) is the only backstop, and it is scoped to *slug* review (is this a synonym of an existing slug?), not *content* review (does this decision duplicate/contradict an existing one under an unrelated-looking slug?).
**Evidence:** `ADR-PROJ031-004-adr-identifier-convention.md:689` (L-3, exact-ID only), `:698` (L-10, slug-string fuzzy match only), `:702` (L-13, fires only on explicit status transitions), `:475` (R-7, the adjacent-but-distinct "same family, wrong subject" risk).
**Dimension:** Completeness (the 5-attack-vector enumeration in this very lint spec has no category for "undeclared competing decision") / Internal Consistency (two ACCEPTED ADRs could assert incompatible governance without any structural signal).
**Countermeasure:** Add a lightweight authoring-time obligation (MEDIUM, WARN-tier, consistent with the convention's own tier posture) requiring a new ADR's frontmatter or body to declare a `related_to: []` list of any existing ADRs on adjacent subjects the author is aware of, checked only for *presence of the field*, not correctness (mirroring L-6c's presence-only pattern for `scope`); pair with an M-5b arbiter cross-check at authoring time that greps the new ADR's title/body against the domain index for topic keyword overlap, not just slug-string overlap.
**Acceptance Criteria:** A new lint rule (proposed L-15, WARN) flags a newly-added ADR whose body shares a defined keyword-overlap threshold with an existing ACCEPTED ADR's body/title but declares no `related_to` entry and sets no `supersedes` link.

### RT-005: Waiver `expires` field has no maximum bound — a "temporary" exception can be made permanent by construction [MAJOR]

**Attack Vector:** Every FAIL-rule waiver requires an `expires` field ("a review-by date," `adr-standards-rule-draft.md:203`), and L-11 re-checks that "a waiver whose `expires` date has passed stops suppressing its target rule" (`:207`, `ADR-PROJ031-004-adr-identifier-convention.md:699`). Neither deliverable specifies any maximum span for `expires`. Combined with the already-disclosed solo-maintainer self-approval fallback (`:674-682`), a single actor can self-waive any FAIL rule — including the collision rules L-2/L-3 and the supersession-legitimacy rule L-13 — with a structurally-valid, ledger-compliant entry whose `expires` date is decades out, converting what the design frames as a "temporary, reviewed" exception into a de facto permanent bypass that still reports as "compliant" (append-only, all required fields present, not yet expired).
**Category:** Rule Circumvention — the ledger's formal completeness requirements are satisfied in letter while defeating the "temporary" premise in spirit.
**Exploitability:** High — setting an arbitrary date requires no special technique.
**Severity:** Major (not Critical) — it compounds the already-disclosed solo-maintainer weakness rather than introducing a wholly independent bypass path; it does not on its own create a new attack surface, but it removes the one property (time-boundedness) that would otherwise force periodic re-justification.
**Existing Defense:** Partial. The ledger's structure (append-only, API-verified approver where a second reviewer exists, expiry re-check) is real; only the *bound* on the expiry value is missing.
**Evidence:** `adr-standards-rule-draft.md:203` (six required waiver fields, `expires` = "a review-by date," no bound stated), `:207` (expiry re-check mechanics, no bound stated), `ADR-PROJ031-004-adr-identifier-convention.md:699` (identical L-11 definition in the ADR's own summary table).
**Dimension:** Actionability (the acceptance criteria for a "compliant" waiver do not constrain the one field that determines how long an exception can silently persist).
**Countermeasure:** Cap `expires` at a fixed maximum span from `date` (e.g., 90 days, mirroring the 90-day rolling-window threshold already used elsewhere in this same document for the R-6 escalation trigger, `:480`); require re-justification (a fresh ledger entry, not an edit — preserving append-only) for renewal, so a still-live exception is visible as a growing chain of entries rather than one distant date.
**Acceptance Criteria:** L-11's lint check additionally rejects any waiver entry whose `expires` date exceeds `date + 90 days` (or whatever bound is ratified) unless `solo_maintainer: true` renewal history is present and itself capped in count.

### RT-006: Topology detection (project-based vs. repository-based) mechanism is never specified — a possible L-4/L-4b gap [MAJOR]

**Attack Vector:** The standard defines two mutually-exclusive worktracker placement topologies and states that L-4 (dialect↔location check) applies "under the project-based topology" while **L-4b** rejects any dialect ID outright "under the repository-based topology" (`ADR-PROJ031-004-adr-identifier-convention.md:690-691`). Neither this ADR nor the companion rule draft (`adr-standards-rule-draft.md:219-220`) specifies **how the lint determines which topology is in effect** for a given repository or PR (no config flag, no directory-existence heuristic, no declared field is named). If topology detection is implemented as an implicit heuristic (e.g., "does `projects/PROJ-NNN-*/` exist anywhere"), a repo in a transitional or mixed state — or a hostile contributor who creates a single stray `projects/` directory not actually used as a worktracker root — could cause the lint to select the wrong topology branch, or select neither, letting a misfiled dialect ADR escape both L-4 and L-4b.
**Category:** Ambiguity Exploitation.
**Exploitability:** Medium — requires either a genuinely mixed repo state (plausible during any migration) or a deliberate stray directory; either way, no part of the spec defines the detection logic to evaluate against, so this cannot currently be verified closed or open.
**Severity:** Major — this is a specification gap in the mechanism meant to enforce ADR-M-003/ADR-M-007's location rules, not a demonstrated live exploit, and Jerry's own repo today is unambiguously project-based (so the immediate blast radius is low); it is rated Major rather than Minor because the standard explicitly names two topologies as first-class and PROJ-031's own stated downstream audience (plugin/CoWork adopters) is exactly the population likely to run the repository-based topology where this ambiguity would first surface.
**Existing Defense:** Missing — no detection mechanism is named in either deliverable.
**Evidence:** `ADR-PROJ031-004-adr-identifier-convention.md:406-407` (topology branch description, no detection method), `:690` (L-4, "Applies under the project-based topology"), `:691` (L-4b, "Under the repository-based topology... rejected outright"); `adr-standards-rule-draft.md:219-220` (identical rows). No line in either file specifies a detection mechanism (grep-verified absence: no match for "detect" + "topology" co-occurrence in either deliverable).
**Dimension:** Completeness.
**Countermeasure:** Require an explicit, declared repo-level marker (e.g., a `worktracker_topology: project-based | repository-based` key in a repo-root config file, or reuse of an existing worktracker SSOT declaration if one exists) that the lint reads deterministically, rather than inferring topology from directory presence/absence.
**Acceptance Criteria:** The lint spec names the exact config key/file it reads to select L-4 vs. L-4b, and the M-6 regression suite includes a fixture asserting correct branch selection for both topologies plus a defined (fail-closed, not fail-open) behavior when the marker is absent.

### RT-007: L-1a entity-prefix lookalike enum is a hardcoded, unsynced second copy of the worktracker entity vocabulary [MINOR]

**Attack Vector:** L-1a's protection against a lowercase entity-prefix look-alike masquerading as a domain slug (e.g., rejecting `ADR-proj031-001` or `ADR-bug006-001`) is implemented as a hardcoded closed enum: `^(proj|epic|feat|story|enabler|en|bug|task|spike|disc|imp|dec)\d+$` (`ADR-PROJ031-004-adr-identifier-convention.md:686`; identical at `adr-standards-rule-draft.md:73`). This list is a second, independently-maintained copy of (a subset of) the worktracker entity-type vocabulary, not derived from the worktracker SSOT (`skills/worktracker/rules/worktracker-entity-hierarchy.md`). That SSOT's entity hierarchy includes `Initiative` and `Capability` (portfolio/solution-level entities, `worktracker-entity-hierarchy.md:26-33`) and `Subtask` (`:46`), **none of which appear in the lookalike-exclusion enum.** A careless (or hostile) contributor could mint `ADR-initiative042-001.md` or `ADR-capability007-001.md` as an apparent "domain slug," and L-1a's lookalike filter would not catch it (it is not in the enum), while L-1b would also not recognize it as a valid dialect (closed set is `{PROJ|EPIC|FEAT|STORY}` only) — the ID would likely pass L-1a as a bare "domain slug" it is not.
**Category:** Dependency Attack — an unacknowledged dependency on a vocabulary that can drift without a corresponding lint update, exactly the pattern the deliverable's own FM-002 (`:636`) discloses for the ADR-vs-rule-draft table duplication, but applied to a different pair (lint enum vs. worktracker SSOT) that carries no equivalent disclosure or parity check.
**Exploitability:** Low-Medium — requires either a future worktracker ontology change (plausible; the ontology has already grown, per the hierarchy file) or an author already aware of the gap.
**Severity:** Minor — the practical blast radius today is small (no live `Initiative`/`Capability`-prefixed ADR exists), but it is a real, currently-verifiable drift risk with no disclosed mitigation.
**Existing Defense:** Partial — the enum exists and covers the currently-dialect-eligible prefixes (`PROJ|EPIC|FEAT|STORY`) plus several non-dialect worktracker types; it simply is not exhaustive against the full, evolving entity vocabulary and carries no sync mechanism.
**Evidence:** `ADR-PROJ031-004-adr-identifier-convention.md:686` (the lookalike enum); `skills/worktracker/rules/worktracker-entity-hierarchy.md:26-33,46` (`Initiative`, `Capability`, `Subtask` entity types not present in the enum).
**Dimension:** Traceability (the enum's coupling to the worktracker ontology is real but unacknowledged and unmonitored).
**Countermeasure:** Either generate the lookalike-exclusion list programmatically from the worktracker entity-hierarchy SSOT at lint-build time, or add an explicit disclosed-drift note (parallel to FM-002's dual-table note at `:636`) naming this as a second synchronization obligation, with a regression-test assertion that the enum's prefix set is a superset of all current worktracker entity-type abbreviations.
**Acceptance Criteria:** M-6's regression suite includes a fixture that fails if the worktracker entity-hierarchy file's entity-type list contains an abbreviation not present in the L-1a lookalike enum.

### RT-008: L-8's `<!-- adr-lint: example -->` exemption tag is unaudited, unlike the FAIL-rule waiver ledger [MINOR]

**Attack Vector:** L-8's exemption model lets any citation escape the (already WARN-only, per RT-001) stale-citation scan by appearing inside a fenced code block, on a line tagged `<!-- adr-lint: example -->`, or on a "known-stale-example allowlist" (`ADR-PROJ031-004-adr-identifier-convention.md:696`). Unlike the FAIL-rule waiver ledger — which requires a >=40-character justification, an API-verified distinct approver (or disclosed solo-maintainer fallback), and an expiry date (`:638`, `:674-682`) — the `adr-lint: example` tag carries **no review requirement, no expiry, and no audit trail**. Any contributor can add this tag next to a genuinely stale (not merely illustrative) citation to silence it permanently, with strictly less governance than applies to any FAIL rule.
**Category:** Degradation Path — an advisory control that erodes to zero over time because its own suppression mechanism is ungoverned.
**Exploitability:** High — adding an HTML comment requires no special access.
**Severity:** Minor — bounded by the fact that L-8 is already WARN-only (RT-001), so this finding is a compounding factor on an already-disclosed-as-Critical primary gap rather than an independent path to a Critical outcome; it is flagged separately because it undermines even the *informational* value WARN-tier still nominally provides.
**Existing Defense:** Partial — the exemption exists for a legitimate purpose (this ADR's own text intentionally cites known-stale examples like `ADR-PROJ007-001/002` and `ADR-CI-001` as evidence, and should not self-trigger, per IN-003's fix at `:696`), it simply has no governance calibrated to its risk of misuse for illegitimate suppression.
**Evidence:** `ADR-PROJ031-004-adr-identifier-convention.md:696` (L-8 exemption definition, no review/expiry/audit language); `:638` and `:674-682` (the contrasting, audited waiver-ledger model applied to FAIL rules).
**Dimension:** Evidence Quality (a WARN signal that can be silently and permanently suppressed with zero review provides materially weaker evidentiary value than the document's framing implies).
**Countermeasure:** Require the `adr-lint: example` tag to be paired with a one-line inline rationale (`<!-- adr-lint: example — cited as a known-stale illustration, see References #N -->`) and add a lightweight (not full-ledger) CI check that any use of the tag appears within a References-cited "known example" context, not an arbitrary location.
**Acceptance Criteria:** L-8's regression fixture set includes a case asserting the tag is rejected (or flagged for a second WARN) when it appears adjacent to a citation with no corresponding References-section disclosure.
