## Detailed Findings

### CC-001-20260626: P-042 Risk Format Violation — No 5×5 Numeric Scoring [MAJOR]

**Principle:** P-042 (Risk Transparency) — "Apply 5×5 risk matrix scoring (Likelihood × Consequence). Classify risks as RED (>15), YELLOW (8-15), or GREEN (<8)."
**Applies to:** `phase1-requirements.md` (NSE-agent output); P-042 is scoped to NSE-agent outputs
**Location:** `phase1-requirements.md`, L2 Systems Perspective → Risk Implications table
**Evidence:**

```
| R-001 | ... | CoWork limit applies to local working directory ... | M × Critical | Stated Assumption R-001 ... |
| R-005 | ... | CI loop ...                                        | L × High     | Three independent guarantees ... |
| R-007 | ... | Supply-chain: CI compromised ...                   | L × Critical | REQ-022 requires verifiable equivalence ... |
```

**Analysis:** P-042 requires numeric 5×5 scoring and RED/YELLOW/GREEN classification. The table uses qualitative shorthand ("M × Critical", "L × High") with no numeric Likelihood or Consequence values. Consequence categories ("Critical", "High", "Medium") are not mapped to a numeric scale. Without numeric scores, no RED/YELLOW/GREEN classification is possible, and R-001 — which at Medium Likelihood (≈3) × Critical Impact (≈5) yields 15, placing it exactly on the YELLOW/RED boundary — is not escalated. P-042 also requires "Escalate RED risks immediately to user attention"; the ambiguous boundary cannot be automatically escalated. The risk content is substantively complete; only the mandated format is missing.

**Remediation:** Replace qualitative risk notation with 5×5 numeric values. Define the scales (e.g., Likelihood 1=Rare … 5=Almost Certain; Consequence 1=Negligible … 5=Critical). Recalculate each risk score numerically. Add a RED/YELLOW/GREEN column. For R-001 (estimated 3×5=15), explicitly classify as YELLOW or RED and escalate to user attention per P-042.

### CC-002-20260626: P-040 Traceability Gap — STK-003 H-04 Bootstrap Not Traced to Documentation [MAJOR]

**Principle:** P-040 (Requirements Traceability) — "Trace requirements to design/test artifacts (downward traceability). Alert when orphan requirements or missing traces are detected."
**Applies to:** `phase1-requirements.md` (NSE-agent output)
**Location:** `phase1-requirements.md`, Traceability Summary + WS-4 Documentation Requirements
**Evidence (Traceability Summary as written):**

```
STK-003 (Bootstrap / H-04 on fresh install)
  └── REQ-004  projects/README.md sentinel file
  └── REQ-005  seven plugin directories intact
  └── REQ-009  .claude/rules and .claude/patterns symlinks resolve
  └── REQ-010  plugin.json agent paths resolve
```

STK-003 states: "A fresh install of the plugin must be immediately usable: H-04 bootstrap (active-project requirement) and SessionStart hook must function from the first session." All four downward traces from STK-003 are WS-1 technical requirements verifying the generated skeleton artifact. Zero traces lead to any WS-4 documentation requirement.

**Analysis:** STK-003's "immediately usable" scope encompasses both (a) the technical skeleton structure (REQ-004/005/009/010 — addressed) and (b) the user experience of encountering H-04 on first launch with no projects. When a CoWork user installs the skeleton, `jerry projects list` will return "No projects found." The SessionStart hook emits `<project-required>`, and the CLAUDE.md spec calls for using AskUserQuestion to guide project creation. However, no WS-4 documentation requirement currently requires any Tutorial or How-To guide to cover this first-time project creation flow. REQ-026 scopes the Tutorial to the installation command only; REQ-024 scopes it to "install Jerry in CoWork." A user who successfully installs but cannot identify what to do next (create their first project via `/worktracker`) is not immediately usable. The P-040 bidirectional trace is incomplete: STK-003 → WS-4 is missing.

**Remediation:** Add a requirement (e.g., REQ-024a or an addition to REQ-026) stating: "The Tutorial SHALL include a step covering the H-04 bootstrap experience on first launch — specifically, what the user should do when no active project exists (run `jerry projects list`, then use the `/worktracker` skill or `jerry session start` to create their first project)." Update the Traceability Summary to add `STK-003 → REQ-024a`.

### CC-003-20260626: Internal Consistency Defect — ADR-001 Plugin Surface vs. REQ-005 [MAJOR]

**Principle:** P-011 (Evidence-Based Decisions) — decisions must be consistent with stated evidence; also affects Internal Consistency (S-014 dimension)
**Location:** `ADR-001-skeleton-derived-branch-strategy.md` constraint c-003 + Consequences; `phase1-requirements.md` REQ-005
**Evidence:**

ADR-001, constraint c-003:
> "The installed artifact (tip tree) MUST be plugin-install compatible: `.claude-plugin/`, `skills/`, `commands/`, `.claude/`, `.context/`, `hooks/` intact."

ADR-001, Consequences (Positive):
> "Full plugin surface preserved — stripping only `projects/` leaves `.claude-plugin/`, `skills/`, `commands/`, `.claude/`, `.context/`, `hooks/` intact, keeping `ci.yml` plugin-validation green."

REQ-005:
> "The skeleton generation script SHALL verify that the following seven directories are present in the generated branch tree after stripping: `.claude-plugin/`, `skills/`, `.claude/`, `.context/`, `src/`, `schemas/`, `hooks/`."

**Analysis:**

| Directory | In ADR-001 c-003 | In REQ-005 |
|-----------|-----------------|------------|
| `.claude-plugin/` | Yes | Yes |
| `skills/` | Yes | Yes |
| `commands/` | **Yes** | **No** |
| `.claude/` | Yes | Yes |
| `.context/` | Yes | Yes |
| `hooks/` | Yes | Yes |
| `src/` | **No** | **Yes** |
| `schemas/` | **No** | **Yes** |

The two documents define the plugin surface differently. If `commands/` is part of the plugin surface (ADR-001), then REQ-005 fails to verify its presence and a regression silently removing `commands/` would not be caught by the generation script. Conversely, `src/` and `schemas/` appear in REQ-005 but not in ADR-001's plugin surface definition, which may indicate REQ-005 is checking non-plugin directories. Neither document is clearly authoritative about what constitutes the complete, correct plugin surface.

**Remediation:** Align the plugin surface definition across ADR-001 and REQ-005. The authoritative source should be the `.claude-plugin/plugin.json` manifest (which REQ-010 already validates agent paths from). Enumerate all directories that contain files referenced by `plugin.json` or required by the plugin loader. Update both ADR-001 c-003 and REQ-005 to use the same consistent, exhaustive list. If `commands/` exists in the repo, add it to REQ-005. If `src/` and `schemas/` are not plugin-surface directories, document why REQ-005 verifies them separately.

### CC-004-20260626: R-007 Threat Scope Incomplete — Direct Branch Push Not Named [MINOR]

**Principle:** P-042 (Risk Transparency) — risk descriptions should cover distinct threat actors
**Location:** `phase1-requirements.md`, Risk Implications table, R-007 row
**Evidence:**
> `R-007 | ... | Supply-chain: CI compromised; malicious content injected into cowork-skeleton and installed by CoWork users | L × Critical | REQ-022 requires verifiable equivalence; REQ-017 SHA-pins Actions; REQ-012/NFR-004 least-privilege token`

**Analysis:** R-007's phrasing leads with "CI compromised" — an attacker who has subverted the GitHub Actions pipeline. The mitigations (SHA-pinned Actions per REQ-017, least-privilege GITHUB_TOKEN per REQ-012) directly address CI pipeline threats. However, a repository collaborator with push access could push malicious content directly to the unprotected `cowork-skeleton` branch without compromising CI at all. This is a distinct threat: it bypasses REQ-017 (SHA pinning applies only to the workflow, not to direct git pushes) and REQ-012 (GITHUB_TOKEN is the CI credential, not a gatekeeping mechanism for other contributors). REQ-022's post-run equivalence check only fires after the next CI run, leaving a detection gap until the next `v*` tag. ADR-002 acknowledges the unprotected posture but does not trace this specific threat vector back to R-007. The risk is LOW likelihood (requires repo write access and deliberate malice), so the severity assessment is not wrong, but the threat model should be explicit.

**Remediation:** Expand R-007's risk description to: "Supply-chain: (a) CI compromised — malicious content injected via workflow; (b) repository collaborator with push access pushes malicious content directly to unprotected `cowork-skeleton` branch between CI runs." Confirm the mitigations address both sub-vectors (they partially do: the detection gap for sub-vector b is acknowledged in ADR-002 and accepted by design, but should be documented in R-007's mitigation column).

### CC-005-20260626: H-05 Gap in Acceptance Criteria — `jerry` Without `uv run` [MINOR]

**Principle:** H-05 (UV-only Python) — "MUST use `uv run` for all Python execution. NEVER use `python`, `pip`, or `pip3` directly."
**Location:** `phase1-requirements.md`, multiple WS-1 and WS-3 acceptance criteria
**Evidence:**

```
| REQ-004 | On a clean clone of `cowork-skeleton`: `git ls-files projects/README.md` returns non-empty;
           `jerry projects list` exits 0 and prints "No projects found." |
```

Additional instances: REQ-006 AC ("confirm the script exits non-zero"), REQ-010 AC reference to plugin.json path resolution — these reference `jerry` indirectly via the script behavior.

**Analysis:** The Jerry CLI is a Python application invoked via `uv run jerry <subcommand>`. H-05 is unconditional: every Python execution MUST go through `uv run`. Acceptance criteria text that names `jerry projects list` without `uv run` will teach testers and implementers an H-05-violating invocation pattern. If any Phase 3 (STORY-003) acceptance test scripts are derived directly from these acceptance criteria, they will invoke `jerry` through the system Python path rather than the UV virtual environment, constituting an H-05 violation at implementation.

**Remediation:** Update all acceptance criteria that reference Jerry CLI invocations to use `uv run jerry <subcommand>`. Specifically: REQ-004 AC → "…`uv run jerry projects list` exits 0 and prints 'No projects found.'". Add a cross-reference note in WS-5 (REQ-030) or the quality checklist that V&V test scripts MUST use `uv run jerry` for any CLI invocation.

### CC-006-20260626: P-022 Constraint Missing on Stub Content [MINOR]

**Principle:** P-022 (No Deception) — agents SHALL NOT deceive users; content shipped to end users must not mislead
**Location:** `ADR-001-skeleton-derived-branch-strategy.md`, Regeneration Commit Determinism section; `phase1-requirements.md`, REQ-004
**Evidence:**

ADR-001: "Stub determinism constraint (c-001/c-006): the stub `projects/README.md` MUST be static content. Any generated date, version string, or run ID inside it changes the tree and breaks reproducibility. Authoring is STORY-002; this ADR fixes only its determinism property."

REQ-004 acceptance criterion: "On a clean clone of `cowork-skeleton`: `git ls-files projects/README.md` returns non-empty; `jerry projects list` exits 0 and prints 'No projects found.'"

**Analysis:** ADR-001 and REQ-004 constrain stub content to "static" (for determinism) and "exists" (for REQ-004 acceptance). Neither document imposes a P-022 constraint on what the stub is permitted to say. A `projects/README.md` stub that says, for example, "No projects created yet" could mislead a CoWork user into thinking they have already attempted project creation, when in fact they have not. Worse, a stub that describes the skeleton branch as if it were the user's development environment could confuse the installation context. Because STORY-002 authors the stub content with no P-022 guardrail from the requirements, this deception risk is unmitigated at the planning level.

**Remediation:** Add a content constraint to REQ-004 or create REQ-004a: "The `projects/README.md` sentinel file SHALL contain a clear, non-deceptive explanation (per P-022) of its role as a placeholder stub for the skeleton branch, SHALL distinguish the skeleton distribution context from a user's development workspace, and SHALL direct users to create their first project using the `/worktracker` skill or `jerry session start`." Pass this constraint as a requirement to STORY-002.

### CC-007-20260626: P-001/P-004 — Skeleton Ships Rule Files with Broken `projects/` Cross-References [MINOR]

**Principle:** P-001 (Truth and Accuracy) — verifiable information; P-004 (Explicit Provenance) — citations must be followable
**Location:** `ADR-001-skeleton-derived-branch-strategy.md`, L2 Architectural Implications #1 (plugin surface); implied by REQ-002 (strip `projects/` only)
**Evidence:**

ADR-001: "Full plugin surface preserved — stripping only `projects/` leaves `.claude-plugin/`, `skills/`, `commands/`, `.claude/`, `.context/`, `hooks/` intact."

The `.context/rules/quality-enforcement.md` file (which ships in the skeleton per REQ-005) contains, in its References section:
> `ADR-EPIC002-001 | Strategy selection, composite scores, exclusion rationale | projects/PROJ-001-oss-release/decisions/ADR-EPIC002-001-strategy-selection.md`

The path `projects/PROJ-001-oss-release/decisions/ADR-EPIC002-001-strategy-selection.md` does not exist on the `cowork-skeleton` branch (only `projects/README.md` exists). Similar dead references appear throughout `.context/rules/` citing `projects/PROJ-*/` paths for ADRs, research, and orchestration artifacts. CoWork users who follow citations in the rule files they receive will encounter missing files with no explanation.

**Analysis:** The requirements correctly scope the skeleton as "`.context/` intact" (REQ-005) and do not require modifying `.context/rules/` contents. However, no requirement addresses the resulting dead-reference condition in the shipped rule files. This is a P-001/P-004 concern because the framework's own governance documents contain inaccurate citations on the skeleton branch. While rule files remain functionally operative (they govern behavior; the referenced ADRs are design rationale only), users who inspect the framework documentation will receive misleading provenance trails.

**Remediation:** Add a requirement (e.g., to WS-4 or WS-1) or a documented known-limitation entry: "The `cowork-skeleton` branch ships `.context/rules/` files containing references to `projects/` design artifacts that exist only on `main`. This is an accepted limitation of the skeleton distribution; users requiring ADR provenance should consult the full repository at `https://github.com/geekatron/jerry` on the `main` branch." Alternatively, add the constraint to the Reference document (REQ-028-scope) so CoWork users are explicitly informed. The minimum acceptable remediation is a documented acknowledgment; the more complete fix is a skeleton-specific notice in `.context/rules/quality-enforcement.md` or via the stub README.
