TITLE: nuclear-sop: verifier takes its acceptance criteria from the file it polices (PR #269 review)

Assignees: @victorlau1 (PR author), @malcolm-x-evo (AI agent).

**What this is about:** the skill's "independent verifier" agent (`sop-verifier`) takes its acceptance criteria, expected file paths, and the workflow's declared criticality level from the workflow-definition file — the untrusted input it exists to police. A crafted definition can therefore declare itself low-risk and define passing criteria it trivially meets: the checker's authority comes from the thing being checked (see `sop-verifier.md`, Step 2 / SR-09), and a self-declared low criticality also relaxes every downstream protection (fewer verification hops, weaker default step classification, silenced warnings, a higher per-run step limit, and a lower quality-review iteration cap). Separately, `PROCEDURE_STATE.template.yaml` and `docs/reference.md` claim the execution-state file (PROCEDURE_STATE.yaml) carries SHA-256 tamper detection computed after every write, verified before every tool call; no agent file implements this, and a hand-edited state file resumes cleanly past every pause point (see `sop-executor.md`, RESUME logic). Scope: the verification path for the highest-risk workflow tier — approval already withdrawn pending QG-E4 re-validation (register section REM-04; see #353) and additionally blocked by this and sibling design issues before it can be restored.

Affected files: skills/nuclear-sop/agents/sop-verifier.md, sop-brief.md, sop-executor.md, templates/PROCEDURE_STATE.template.yaml, docs/reference.md, rules/nuclear-sop-behavior-rules.md.

**Design questions to answer:** (1) Where do the verifier's acceptance criteria and expected paths come from, if not the artifact they police (e.g., a user-approved brief fixed at an earlier hold point, orchestrator-supplied criteria, or a signed/pinned copy of the definition)? (2) How is the workflow's declared criticality level cross-checked and auto-escalated against independent signals (such as the paths a step actually touches or the operations it performs, evaluated independently of what the workflow definition itself declares)? (3) Will tamper evidence for PROCEDURE_STATE.yaml be implemented for real (a self-computed hash with no external key or anchor is not protection against the same actor who edits the file — the mechanism must live outside PROCEDURE_STATE.yaml) or withdrawn everywhere it is claimed — and how is a state file hand-edited to skip HELD status stopped from resuming past a hold before execution continues, not just detected afterward? Reply here with your proposed design, or push a commit to this PR implementing it, before requesting re-review.
