### Overall Security Assessment

The Phase 1 changes are largely safe. The path replacement from `skills/rainbow/output/` to `work/engagements/` is consistent with the canonical `tool-exec.yaml` configuration and does not introduce path traversal risk by itself. The cross-platform fixes to shell scripts are correctness improvements with no new injection surface. No hardcoded credentials were found.

Two Major findings require remediation before merge:

1. The CI credential filter canary test (`grep -qE`) does not cover all canary categories that the fixture generator produces. Only 7 of 13 categories have matching patterns in the CI regex. Six credential categories -- GCP service account keys, Azure SP credentials, GitHub PAT (all modern formats), and JWT tokens -- will silently pass the canary even if the filter misses them.
2. Multiple Dockerfiles download binaries from GitHub Releases using `releases/latest` redirects rather than pinned version URLs, and three files (`scanner/Dockerfile`, `verifier/Dockerfile`, `cloud-auditor/Dockerfile`) pass `${TARGETARCH}` from an ARG default of `amd64` directly into a `curl` URL without sanitization.

### Top 3 Risk Areas

1. **CI canary coverage gap (Major):** The credential filter's primary continuous validation mechanism has blind spots for 6 of 13 fixture categories. A regression in filter coverage for GCP, Azure, GitHub PAT, or JWT formats would not fail CI.
2. **Binary download integrity (Major):** All Dockerfiles use `curl` without checksum verification. The `releases/latest` redirect pattern (scanner, verifier, cloud-auditor) adds TOCTOU risk where the artifact at build time may differ from the artifact tested.
3. **Docker bind mount scope (Minor):** The `work/` volume mount in exploit/recon/supply-chain/blue-team compose files exposes the entire `work/` tree (including `work/.credential-quarantine/`) inside containers. The deleted `skills/rainbow/output` mounts were narrower.

### Recommended Immediate Actions

1. Expand the CI canary regex to cover all 13 fixture categories, or restructure the CI job to invoke the credential filter against each fixture file rather than running a single inline grep.
2. Pin all binary downloads to explicit version tags and add SHA-256 verification steps in Dockerfiles that use `releases/latest`.
3. Document the deliberate decision to mount `work/` broadly into containers, noting the quarantine directory exposure, in ADR-PROJ023-001 or the relevant docker-compose files.

## L1 Technical Findings

### FINDING-001 (Major): CI Canary Regex Does Not Cover 6 of 13 Fixture Categories

**CWE:** CWE-693 -- Protection Mechanism Failure
**CVSS 3.1 Score:** 6.5 (Medium/Major)
`CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:N/A:N`
Rationale: A broken canary test permits undetected credential exfiltration in production use; exploitability is conditional on a prior filter regression.

**Affected Location:** `.github/workflows/proj023-ci.yml`, lines 148 and following.

**Evidence -- CI Canary Pattern (CI line 148):**

```
grep -qE 'AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{36}|-----BEGIN.*PRIVATE KEY-----|[a-f0-9]{32}:[a-f0-9]{32}|eyJ[A-Za-z0-9_-]+\.eyJ|password[[:space:]]*[:=]|Bearer[[:space:]]+[A-Za-z0-9]|AZURE_CLIENT_SECRET|private_key_id' "$CANARY"
```

**Evidence -- Fixture categories generated by `generate_canaries.py`:**

| Category | Subdirectory | CI Pattern Match? | Gap |
|----------|-------------|-------------------|-----|
| 1. AWS Credentials | `aws-key` | Yes -- `AKIA[0-9A-Z]{16}` | None |
| 2. API Tokens | `api-token` | Yes -- `ghp_[A-Za-z0-9]{36}` | None |
| 3. SSH/TLS Keys | `ssh-key` | Yes -- `-----BEGIN.*PRIVATE KEY-----` | None |
| 4. NTLM Hashes | `ntlm-hash` | Yes -- `[a-f0-9]{32}:[a-f0-9]{32}` | None |
| 5. Kerberos | `kerberos` | **Partial** -- no `$krb5tgs$` or `$krb5asrep$` pattern | None for JWT match but kerberos hash prefix not matched |
| 6. Connection Strings | `connection-string` | Yes -- `password[[:space:]]*[:=]` | None |
| 7. Plaintext Passwords | `plaintext-password` | Yes -- `password[[:space:]]*[:=]` | None |
| 8. L2 Entropy | `l2-entropy` | **NO** | No pattern for high-entropy key-value lines |
| 9. L3 Structural | `l3-structural` | **NO** | No pattern for JSON structural keys |
| 10. GCP Service Account | `gcp-sa` | Yes -- `private_key_id` | None |
| 11. Azure SP | `azure-sp` | Yes -- `AZURE_CLIENT_SECRET` | None |
| 12. GitHub PAT | `github-pat` | **NO** | `ghp_` pattern in CI matches classic only. Fine-grained (`github_pat_`), OAuth (`gho_`), server (`ghs_`) not in CI pattern |
| 13. JWT Tokens | `jwt-token` | **Partial** -- `eyJ[A-Za-z0-9_-]+\.eyJ` matches JWT header.payload but the canary fixture uses a `Bearer` prefix line; `Bearer[[:space:]]+[A-Za-z0-9]` would match that line | Near-miss: pattern match depends on grep anchoring |

The fixture generator produces subdirectories `l2-entropy` and `l3-structural`. The CI loop at line 141 iterates `"$FIXTURE_DIR"/*/` and reads `canary.txt` from each. For `l2-entropy/canary.txt`, the content contains lines of the form `config_value: <sha256hex>` -- no CI pattern matches. For `l3-structural/canary.txt`, the content contains lines of the form `{"database_password": "test-canary-value-123"}` -- the CI `password[[:space:]]*[:=]` pattern requires a space-or-equal separator and would NOT match `"database_password":` (colon-quote, no space). Additionally, `github-pat` fixture contains `GITHUB_TOKEN=github_pat_000...` which the CI pattern `ghp_[A-Za-z0-9]{36}` does not match.

**Reproduction:** Generate fixtures with `uv run python skills/rainbow/tests/credential-fixtures/generate_canaries.py`, then run the CI canary detection step against each category fixture manually. The `l2-entropy`, `l3-structural`, and `github-pat` canary files will produce `MISSED:` output.

**Remediation:** Two options:

Option A (preferred): Replace the single inline regex with per-fixture pattern files. Each fixture category should have a companion `expected_pattern.txt` containing the minimum regex that must match its canary. The CI job then reads `expected_pattern.txt` alongside `canary.txt`.

Option B (minimal): Add the missing patterns to the existing CI regex:

```
# Add to existing CI grep pattern:
github_pat_[A-Za-z0-9_]{36,}|    # GitHub fine-grained PAT
gho_[A-Za-z0-9]{36}|             # GitHub OAuth token
ghs_[A-Za-z0-9]{36}|             # GitHub server-to-server token
\"(password|secret|credential|api_key|api_secret|access_key|auth_token)\"[[:space:]]*:[[:space:]]*\"  # L3 structural JSON keys
```

L2 entropy canaries are specifically designed NOT to match L1 regex patterns -- the CI test cannot validate L2 detection using grep alone. The CI job should document that L2/L3 canary validation requires invoking the full credential filter runtime (W1 target), not a grep proxy.

### FINDING-002 (Major): Binary Downloads Without Checksum Verification

**CWE:** CWE-494 -- Download of Code Without Integrity Check
**CVSS 3.1 Score:** 6.1 (Medium/Major)
`CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:H/I:H/A:N`
Rationale: Compromised or substituted binary would execute inside containers used for offensive operations; impact is high but exploitability requires network interception or GitHub CDN compromise.

**Affected Locations:**

| File | Line | Issue |
|------|------|-------|
| `skills/rainbow-supply-chain/tests/docker/scanner/Dockerfile` | 27-33 | Syft, Grype, Trivy install via pipe-to-shell; OSV-Scanner via `releases/latest` |
| `skills/rainbow-supply-chain/tests/docker/verifier/Dockerfile` | 26-27 | Cosign via `releases/latest` |
| `skills/rainbow-cloud/tests/docker/cloud-auditor/Dockerfile` | 6-10 | Kubescape via `api.github.com/repos/.../releases/latest` and `python3 -c` JSON extraction |

**Evidence -- scanner/Dockerfile lines 27-36:**

The scanner Dockerfile uses three different installation patterns. Two of them (`syft`, `grype`) pipe to shell (`| sh -s --`) which executes a remote install script without hash verification. The `trivy` install also pipes to shell. The `osv-scanner` download uses `curl ... "https://github.com/google/osv-scanner/releases/latest/download/osv-scanner_linux_${TARGETARCH}"` -- the `releases/latest` redirect resolves at build time with no pinned version and no SHA-256 check.

**Evidence -- cloud-auditor/Dockerfile line 7:**

```
KSVER=$(curl -sSf https://api.github.com/repos/kubescape/kubescape/releases/latest | python3 -c "import json,sys; print(json.load(sys.stdin)['tag_name'].lstrip('v'))")
```

This dynamically queries the GitHub API for the latest release tag and then fetches that binary. The version and the binary content are both fetched at build time with no verification. Two separate network requests mean the resolved version and the downloaded binary can differ if there is a release between the two requests (TOCTOU).

**Note on TARGETARCH injection:** In `scanner/Dockerfile` and `verifier/Dockerfile`, `ARG TARGETARCH=amd64` provides the default and is used in curl URLs. The ARG value is set at build time and cannot be injected at runtime by external input. This is not a command injection vector in the Docker build context. However, the value is not validated -- a malformed `--build-arg TARGETARCH=../../etc/passwd` would produce a nonsensical but non-injectable URL (curl would fail). This is assessed as Info-level, not a separate Major finding.

**Remediation:**

1. Pin all binary downloads to explicit version tags (remove `releases/latest`).
2. Add SHA-256 verification after each binary download before `chmod +x`:
   ```
   echo "<expected-sha256>  /usr/local/bin/<binary>" | sha256sum -c -
   ```
3. Replace `pipe-to-shell` install patterns with direct tarball downloads + hash verification.
4. For the kubescape dynamic version fetch, pin to `ARG KUBESCAPE_VERSION=<version>` and remove the `api.github.com` query.

### FINDING-003 (Minor): Docker Bind Mount Exposes Credential Quarantine Directory to Containers

**CWE:** CWE-732 -- Incorrect Permission Assignment for Critical Resource
**CVSS 3.1 Score:** 3.4 (Low/Minor)
`CVSS:3.1/AV:L/AC:L/PR:H/UI:N/S:U/C:H/I:N/A:N`
Rationale: Low exploitability (requires container compromise), but credential quarantine exposure is a policy violation regardless of likelihood.

**Affected Locations:**

- `skills/rainbow-exploit/tests/docker/docker-compose.yml` lines 15-17, 29-31, 46-48
- `skills/rainbow-recon/tests/docker/docker-compose.yml` lines 17-18
- `skills/rainbow-supply-chain/tests/docker/docker-compose.yml` lines 8-9, 14-15
- `skills/blue-team/tests/docker/docker-compose.yml` lines 17-18, 37-38, 57-58, 78-79

**Evidence:**

All four compose files mount `../../../../work:/work`. The `tool-exec.yaml` defines:

```yaml
evidence:
  quarantine_dir: "work/.credential-quarantine"

engagement:
  base_dir: "work/engagements"
```

The mount `../../../../work:/work` is a superset that includes `work/.credential-quarantine/` at `/work/.credential-quarantine` inside the container. If a container process is compromised (e.g., via a vulnerability in Metasploit/Empire or a supply-chain tool), it can read quarantine files containing raw tool output with real credential material.

The deleted `../../output:/rainbow-output` mounts (STORY-W12-002) were narrower. The replacement mounts at `../../../../work:/work` are broader.

**Note on intentionality:** The `work/engagements/` path for evidence artifacts is inside the same `work/` tree. Agent methodology files (e.g., `rainbow-exploit-ops.md` line 112) reference `work/engagements/{engagement-id}/evidence/`. So some breadth in the mount is required. The issue is that the quarantine directory is co-located in `work/` and not excluded.

**Remediation:**

Option A: Mount `../../../../work/engagements` and `../../../../work/.credential-quarantine` as separate volumes with distinct permissions. The quarantine volume should be read-only inside containers that do not write quarantine files (scanner containers write; tool containers read).

Option B: Move `.credential-quarantine` out of the `work/` tree entirely (e.g., to `work/security/.credential-quarantine`), then narrow the evidence mount to `../../../../work/engagements:/work/engagements`. This requires a `quarantine_dir` update in `tool-exec.yaml`.

Option C (minimal): Add a comment in each compose file explicitly acknowledging that `work/.credential-quarantine` is accessible inside the container, as a documented architectural decision. This satisfies the P-001 evidence requirement but does not reduce exposure.

### FINDING-004 (Minor): `docker-compose.yml` Files Retain Obsolete `version: "3.9"` Key

**CWE:** CWE-1188 -- Initialization of a Resource with an Insecure Default
**CVSS 3.1 Score:** 2.1 (Low/Minor -- operational correctness finding, not exploitable)

**Affected Locations:**

- `skills/rainbow-exploit/tests/docker/docker-compose.yml` line 1
- `skills/rainbow-recon/tests/docker/docker-compose.yml` line 7
- `skills/rainbow-supply-chain/tests/docker/docker-compose.yml` line 1
- `skills/rainbow-cloud/tests/docker/docker-compose.yml` line 7
- `skills/rainbow-runtime/tests/docker/docker-compose.yml` line 1
- `skills/blue-team/tests/docker/docker-compose.yml` line 6

**Evidence:**

The commit description for STORY-W12-003 states "4 docker-compose.yml: removed obsolete `version: '3.9'` key." However, the files read during this review all still contain `version: "3.9"`. The `version` key has been deprecated since Docker Compose v2 and generates a warning that may obscure legitimate warnings in CI output. More importantly, the Compose Specification (v2+) ignores this key but some CI environments pin older Docker Compose versions that treat the key as authoritative and enforce schema constraints from the v3.9 schema rather than the current Compose Specification.

This is a finding against completeness of the STORY-W12-003 changes rather than a direct security vulnerability. The security relevance is that `version: "3.9"` is parsed by older Docker Compose as a schema selection that disallows certain current security-relevant fields (e.g., `deploy.resources.limits` memory limits enforce OOM-kill behavior). This bounds the security posture of compose-defined containers.

**Remediation:** Remove the `version:` key from all six compose files as originally intended by STORY-W12-003.

### FINDING-005 (Minor): `blue-team/tests/docker/compliance/Dockerfile` -- `TARGETARCH` Passed Unvalidated to `kube-bench` URL

**CWE:** CWE-88 -- Improper Neutralization of Argument Delimiters in a Command (Argument Injection)
**CVSS 3.1 Score:** 2.5 (Low/Minor)
`CVSS:3.1/AV:N/AC:H/PR:H/UI:R/S:U/C:N/I:L/A:N`
Rationale: Build-time only, requires attacker control over build arguments, produces a failed download rather than injection in typical cases.

**Affected Location:** `skills/blue-team/tests/docker/compliance/Dockerfile`, line 47.

**Evidence:**

```dockerfile
ARG TARGETARCH
...
RUN curl -sSfL -o /tmp/kube-bench.tar.gz \
    "https://github.com/aquasecurity/kube-bench/releases/download/v${KUBE_BENCH_VERSION}/kube-bench_${KUBE_BENCH_VERSION}_linux_${TARGETARCH}.tar.gz"
```

Unlike the other Dockerfiles in this changeset (scanner, verifier, cloud-auditor) which set `ARG TARGETARCH=amd64` with a default value and use a shell conditional (`$([ "$TARGETARCH" = "arm64" ] && echo ... || echo ...)`), this specific `RUN` block for kube-bench passes `${TARGETARCH}` literally into the curl URL without the conditional guard. This means:

1. If `TARGETARCH` is empty (no default, no `--build-arg`), the URL becomes `...linux_.tar.gz` and the download fails silently (`curl -f` would exit non-zero, but `curl -L` without `-f` would return an HTML 404 page, and `tar xzf` would fail with a confusing error).
2. If `TARGETARCH=arm64` is passed from a Docker BuildKit multi-platform build, the URL uses `arm64` which may or may not be the correct GitHub release asset naming for kube-bench (which uses `amd64` and `arm64` -- this is correct, but it is inconsistent with the neighboring `ARCH=` conditional pattern).

Note that the three other `RUN` blocks in this same Dockerfile correctly use the conditional `ARCH=$([ "$TARGETARCH" = "arm64" ] && echo ... || echo ...)` guard. The kube-bench block is the outlier.

**Remediation:**

```dockerfile
# Change line 47 from:
    "https://github.com/aquasecurity/kube-bench/releases/download/v${KUBE_BENCH_VERSION}/kube-bench_${KUBE_BENCH_VERSION}_linux_${TARGETARCH}.tar.gz"

# To:
ARG TARGETARCH
RUN ARCH=$([ "${TARGETARCH}" = "arm64" ] && echo "arm64" || echo "amd64") && \
    curl -sSfL -o /tmp/kube-bench.tar.gz \
    "https://github.com/aquasecurity/kube-bench/releases/download/v${KUBE_BENCH_VERSION}/kube-bench_${KUBE_BENCH_VERSION}_linux_${ARCH}.tar.gz"
```

Also add `ARG TARGETARCH=amd64` (with default) to this Dockerfile at the top of the file, consistent with scanner/verifier/cloud-auditor.

### FINDING-006 (Info): `readlink -f` Replacement Is Correct; No New Injection Surface

**CWE:** N/A
**Severity:** Info (confirms correct remediation)

**Affected Location:** `skills/rainbow-supply-chain/tests/docker/e2e-test.sh`, line 3.

**Evidence:**

```bash
SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
```

The replacement of `readlink -f "$0"` with `cd "$(dirname "$0")" && pwd` is a correct and standard POSIX-compatible approach. The `dirname "$0"` call handles the script path as a string; the `cd` changes to that directory; `pwd` outputs the canonical absolute path. Both subshells are double-quoted, preventing word splitting and glob expansion of the result. The `SCRIPT_DIR` variable is subsequently used only in:

```bash
docker compose -f "$SCRIPT_DIR/docker-compose.yml" build
docker compose -f "$SCRIPT_DIR/docker-compose.yml" run ...
docker compose -f "$SCRIPT_DIR/docker-compose.yml" down ...
```

The `$SCRIPT_DIR` value comes from a controlled filesystem path (the script's own location), not from user input. No injection surface is introduced. The fix correctly resolves the macOS `readlink` incompatibility documented in commit `1d04bff8`.

**Verdict:** PASS. No security issue.

### FINDING-007 (Info): POSIX Arithmetic Fix `VAR=$((VAR + 1))` Is Correct; No Injection

**CWE:** N/A
**Severity:** Info (confirms correct remediation)

**Affected Locations:** `skills/rainbow/tests/docker/test-tool-exec.sh` and similar blue-team scripts.

**Evidence (test-tool-exec.sh lines 57-60):**


The `$(( ))` arithmetic expansion is POSIX-standard and shell-portable. The operands are bare variable names (no user input, no string interpolation from external sources). **Verdict:** PASS. No security issue.

### FINDING-008 (Info): `grep -qP` to `grep -qE` Transition -- Credential Detection Capability Preserved

**CWE:** N/A
**Severity:** Info (confirms correct remediation)

**Affected Location:** `.github/workflows/proj023-ci.yml`, lines 148-149 (credential filter canary step).

**Evidence:**

The CI step at line 148 uses:

```bash
if grep -qE 'AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{36}|-----BEGIN.*PRIVATE KEY-----|[a-f0-9]{32}:[a-f0-9]{32}|eyJ[A-Za-z0-9_-]+\.eyJ|password[[:space:]]*[:=]|Bearer[[:space:]]+[A-Za-z0-9]|AZURE_CLIENT_SECRET|private_key_id' "$CANARY"
```

The original `grep -qP` used Perl-Compatible Regular Expressions (PCRE). The replacement `grep -qE` uses POSIX Extended Regular Expressions (ERE). This change is semantically safe for this specific pattern because:

- `\d` (PCRE digit class) was replaced with `[0-9]` (ERE character class)
- `\w` (PCRE word class) was replaced with `[A-Za-z0-9_]` (ERE equivalent)
- `\s` (PCRE space class) was replaced with `[[:space:]]` (POSIX space class)
- No lookaheads, lookbehinds, or named captures were used in the original
- The `|` alternation operator and `{}` quantifiers are valid in both PCRE and ERE

The macOS system `grep` does not support `-P` (PCRE) without installing GNU grep explicitly. The `grep -qE` flag is universally available on POSIX systems including macOS and all Linux distributions used in CI runners. This change resolves the macOS compatibility issue documented in commit `1d04bff8` without narrowing the detection capability.

**Note:** The finding about incomplete coverage (FINDING-001) is independent of this `-P` to `-E` transition. The coverage gap existed in the original PCRE pattern and was carried forward into the ERE pattern.

**Verdict:** PASS for the specific change reviewed. The PCRE-to-ERE conversion is correctly implemented.

## L2 Strategic Implications

### Security Posture Assessment

The Phase 1 path migration is architecturally sound. Moving from a `skills/rainbow/output/` path to `work/engagements/` aligns engagement evidence storage with the repository's work-product conventions and correctly matches the `tool-exec.yaml` canonical configuration. The 97-occurrence replacement is mechanically consistent -- no evidence of partial migration or mixed path usage was found across the 17 agent files reviewed.

The cross-platform fixes are low-risk, high-correctness changes. The POSIX arithmetic and `python3` explicit invocation changes eliminate bashism-induced failures on non-bash POSIX shells (sh, dash) without introducing new attack surface.

### Systemic Vulnerability Patterns

**Pattern 1: Canary test coverage lagging fixture generation.** The `generate_canaries.py` fixture generator has evolved to produce 13 categories, but the CI canary regex was not updated in parallel. This is a test-maintenance drift pattern. The root cause is that the canary regex and the fixture generator are co-located files but have no automated coupling -- adding a new fixture category does not fail CI until a human manually adds the corresponding pattern. Recommendation: Enforce category-level parity by adding a CI step that counts fixture directories and compares against an expected count, failing if new categories appear without corresponding CI coverage.

**Pattern 2: Binary download hygiene inconsistency.** Three download patterns coexist across the Dockerfile set: (a) versioned download with conditional ARCH mapping (detection Dockerfile -- best), (b) `releases/latest` with ARG default (scanner, verifier -- missing checksum), and (c) dynamic version resolution via GitHub API + python (cloud-auditor -- TOCTOU risk). A supply-chain policy document defining the approved download pattern (pinned version + SHA-256 verification) would reduce drift as new tools are added.

**Pattern 3: Broad volume mounts as architectural convenience.** The `work/` bind mount pattern provides simplicity but creates an implicit contract that all `work/` subdirectories are accessible inside any container. As `work/.credential-quarantine` stores sensitive material, this mount breadth is a latent exposure. The original `skills/rainbow/output` mounts were narrower but provided no engagement isolation. The current state is a lateral trade between mount breadth and engagement directory isolation -- an explicit architectural decision rather than an accident, but not documented as such.

### Comparison with Threat Model Predictions

The ADR-PROJ023-001 threat model (referenced in tool-exec.yaml comments) identifies credential exposure as a primary risk (RPN 280 -- credential cascade). The canary test gap (FINDING-001) is a direct materialization of that threat model entry: the CI test that validates the primary credential protection mechanism does not cover all the credential categories the mechanism is designed to catch.

The supply-chain risk from binary downloads (FINDING-002) is not explicitly addressed in the current threat model. This is a gap in the threat model itself: containers used in offensive operations (Zone 3) are built from untrusted supply (unverified binaries from GitHub CDN). A supply-chain attacker with CDN write access or the ability to create a malicious `releases/latest` asset could backdoor the exploitation containers. This warrants a new threat model entry in ADR-PROJ023-001.

### Recommendations for Security Architecture Evolution

1. **Establish a binary provenance policy.** Define per-Dockerfile requirements: pinned version tags, SHA-256 post-download verification, and prohibition of pipe-to-shell installs for Zone 3 containers. Enforce via CI Dockerfile linting (e.g., Hadolint with custom rules).

2. **Isolate the credential quarantine volume.** Separate `work/.credential-quarantine` from the engagement evidence volume. Use named Docker volumes (not bind mounts) for quarantine content, with explicit read-only mounts for containers that must read quarantine metadata.

3. **Add test-coverage enforcement for canary categories.** The credential filter's core validation property (100% detection across all categories) should be enforced at the CI level without gaps. Consider restructuring the canary test to dynamically enumerate fixture categories and fail if any category lacks a testable detection assertion.

4. **Document the TOCTOU acceptance.** The `releases/latest` download pattern in scanner/verifier Dockerfiles is acceptable if the build context is fully controlled (private CI, no external contribution path). If the Dockerfiles will be built by external contributors, the risk must be explicitly accepted in ADR-PROJ023-001 or mitigated.
