## 1. Credential Canary Test Patterns

### 1.1 Why Fixtures Instead of Literal Strings

The pre-commit secret scanner (gitleaks / detect-secrets / Trufflehog) runs on staged files before commit. Any `.feature` file, `.py` step definition, or conftest that contains a literal credential-pattern string -- even a fake one -- will cause a hook failure. The canary generator in `skills/rainbow/tests/credential-fixtures/generate_canaries.py` solves this using fragment assembly at runtime. The BDD step definitions must apply identical discipline.

**The core rule:** No test source file may contain a string that, when read linearly by the scanner, matches any of the 15 base patterns in `CredentialFilterService`. Fragment assembly (splitting the pattern-triggering prefix into two string literals joined at runtime) is the approved evasion technique -- it is security-working-as-designed, preventing accidental credential check-in. Fixture files generated by the canary script are excluded from scanner scope via `.gitignore` and the scanner's exclude path config.

### 1.2 Loading Canary Fixtures in pytest-bdd Step Definitions

The canary generator writes one `canary.txt` per category under `skills/rainbow/tests/credential-fixtures/{category}/`. Step definitions load them at runtime, so the scanner never inspects the assembled values.

**Recommended conftest pattern:**

```python
# tests/bdd/tool_exec/conftest.py
import subprocess
from pathlib import Path
import pytest

FIXTURE_BASE = Path("skills/rainbow/tests/credential-fixtures")

REQUIRED_CATEGORIES = [
    "aws-key", "api-token", "ssh-key", "ntlm-hash", "kerberos",
    "connection-string", "plaintext-password", "gcp-sa",
    "azure-sp", "github-pat", "jwt-token",
]


@pytest.fixture(scope="session", autouse=True)
def ensure_canaries_generated() -> None:
    """Regenerate canary fixtures if any category canary.txt is missing."""
    missing = [
        cat for cat in REQUIRED_CATEGORIES
        if not (FIXTURE_BASE / cat / "canary.txt").exists()
    ]
    if missing:
        subprocess.run(
            ["uv", "run", "python",
             str(FIXTURE_BASE / "generate_canaries.py")],
            check=True,
        )


def load_canary(category: str) -> str:
    """Return the full text of a canary fixture file.

    Args:
        category: Subdirectory name under credential-fixtures/.

    Returns:
        File content as a string.
    """
    return (FIXTURE_BASE / category / "canary.txt").read_text(encoding="utf-8")


def load_canary_line(category: str, test_label: str) -> str:
    """Extract a single test line from a canary fixture by its section label.

    Canary files use '# --- Test N: {label} ---' section headers.
    Returns the first non-comment, non-blank line after the matching header.

    Args:
        category: Subdirectory name under credential-fixtures/.
        test_label: Substring to match in the section header (case-sensitive).

    Returns:
        The first content line in that section.

    Raises:
        KeyError: If no section matching test_label is found.
    """
    lines = load_canary(category).splitlines()
    found = False
    for line in lines:
        if found:
            if line.strip() and not line.startswith("#"):
                return line.strip()
        elif test_label in line and line.startswith("# --- Test"):
            found = True
    raise KeyError(f"Section '{test_label}' not found in {category}/canary.txt")
```

## 2. Bypass Test Vectors

### 2.1 Sliding Window Architecture

`filter_output()` implements a two-pass scan:

- Pass 1: single-line scan over each line (fast path for most detections).
- Pass 2: sliding window over N-line groups where N ranges from 2 to `window_size` (default 3).

The window joins lines with no separator (`"".join(lines[i:i+win])`). A credential split across two lines such that the first contains only the prefix and the second contains the suffix will be reconstructed in the joined window and match the pattern.

`window_size` is clamped to a minimum of 2 (`effective_window = max(2, window_size)` at line 244). A caller passing `window_size=1` receives window_size=2 behavior.

### 2.3 Step Definitions for Split Scenarios

Split payloads must not appear as assembled credential strings in source. Use the following construction strategy:

**2-line split (AWS key):**
The step definition assembles the split using the same fragment technique from `generate_canaries.py`. The prefix fragment goes on line 1; the suffix fragment goes on line 2. When joined by the window scanner, the reconstructed string matches the CS pattern. Reference `_aws_access_key()` in the canary generator for the fragment decomposition -- replicate the split point at the prefix/body boundary.

```python
@given("the tool output contains an AWS access key split across 2 consecutive lines")
def aws_key_2line_split(context) -> None:
    # Fragments derived from generate_canaries._aws_access_key() split point.
    # Each fragment alone does not match the CS pattern prefix length requirement.
    # The canary generator splits after the 2-char prefix header ("AK").
    # Reuse that same split here: line 1 = first 2 chars, line 2 = remaining 18 chars.
    # Do NOT inline the assembled 20-char key value -- load from canary fixture instead
    # and split it programmatically.
    full_key_line = load_canary_line("aws-key", "AWS Access Key ID (permanent)")
    # Extract just the key value token (last whitespace-delimited token on the line)
    key_value = full_key_line.split()[-1]
    split_point = 2  # Split after the 2-char prefix header
    context.raw_output = (
        f"prefix: {key_value[:split_point]}\n"
        f"{key_value[split_point:]}\n"
        f"suffix line"
    )
```

**3-line split (password assignment):**
The step must split the pattern across 3 lines such that no single-line pass fires and no 2-line window fires, but the 3-line window fires. The password pattern is `(password|passwd|pwd)\s*[=:]\s*\S{8,}`. A valid split: line 1 = "pass", line 2 = "word", line 3 = "=longvalue999". No 2-line window ("password" without `=value`, or "word=longvalue999" which does not start with a password label) matches the pattern. The 3-line window reconstructs "password=longvalue999" which matches.

```python
@given("the tool output contains a password assignment split across 3 consecutive lines")
def password_3line_split(context) -> None:
    # Split strategy: "pass" | "word" | "=longvalue999"
    # Pass 1 (single line): no line contains the full pattern.
    # Pass 2 (win=2): "password" does not match (no = value); "word=longvalue999"
    #   does not match (no password label prefix).
    # Pass 2 (win=3): "password=longvalue999" matches CI pattern.
    # Fragment construction avoids any single line being a complete credential.
    p1 = "pass"
    p2 = "word"
    p3 = "=longvalue999"  # value >= 8 chars satisfies \S{8,}
    context.raw_output = f"config:\n{p1}\n{p2}{p3}\nend"
    # Note: "word=longvalue999" on a single line does NOT match the CI pattern
    # because the label group requires (password|passwd|pwd) at the start.
```

**4-line split (negative case for window=3):**
Split across 4 lines such that no window of size 2 or 3 reconstructs a matching string. Strategy: distribute the label keyword and value across 4 lines.

```python
@given("the tool output contains a password assignment split across 4 consecutive lines")
def password_4line_split(context) -> None:
    # Split "p" | "ass" | "word" | "=longvalue999"
    # win=2: "pass" (no match), "assword" (no match), "word=longvalue999" (no match)
    # win=3: "password" (no = value), "assword=longvalue999" (no label prefix),
    #        "word=longvalue999" (no label prefix)
    # win=3 never reconstructs "password=longvalue999" as a complete unit.
    context.raw_output = "config:\np\nass\nword=longvalue999\nend"
```

### 2.4 Encoding Attack Vectors

The current `CredentialFilterService` operates on raw string output from tools. The L1 regex layer has no base64 decode step. L2 (entropy) and L3 (structural) detection are documented in the canary generator (Categories 8 and 9) but are not yet implemented in `CredentialFilterService`.

The following encoding vectors bypass the current L1 filter and should be documented as **negative scenarios** in the BDD suite. These are expected failures -- the test must assert non-detection and include a comment that this is a known gap pending L2/L3 implementation.

```gherkin
@encoding @base64 @negative @known-gap
Scenario: Base64-encoded AWS access key is not detected by L1 regex filter (known gap)
  Given the credential filter profile is "default"
  And the tool output contains a base64-encoded AWS access key ID
  # canary generator aws-key/canary.txt Test 4 provides this value
  When the credential filter scans the output
  Then no CredentialDetectedError is raised
  # NOTE: This is a known L1 limitation. L2 entropy detection would catch this.
  # Track as open finding until L2 is implemented.
```

The step for this scenario loads from `load_canary_line("aws-key", "Base64-encoded AWS access key")` -- the canary generator's Test 4 produces the base64 value using `base64.b64encode(assembled_key.encode()).decode()`. The base64 output does not contain any L1 pattern prefix and will not trigger detection.

**Encoding attack surface summary (L1 bypass vectors):**

| Encoding | Detected by Current L1? | Detection Layer Required |
|---|---|---|
| Base64 of any key value | No | L2 (entropy) |
| Hex encoding of key value | No | L2 (entropy) |
| URL-percent encoding (`%3D` for `=`) | No | L1 with decode pre-pass |
| 4-or-more-line split (> window_size) | No | L1 with larger window |
| Unicode homoglyph substitution in prefix | No | L1 normalization pre-pass |
| Null-byte injection mid-token | Partial | Tool-specific |

## 3. Quarantine Verification

### 3.1 Properties to Verify

The feature file specifies three quarantine properties:
1. The quarantine filename stem is the SHA-256 hex digest of the raw output bytes.
2. A companion `*.meta.json` file exists with specified fields.
3. Quarantine path is engagement-scoped when an engagement is active, global otherwise.

Additionally, the implementation applies `0o700` to the quarantine directory (M-10 mitigation, `engagement_initializer.py` line 101). Individual `.raw` files written by the tool executor should carry `0o600`. Both must be verified.

### 3.2 Permissions Discrepancy Note

The feature file header text implies 0o600 file permissions. The `EngagementInitializer.initialize()` applies `0o700` to the **directory** (owner-only, which is stronger than 0o600 because it also prevents directory listing). These are distinct assertions -- test both:

- `os.stat(quarantine_dir).st_mode & 0o777 == 0o700` on the directory.
- `os.stat(quarantine_file).st_mode & 0o777 == 0o600` on individual `.raw` files.

`CredentialFilterService` does not itself create quarantine files. The quarantine write is expected in a higher-level service (tool executor or CLI handler). BDD tests for quarantine properties must exercise that composition layer.

**Step definitions for permission assertions:**

```python
import os
import stat
from pathlib import Path

@then("the quarantine directory has permissions 0o700")
def quarantine_dir_permissions(context) -> None:
    q_dir = Path(context.quarantine_dir)
    actual_mode = stat.S_IMODE(os.stat(q_dir).st_mode)
    assert actual_mode == 0o700, (
        f"Expected quarantine directory mode 0o700, got 0o{actual_mode:o}"
    )


@then("each quarantine file has permissions 0o600")
def quarantine_file_permissions(context) -> None:
    q_dir = Path(context.quarantine_dir)
    for raw_file in q_dir.glob("*.raw"):
        actual_mode = stat.S_IMODE(os.stat(raw_file).st_mode)
        assert actual_mode == 0o600, (
            f"{raw_file.name}: expected mode 0o600, got 0o{actual_mode:o}"
        )
```

### 3.3 SHA-256 Filename Verification

The quarantine filename stem is the SHA-256 hex digest of the raw output bytes using UTF-8 encoding (`EvidenceHasher.hash_string()` encodes via `.encode("utf-8")`). This is content-addressable storage that provides deduplication.

```python
import hashlib
from pathlib import Path

@then("the filename stem is the SHA-256 hex digest of the raw output bytes")
def quarantine_filename_is_sha256(context) -> None:
    expected_hash = hashlib.sha256(
        context.raw_output.encode("utf-8")
    ).hexdigest()
    q_dir = Path(context.quarantine_dir)
    raw_files = list(q_dir.glob("*.raw"))
    assert len(raw_files) == 1, f"Expected 1 .raw file, found {len(raw_files)}"
    actual_stem = raw_files[0].stem
    assert actual_stem == expected_hash, (
        f"Quarantine filename stem '{actual_stem}' does not match "
        f"expected SHA-256 '{expected_hash}'"
    )
```

**Encoding consistency note:** `EvidenceHasher.hash_string()` uses `.encode("utf-8")`. If the quarantine write path uses a different encoding, the hash will not match the filename. The BDD step above hardcodes UTF-8 to match the hasher; if the implementation changes the encoding, both must change together.

### 3.5 Deduplication Scenario

The "identical output produces same quarantine file" scenario (feature file line 213) requires that two invocations with identical raw output produce exactly one file. This works because the filename is the hash of the content: writing the same hash twice either overwrites or the quarantine writer checks existence first.

The step must invoke the full tool executor layer (not just `CredentialFilterService`) because the file write happens above the domain service. If the tool executor uses open-with-exclusive-create (`O_EXCL`), the second write is a no-op. If it uses normal open-for-write, the file is overwritten with identical content. Either way, one file must exist after two scans.

```python
@when("the credential filter scans the output both times")
def filter_scans_twice(context) -> None:
    for _ in range(2):
        context.invoke_tool_exec_with_output(context.raw_output)


@then("only one quarantine file exists (deduplicated by hash)")
def single_quarantine_file(context) -> None:
    q_dir = Path(context.quarantine_dir)
    raw_files = list(q_dir.glob("*.raw"))
    assert len(raw_files) == 1, (
        f"Expected 1 deduplicated .raw file, found {len(raw_files)}: "
        f"{[f.name for f in raw_files]}"
    )
```

## 4. Strict Mode Test Matrix

### 4.1 Variable Definitions

| Variable | Values to Test | Layer |
|---|---|---|
| `JERRY_STRICT_MODE` env var | `"true"`, `"false"`, `""` (empty string), unset | CLI (env var) |
| `strict_mode` parameter | `True`, `False` | Domain (injected boolean) |
| `--no-filter` CLI flag | present, absent | CLI |
| Zone | 1, 2, 3 | Security policy |

`CredentialFilterService.filter_output()` accepts `strict_mode` as an injected boolean (PM-004-R2, H-07 compliance). The CLI handler reads `JERRY_STRICT_MODE` from `os.environ` and resolves it to a boolean before calling the domain. Tests are organized into two layers.

### 4.2 Layer A: Domain-Level Matrix

Direct calls to `filter_output(strict_mode=..., no_filter=...)`. These tests do not touch the CLI or environment variables.

| strict_mode | no_filter | Credential in Output | Expected Outcome |
|---|---|---|---|
| True | False | No | FilterResult(detected=False), no exception raised |
| True | False | Yes | FilterResult(detected=True), filtering proceeds, no RuntimeError |
| True | True | N/A | RuntimeError raised immediately, message contains "FORBIDDEN" |
| False | False | No | FilterResult(detected=False), no exception |
| False | False | Yes | FilterResult(detected=True), no exception |
| False | True | No | FilterResult(detected=False), raw output returned unfiltered |
| False | True | Yes | FilterResult(detected=False), raw output returned (bypass honoured) |

## 5. Path Traversal Test Vectors

### 5.1 Allowlist Pattern

`EngagementInitializer._validate_id()` enforces the following regex against every engagement ID before any filesystem operation (M-05 mitigation, FINDING-002/CWE-22 fix):

```
^[a-zA-Z0-9][a-zA-Z0-9_-]{0,127}$
```

Rules derived from the pattern and the pre-regex guard:
- Empty or whitespace-only strings: rejected by `if not engagement_id or not engagement_id.strip()` before the regex.
- First character: must be alphanumeric `[a-zA-Z0-9]`.
- Remaining characters: alphanumeric, hyphen, or underscore only.
- Maximum length: 128 characters total (first char + up to 127 in body).

`_validate_id()` is called from `initialize()`, `is_initialized()`, `evidence_dir()`, and `quarantine_dir()` -- all trust boundary crossings (FINDING-002 defence-in-depth).

## 7. Risk Assessment

### 7.1 Design Findings (CVSS-Annotated)

All findings are within the authorized scope of RED-W12-BDD engagement. No exploitation was performed; findings are from static design and code review.

**FINDING-BDD-001: Multiple credentials not all redacted**

- CVSS Base Score: 7.5 -- High
- Vector: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N
- Description: `filter_output()` exits on first match. A tool output containing multiple credential patterns will have only the first pattern redacted. All remaining credential material appears in `FilterResult.filtered_output` and is returned to the caller. In an agent context, the unredacted credentials would be injected into the LLM context window (the T-03 threat).
- Evidence: `credential_filter.py` lines 249-257.
- Recommendation: Refactor `filter_output()` to iterate all lines, collect all `CredentialMatch` objects, and perform redaction on all matches before returning. Return a `FilterResult` with a list of matches.
- BDD test: Implement the multiple-credential scenario from feature lines 98-107; it will fail and document the gap.

**FINDING-BDD-002: Exit code mismatch in feature file**

- Severity: High (defect, not exploitable independently)
- Description: Feature file lines 234-239 assert exit code 6 for `--no-filter` in strict mode. The `ExitCode` enum maps `STRICT_MODE_VIOLATION = 9` for this case (M-03). `MODE_UNSET = 6` is for a different scenario. If BDD step definitions assert exit 6, they will pass only if the CLI handler is implemented inconsistently with the stated design.
- Evidence: `exit_codes.py` lines 56-67 vs feature file lines 234-239.
- Recommendation: Update the feature file to assert exit code 9. Verify CLI handler mapping before updating.

**FINDING-BDD-003: SecurityPolicy.permit_bypass field absent**

- CVSS Base Score: 6.5 -- Medium
- Vector: AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N
- Description: The feature file specifies family-level bypass control via `SecurityPolicy`. The `SecurityPolicy` dataclass has no such field. Without it, bypass control is binary (strict mode on/off globally) with no per-family granularity. A tool family that requires mandatory filtering cannot opt out of bypass even in non-strict mode.
- Evidence: `security_policy.py` fields vs feature lines 228-247.
- Recommendation: Add `allow_filter_bypass: bool = True` to `SecurityPolicy`. Test all combinations of the field x strict_mode x --no-filter.

**FINDING-BDD-004: L1 base64 bypass (known gap)**

- CVSS Base Score: 5.3 -- Medium
- Vector: AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N (reduced from High by AC:H -- attacker must control tool output format)
- Description: Any tool whose output contains base64-encoded credential values bypasses all 15 L1 regex patterns. The L2 entropy layer is documented in the canary generator (Category 8) but is not yet implemented in `CredentialFilterService`.
- Evidence: `credential_filter.py` (no entropy check); `generate_canaries.py` lines 738-776.
- Recommendation: Implement L2 entropy scanning as a second filter pass. Until then, add negative BDD scenarios explicitly documenting the bypass as a known gap with a reference to the implementation task.

**FINDING-BDD-005: Quarantine directory permission race (TOCTOU)**

- CVSS Base Score: 3.7 -- Low
- Vector: AV:L/AC:H/PR:L/UI:N/S:U/C:L/I:N/A:N
- Description: `mkdir(..., exist_ok=True)` followed by `os.chmod(0o700)` is not atomic. A brief window exists between directory creation with default umask permissions and the chmod. On shared filesystems this could allow a race, but engagement directories are created in user-owned workspace paths, making exploitation unlikely in practice.
- Evidence: `engagement_initializer.py` lines 94-101.
- Recommendation: Low priority. BDD test should verify the final state post-creation, not attempt to race the window.
