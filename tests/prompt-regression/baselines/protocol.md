## Overview

This protocol governs the N=30 baseline capture process for the PROJ-036 Prompt Regression Harness. The baseline suite establishes the "before" quality distribution for each of the 5 target agents (ps-researcher, ps-analyst, ps-architect, ps-critic, adv-scorer) across their canonical test prompt sets. Baseline data is the reference distribution against which future prompt changes are statistically compared using Wilcoxon signed-rank tests.

**What this protocol covers:**
- Environment setup and pinning for reproducibility
- Execution order and sequencing across all agents and prompts
- Data capture schema for every individual run record
- Statistical validation of the resulting N=30 sample sets
- Cost management and error recovery
- Post-capture integrity verification

**What this protocol does NOT cover:**
- Regression comparison against baselines (handled by the statistical engine in `jerry/testing/stats.py`)
- Prompt authorship (handled in `baselines/prompts/*.yaml`)
- CI/CD gate configuration (handled by promptfoo YAML in `tests/prompt-regression/`)

**Baseline capture is a one-time activity per stable configuration.** Captures are re-run only when the conditions in the [Baseline Refresh Protocol](#baseline-refresh-protocol) section are met.

**Traceability:** Score fields in the data collection schema use SSOT 6-dimension weights from `.context/rules/quality-enforcement.md`. Expected behaviors in prompt files are linked to behavioral contract IDs in `projects/PROJ-036-prompt-regression-harness/contracts/behavioral-contracts.md` (see [Data Collection Schema](#data-collection-schema) for linking convention).

## Statistical Rationale for N=30

### Why N=30 Is the Minimum Adequate Sample Size

The N=30 target is grounded in three independent statistical arguments, each of which independently supports this threshold. All three converge on 30 as the practical minimum.

#### Argument 1: Central Limit Theorem Applicability

The Wilcoxon signed-rank test operates on the distribution of signed differences between paired scores. For the test's normal approximation of the signed-rank statistic to be valid, the difference distribution must be approximately symmetric, which in practice requires N >= 25-30 pairs regardless of the underlying score distribution (Hollander, Wolfe & Chicken [1], p. 35-38).

LLM quality scores have an unknown, potentially non-normal distribution -- empirically, they tend to cluster near 0.7-0.9 with a left skew from occasional structural failures. The Central Limit Theorem guarantees that the sampling distribution of the mean converges to normality as N increases; for moderate-to-high skewness distributions, N=30 is the commonly accepted minimum at which this convergence is reliable enough for inferential testing (Montgomery & Runger [2], p. 226).

At N=30:
- The standard error of the mean is `sigma / sqrt(30) = sigma * 0.183`
- Confidence intervals computed from the sample have adequate precision for the observed variance in LLM quality scores (empirically sigma = 0.08-0.12 based on PROJ-017 Phase 5 evaluation runs; raw data location to be confirmed during implementation -- the estimated sigma range 0.08-0.12 is the calibration input regardless of exact file location[^proj017-path])
- The Wilcoxon normal approximation is valid for N >= 20 (exact tables required below this threshold per Hollander et al. [1]); N=30 provides a 50% safety margin above this minimum

**Consequence of using N < 20:** The statistical engine enforces a runtime hard check (`len(scores) < 20 raises InsufficientSamplesError`, per PROJ-035 ADR-001 code patterns). N=20 is the absolute floor; N=30 is the baseline standard for adequate power.

#### Argument 2: Wilcoxon Signed-Rank Test Power Analysis

For the harness's regression detection use case, we need sufficient statistical power to detect a practically significant quality regression. Based on quality score variance observed in PROJ-017 Phase 5:

- Observed score standard deviation within a single agent/prompt: approximately sigma = 0.08-0.12
- Minimum regression effect size of practical significance: delta = 0.05 (5 percentage points on the 0-1 quality scale -- chosen as the metamorphic relation tolerance threshold from PROJ-035 ADR-001 MR-001)
- Target power: >= 0.80 (80% probability of detecting a true regression of this magnitude)
- Significance level: alpha = 0.05 (two-sided)

Using the normal-approximation power formula for nonparametric tests (Noether [3]):

```
N >= (z_alpha/2 + z_beta)^2 * sigma^2 / delta^2

For alpha=0.05, beta=0.20:
N >= (1.96 + 0.84)^2 * (0.10)^2 / (0.05)^2
N >= 7.84 * 0.01 / 0.0025
N >= 7.84 * 4
N >= 31.36
```

This rounds up to N=32 at sigma=0.10. At the lower observed sigma of 0.08:

```
N >= 7.84 * (0.08)^2 / (0.05)^2
N >= 7.84 * 0.0064 / 0.0025
N >= 7.84 * 2.56
N >= 20.07
```

**Important methodological note:** The formula applied here is Noether's normal-approximation formula, derived originally for the sign test [3]. For the Wilcoxon signed-rank test, the asymptotic relative efficiency (ARE) of the Wilcoxon versus the t-test is 3/pi ≈ 0.955 for normal data and can exceed 1.0 for non-normal distributions (Hollander et al. [1], p. 116). This means the Noether formula applied to the Wilcoxon test is a conservative lower bound on sample size: the actual Wilcoxon power at N=30 is at least as high as the formula predicts, and typically higher for the non-normal score distributions observed in LLM evaluation. The choice of Wilcoxon over a parametric paired t-test is further supported by Dror et al. [6], who demonstrate that non-parametric significance tests are preferred for NLP evaluation metrics when score distribution normality cannot be assumed -- precisely the condition that applies to LLM quality scores.

**The power-analysis-derived range is N=20 to N=32 across the plausible variance range.** N=30 sits within this range and provides:
- 80%+ power at sigma <= 0.09 (derived directly from the formula)
- Approximately 78% power at sigma=0.10 (slight shortfall; the Noether approximation gives N=31.4; N=30 is accepted as a practical standard with explicit acknowledgment of this minor gap)
- 90%+ power at sigma=0.08 (optimistic variance estimate)
- Adequate margin above the N=20 absolute floor

#### Argument 3: Wilson Score Interval Precision

The Wilson score confidence interval for a proportion (Wilson [4]) is used to estimate the pass rate above the 0.92 quality gate threshold. The interval has width proportional to `1/sqrt(N)`. At N=30 with a true pass rate of p=0.70:

```
Wilson interval half-width = z * sqrt(p*(1-p)/N + z^2/(4*N^2)) / (1 + z^2/N)

At N=30, p=0.70, z=1.96:
Half-width ≈ 1.96 * sqrt(0.70*0.30/30) / 1.128
           ≈ 1.96 * sqrt(0.007) / 1.128
           ≈ 1.96 * 0.0837 / 1.128
           ≈ 0.1455

95% CI: [0.555, 0.845] -- width 0.290
```

At N=20 (half-width increases to approximately 0.185): `95% CI: [0.515, 0.885]` -- width 0.370.

N=30 reduces Wilson interval width by approximately 21% relative to N=20, providing meaningful precision improvement. For detecting whether two prompt versions differ in their pass rates (the primary regression detection question), N=30 achieves adequate precision for practical effect sizes.

**Why Wilson over Wald (normal approximation)?** The Wald interval `p ± z*sqrt(p*(1-p)/n)` exhibits poor coverage at small N and extreme proportions (Agresti & Coull [5]). Wilson's interval maintains near-nominal coverage for N >= 10 and any p, making it preferable for our range of plausible pass rates (0.20-0.90).

#### Summary

| Argument | Minimum N Derived | Safety Margin at N=30 |
|----------|--------------------|----------------------|
| CLT applicability (Hollander et al. [1]) | 25-30 | 0-20% margin |
| Wilcoxon power, sigma=0.08-0.10 (Noether [3]) | 20-32 | 0-50% margin |
| Wilson interval precision (Wilson [4]) | 25-30 | 0-20% margin |
| **Convergence** | **30** | **Adequate across all arguments** |

N=30 is the minimum sample size that satisfies all three arguments simultaneously. N < 30 degrades at least one of the three statistical guarantees. N > 30 provides diminishing returns relative to cost (each additional run costs approximately $0.15-0.25 in API fees).

### Model Version Pinning

**CRITICAL:** Baselines MUST be captured against a pinned model version. Baseline data is invalidated if the model version changes. Record the model version in every baseline run record.

```bash
# Pin the target model version for baseline capture
export HARNESS_MODEL_VERSION="claude-sonnet-4-20250514"
export HARNESS_JUDGE_MODEL_VERSION="claude-sonnet-4-20250514"
```

The model version string MUST match the Anthropic API model identifier exactly. Do NOT use alias strings like `claude-sonnet-latest` -- aliases resolve to different model versions over time and break baseline reproducibility.

**Version verification:**
```bash
uv run python -c "
import anthropic, os
client = anthropic.Anthropic()
# Send a minimal test request to verify model version is accessible
response = client.messages.create(
    model=os.environ['HARNESS_MODEL_VERSION'],
    max_tokens=10,
    messages=[{'role': 'user', 'content': 'Say: OK'}]
)
print(f'Model version verified: {response.model}')
"
```

### Temperature Settings

LLM temperature MUST be set to `temperature=1.0` (Anthropic default for sampling). Do NOT use `temperature=0` for baseline capture.

**Rationale:** The harness's purpose is to characterize the actual output quality distribution, including its natural variance from LLM stochasticity. Setting `temperature=0` would collapse this distribution to near-deterministic outputs, producing artificially narrow variance estimates that underestimate real-world regression risk. The N=30 samples at natural temperature provide the true distribution the statistical engine needs.

**Exception:** Smoke-mode structural checks (deterministic checks only) MAY use `temperature=0` for reproducibility, but smoke-mode outputs are NOT baseline data and MUST NOT be included in baseline suites.

## Reproducibility Controls

### Run ID Generation

Every individual run MUST be assigned a globally unique run ID before execution:

```python
import uuid
import hashlib

def generate_run_id(agent: str, prompt_id: str, run_index: int, timestamp: str) -> str:
    """Generate a deterministic, unique run identifier.

    Format: RUN-{agent-short}-{prompt-id}-{run_index:03d}-{uuid4-prefix}
    Example: RUN-psr-P-PSR-001-027-a3f2

    Agent short codes (unique per agent -- no collisions):
        ps-researcher -> 'psr'
        ps-analyst    -> 'psa'
        ps-architect  -> 'pac'   # Note: 'pac' not 'psc' to avoid collision with ps-critic
        ps-critic     -> 'psc'
        adv-scorer    -> 'ads'
    """
    agent_short = {
        'ps-researcher': 'psr',
        'ps-analyst': 'psa',
        'ps-architect': 'pac',   # pac = ps-architect (distinct from psc = ps-critic)
        'ps-critic': 'psc',
        'adv-scorer': 'ads',
    }.get(agent, agent[:3])
    unique_suffix = str(uuid.uuid4())[:4]
    return f"RUN-{agent_short}-{prompt_id.lower()}-{run_index:03d}-{unique_suffix}"
```

**Note on agent short codes:** `ps-architect` uses `'pac'` and `ps-critic` uses `'psc'`. These codes are unique -- no two agents share the same short code. This ensures the run_id prefix unambiguously identifies the generating agent, which is required for V-005 (duplicate run ID detection) to function correctly.

### Model Version Locking

The model version is recorded in three places for traceability:

1. **Baseline manifest** (`baselines/manifest.json`): Records the model version for the entire baseline suite
2. **Baseline suite** (`baselines/data/{agent}/baseline-suite.json`): Records the model version per agent suite
3. **Individual run record** (`baselines/data/{agent}/{prompt_id}/run-{NNN}.json`): Records model version per run

If the `HARNESS_MODEL_VERSION` environment variable does not match the model version recorded in an existing baseline manifest, the capture script MUST abort with an error:

```
ERROR: Model version mismatch. Existing baseline captured against
'claude-sonnet-4-20250514', current HARNESS_MODEL_VERSION='claude-sonnet-4-20251201'.
To capture against a new model version, run: uv run jerry baselines refresh --reason model-upgrade
```

### Timestamp Recording

Every run record MUST include:

1. **`capture_timestamp_utc`**: ISO 8601 UTC timestamp at run initiation (`2026-03-07T14:23:11.482Z`)
2. **`capture_session_id`**: A session-level ID shared across all runs in a single capture invocation

```python
from datetime import datetime, timezone

def current_utc_timestamp() -> str:
    return datetime.now(timezone.utc).isoformat()

def generate_session_id() -> str:
    import uuid
    ts = datetime.now(timezone.utc).strftime('%Y%m%d-%H%M')
    return f"SESSION-{ts}-{str(uuid.uuid4())[:6]}"
```

### Git Commit Hash Tracking

The git commit hash of the agent definition file MUST be recorded in each run:

```bash
# Get commit hash of the agent definition at capture time
git log --format="%H" -1 -- skills/problem-solving/agents/ps-researcher.md
```

This enables exact reproducibility: to re-run any individual baseline run, check out the git commit hash recorded in the run record and re-execute.

### Phase 2: Agent-by-Agent Execution

Execute agents in the following order. The order is chosen to distribute cost evenly and to allow early detection of schema or API issues before committing to the full capture.

**Execution order:**
1. ps-critic (cheapest: reads existing artifacts, sonnet model)
2. adv-scorer (cheapest: reads existing artifacts, sonnet model)
3. ps-analyst (moderate: sonnet model)
4. ps-researcher (most expensive: opus model, web search)
5. ps-architect (most expensive: opus model, ADR generation)

For each agent, execute the following loop:

```bash
# Template: replace AGENT_NAME and PROMPT_FILE with actual values

AGENT_NAME="ps-critic"
PROMPT_FILE="projects/PROJ-036-prompt-regression-harness/baselines/prompts/ps-critic-prompts.yaml"

uv run python projects/PROJ-036-prompt-regression-harness/scripts/capture_baseline.py \
  --agent "${AGENT_NAME}" \
  --prompts "${PROMPT_FILE}" \
  --n-runs 30 \
  --session-id "${CAPTURE_SESSION_ID}" \
  --model-version "${HARNESS_MODEL_VERSION}" \
  --output-dir "projects/PROJ-036-prompt-regression-harness/baselines/data/${AGENT_NAME}" \
  --requests-per-minute 60 \
  --tokens-per-minute 200000 \
  --resume  # Enables checkpoint-based resumption on failure
```

The `--resume` flag enables safe interruption and resumption: completed runs are skipped, incomplete runs are retried.

**Default flag values for `capture_baseline.py`:**
- `--requests-per-minute`: 60 (adjust down for Tier 1 API access; Tier 2+ supports 120+)
- `--tokens-per-minute`: 200000 (adjust based on your API tier)
- `--batch-size`: 1 (sequential; use 3-5 for Tier 2+ to speed up capture)
- `--eval-mode`: `full` (evaluates each run as captured; use `skip` for raw-only first pass)
- `--n-runs`: 30 (the baseline standard; do not change without updating the manifest schema)

### Phase 3: Per-Agent Completion Validation

After each agent completes all N=30 x P prompts runs, validate the captured data:

```bash
uv run python projects/PROJ-036-prompt-regression-harness/scripts/validate_baseline.py \
  --agent "${AGENT_NAME}" \
  --data-dir "projects/PROJ-036-prompt-regression-harness/baselines/data/${AGENT_NAME}" \
  --expected-runs 30
```

This script checks:
- Exactly N=30 valid (non-error) run records per prompt
- Schema compliance of all run records
- Score value ranges (all scores in [0.0, 1.0])
- No duplicate run IDs

## Error Handling

### API Timeout

**Symptom:** `anthropic.APITimeoutError` or requests that do not return within 120 seconds.

**Recovery procedure:**
1. The capture script automatically retries with exponential backoff (3 attempts: 30s, 60s, 120s wait)
2. If all retries fail, the run record is written with `api_error: "timeout_after_3_retries"` and `raw_output: null`
3. The run is marked as FAILED in the session log
4. Capture continues with the next run (do not abort the session)
5. After session completes, re-run failed runs: `uv run python capture_baseline.py --retry-failed`

**Validation impact:** Runs with `api_error != null` are excluded from the N=30 valid run count. The capture script automatically adds replacement runs to reach N=30 valid runs.

### Rate Limiting

**Symptom:** `anthropic.RateLimitError` (HTTP 429).

**Recovery procedure:**
1. The capture script implements token-bucket rate limiting with a default of 60 requests/minute
2. On 429 receipt, the script pauses for 60 seconds and retries
3. If 429 persists after 3 retries, the script enters a slow mode: 1 request per 90 seconds
4. Slow mode continues until 3 consecutive successful requests, then returns to normal rate

**Configuring rate limits for your API tier:**
```bash
uv run python capture_baseline.py \
  --requests-per-minute 30 \
  --tokens-per-minute 100000
```

### Partial Completion

**Symptom:** Capture session interrupted (network outage, process kill, machine restart).

**Recovery procedure:**
1. The `--resume` flag enables checkpoint-based resumption: completed runs are stored to disk immediately after each run
2. On restart, the script reads the session's checkpoint file (`baselines/data/{agent}/.checkpoint-{session-id}.json`)
3. Runs already completed are skipped; incomplete runs resume from where the session stopped
4. If a checkpoint file is corrupted, use `--rebuild-checkpoint` to reconstruct from completed run records in the output directory

**Checkpoint format:** The checkpoint file records completed run IDs and counts per prompt, updated atomically after each successful run write.

### Evaluation Failure

**Symptom:** DeepEval metric evaluation raises an exception (model error, malformed output).

**Recovery procedure:**
1. Evaluation errors are captured in `evaluation_error` field; `scores` object is populated with `null` values
2. A run with `evaluation_error != null` is still counted as a valid run for N=30 purposes IF `raw_output` is non-null
3. Score-based statistical analysis excludes runs with `evaluation_error != null`
4. If more than 20% of runs for a prompt have evaluation errors, re-evaluate all runs: `uv run python re_evaluate.py --prompt P-PSR-001`

### Schema Validation Failure

**Symptom:** `validate_baseline.py` reports schema validation errors.

**Recovery procedure:**
1. Identify the failing run records: the validation script reports run IDs and failed fields
2. Common causes: `output_token_count` set to incorrect type, `scores` object missing a required dimension
3. Fix data in-place using the repair script: `uv run python repair_run_record.py --run-id RUN-psr-p-psr-001-027-a3f2 --fix-field scores.traceability --value 0.65`
4. Re-run validation after repair
5. If the failure is systematic (affects many runs), identify the bug in the capture script, fix it, and re-capture the affected runs

## Baseline Refresh Protocol

### When to Refresh Baselines

Baselines MUST be refreshed when any of the following conditions are met:

| Trigger | Severity | Action Required |
|---------|----------|----------------|
| **Model version upgrade** | MANDATORY | Full re-capture against new model version before retiring old baselines |
| **Agent definition change** | MANDATORY for significant changes | Re-capture for the affected agent only |
| **Prompt file change** | MANDATORY | Re-capture for the affected prompt only |
| **Scoring algorithm change** (DeepEval version bump) | MANDATORY | Re-capture all agents |
| **Baseline quality gate failure** (median < 0.65) | MANDATORY | Investigate and fix, then re-capture |
| **Statistical drift detected** (score distribution shift > 2 sigma over 90 days) | RECOMMENDED | Investigate before re-capture |

Baselines do NOT need to be refreshed for:
- Infrastructure changes that do not affect the LLM invocation (CI/CD config, script refactoring)
- Adding new prompts to a prompt file (new prompts need fresh capture; existing baselines remain valid)
- Project documentation updates

### Refresh Procedure

```bash
# Step R-1: Tag the current baseline as historical before overwriting
git tag "baseline-${CURRENT_MODEL_VERSION}-$(date +%Y%m%d)" HEAD

# Step R-2: Record refresh rationale in manifest
uv run python scripts/record_refresh.py \
  --reason "model-upgrade" \
  --old-model "${OLD_MODEL_VERSION}" \
  --new-model "${HARNESS_MODEL_VERSION}" \
  --comment "Anthropic released claude-sonnet-5; re-baselining all agents"

# Step R-3: Execute fresh capture (same procedure as initial capture)
# ... (follow Step-by-Step Run Procedure above)

# Step R-4: Validate new baselines meet quality gate before retiring old
uv run python scripts/check_baseline_quality.py --min-median-composite 0.65

# Step R-5: Retire old baseline data (move to baselines/archive/, do not delete)
mv baselines/data baselines/archive/data-${OLD_MODEL_VERSION}-$(date +%Y%m%d)
mv baselines/suites baselines/archive/suites-${OLD_MODEL_VERSION}-$(date +%Y%m%d)
```

### Baseline Versioning

Baselines are versioned by a composite key: `{model_version}:{agent_definition_git_hash}:{prompt_file_git_hash}`. This key is stored in the manifest and in each run record. The statistical engine uses this key to ensure it always compares a candidate prompt version against the correct baseline.

**Note on [3]:** Noether's 1987 formula was derived for the sign test. Its application to the Wilcoxon signed-rank test yields a conservative (lower) bound on N because the Wilcoxon test is more powerful than the sign test for symmetric distributions (ARE = 3/pi ≈ 0.955 vs. the sign test; Hollander et al. [1], p. 116). The actual N needed for 80% power under the Wilcoxon test is at most what Noether's formula predicts, and typically less.

**Note on [6]:** Dror et al. (2018) provide a comprehensive evaluation of significance tests for NLP tasks, demonstrating that non-parametric tests (Wilcoxon, bootstrap) outperform parametric tests (t-test) when score distributions deviate from normality -- the expected condition for LLM quality scores. The paper's recommendation to avoid assuming normality for NLP evaluation metrics directly supports the protocol's choice of Wilcoxon signed-rank over a paired t-test.
